## Hard Constraints

1. **Local-only thesis preserved.** No new outbound call destinations beyond `localhost:11434` (Ollama) and the existing user-opt-in OTLP endpoint. No new third-party data processors. No new commercial relationships.
2. **No new product surface besides the VS Code extension.** Browser extensions, federation, hosted UIs, and multi-provider routing are explicitly out of scope (per Section 13 N1-N5 of the comparison report).
3. **No cross-platform sandbox in v0.7.0.** Per Section 13 N6, the sandbox-for-yolo-mode candidate is dropped this cycle. Document the existing `toolConfirmationMode = "never"` risk in [docs/archive/versions/v0/v0.7.0/architecture.md](../architecture.md) and revisit in v0.8.0.
4. **Backwards-compatibility is not a goal.** When a setting or command surface changes (e.g. permission-prompt UX from Yes/No modal -> numbered keyboard shortcut), references update; no compatibility shims are left behind beyond the single `Yes/No`-as-alias dual-label policy noted in Section 13 of the comparison report.
5. **AGENTS.md discipline preserved.** Conventional commits, SHA-pinned actions, ASCII-only commit messages, no `Co-Authored-By` lines.
6. **No backsliding on the v0.6.0 module-boundary contract.** Every new file lives in the right module per [configs/dependency-cruiser.cjs](../../../../configs/dependency-cruiser.cjs); any baseline exception added is rejected.
7. **Definition of Done for v0.7.0**:
   - **Phase 0 close-out**: every v0.7.0 known-gaps Section 1-4 P1 item closed -- live-Ollama baselines (v0.4.0 + v0.6.0) captured against `gemma4:e4b`; post-tag v0.6.0 exit verification reproduced clean; v0.7.0 cycle-plan files committed; panel < 400 lines after ChatController construction-graph hoist (ADR-0009 lands); marked at ^12 with renderers rewritten; mutation-testing focused-runner score > 60% (up from 50.64%); orchestration directory back in Stryker; `tests/benchmarks/baselines/v0.7.0-precycle.json` captured.

   - `~/.gemma-code/memory/<workspace-id>/` is auto-created on first session with Instructions.md / Memory.md / Context.md scaffolds; weekly Archive snapshots fire on a schedule the user can disable; the file system is the source of truth when in conflict with SQLite-stored memories.

## Overview

v0.7.0 is the first feature release after the v0.6.0 hygiene cycle. It opens with **Phase 0**, a foundation phase that discharges the operator-action items and P1 carryovers documented in [docs/archive/versions/v0/v0.7.0/known-gaps.md](../known-gaps.md) (live-Ollama baseline capture, post-tag exit verification, panel decomposition / ChatController hoist, marked v12 migration, mutation-testing gap fixes, pre-cycle baseline). Phase 0 must complete before any feature work begins, because the panel hoist and marked migration both touch surfaces (`GemmaCodePanel`, `MarkdownRenderer`) that the later UX overhaul will modify -- doing them later would require re-doing the migration on top of new code.

Phases 1-8 then sequence the adoption work so that **infrastructure work other phases depend on lands first** (memory file architecture in Phase 2; deterministic strategies + compress tool in Phase 3), and the **UI overhaul (Phase 4)** lands once the agent loop emits the new structured events. Phase 5 polish lands the smaller commands and the manual memory page UI. Phase 6 lands the multi-harness skill packaging and the standalone CLI. Phase 7 lands the optional HNSW vector-index swap and background workers. Phase 8 closes with ADRs, baselines, and the release gate.

The user-visible delta in v0.7.0 is large: a measurably more presentable webview, a memory architecture the user can directly edit on disk, model-driven context compression that recovers from long sessions without a global truncation, and a richer skill set for design/polish/critique workflows. The internal-developer-visible delta is moderate: a new tool handler under `src/tools/handlers/compress.ts`, a new storage module `src/storage/MemoryFiles.ts`, an expanded webview render protocol, and a new build script for the multi-harness export.

Success is measured through three artifacts: (a) `tests/golden/baselines/v0.7.0.json` and a regression delta against `v0.6.0.json` proving no quality regression; (b) `tests/benchmarks/baselines/v0.7.0.json` proving no perf regression past the v0.6.0 thresholds; (c) a manually-graded "Claude-Code-resemblance" UX walkthrough where the seven primitives from S7 are observable in a fresh session.

> - `distill`: Strip a piece of code or a function to its essence -- remove indirection, simplify conditionals, collapse abstractions that have only one consumer. Behaviour-preserving.
> - `harden`: Add error handling, input validation, edge-case coverage, retry/timeout where appropriate. Each addition must trace to a specific risk.
> - `animate`: Introduce purposeful motion / interactivity to UI elements. Restricted to webview / extension UI surfaces (not generic). Argument: target file or component.

Add a unit test in `tests/unit/skills/SkillLoader.test.ts` that asserts each new skill is loaded and has non-empty `description` and `prompt`. #### 3.1 -- Deduplication compaction strategy

**Objective**: Adopt C13. Eliminate same-tool-same-args repeated outputs from the conversation history.

**Prompt**:
> Create `src/chat/strategies/deduplication.ts` exporting a `deduplicate(messages: Message[], state: CompactionState, config: CompactionConfig): Message[]` pure function. Algorithm:
> 1. Walk messages newest-to-oldest, building a Map<signature, idx> where `signature = toolName + ":" + canonicalizeArgs(args)`. `canonicalizeArgs` sorts object keys, trims whitespace in string args, and JSON-stringifies.
> 2. For tool-result messages whose signature already maps to a more-recent message, replace the older content with `[deduplicated -- see message #${recentIdx}]`.

#### 3.4 -- `compress_range` tool handler

**Objective**: Adopt C12 (range mode).

**Prompt**:
> Create `src/tools/handlers/compress.ts` exporting two tool handlers: `compressRangeHandler` and `compressMessageHandler`. Register both in [src/tools/ToolCatalog.ts](../../../../src/tools/ToolCatalog.ts) with `permission_tier: 0` (auto-approve), `category: "compaction"`. The compressRange handler accepts:
> ```typescript
> {
>   topic: string;     // 3-5 word label, displayed in /compact context
>   ranges: Array<{
>     startId: string;   // e.g. m0005 or b3
>     endId: string;
>     summary: string;   // technical summary replacing the range
>   }>;
> }
> ```
> Algorithm:
> 1. Validate args (Zod schema). Reject empty ranges, reject ranges where startId index > endId index, reject ranges that overlap each other in a single call.
> 2. For each range, call `state.allocateBlockId()` and apply: replace messages in `[startId..endId]` with a placeholder message of role `system` and content like `[BLOCK ${blockId}: ${topic}]\n${summary}`. If the range overlaps an earlier block, embed that block's summary inside the new summary (resolveOverlap helper).
> 3. Append protected user messages to the end of the summary block (per `protectUserMessages` setting; default false).
> 4. Append protected tool outputs to the end (per protectedTools list).
> 5. Record a CompressionRun in CompressionState.
> 6. Return success metadata (block IDs created; tokens saved estimate).
>
> The tool's prompt description (the model-facing text) lives in `src/chat/prompts/compress-range.md` and is **written by us, not copied from S5** (S5 is AGPL-3.0). The prompt explains: when to compress (after task completion, before context-pressure rather than after), what to summarise (key decisions, file references, error states; not chit-chat), the format the model must emit (JSON matching the schema). Document in [docs/archive/versions/v0/v0.7.0/architecture.md](../architecture.md) the schema and lifecycle.
>
> Tests in `tests/unit/tools/handlers/compress-range.test.ts`: (a) three messages compressed, placeholder visible; (b) overlapping ranges in same call -> rejected; (c) range that overlaps a prior block -> nested correctly; (d) protected tool output preserved verbatim at end of summary. Acceptance: feature green, mutation tests pass.

## Phase ordering rationale (recap)

1. Phase 0 (v0.6.0 close-out) discharges every P1 obligation in [docs/archive/versions/v0/v0.7.0/known-gaps.md](../known-gaps.md) before feature work starts. Without this, the panel hoist and marked migration would have to land on top of changes from later phases that touch the same surfaces, doubling the work.
2. Phase 1 (skills) ships zero-code-first so the catalog change is visible immediately.
3. Phase 2 (memory file architecture) underpins both the build-second-brain skill from Phase 1 (which is non-functional until Phase 2 lands) and the manual memory page UI in Phase 5.
4. Phase 3 (compaction stack) is the largest single piece of code; it changes both the agent loop's compaction surface AND adds a tool. It runs after Phase 2 because the diff size of phase 2+3 in one PR would be too large to review safely.
5. Phase 4 (UX) depends on Phase 3 to emit the structured events the new render protocol needs.
6. Phase 5 (memory polish) lands the smaller commands + manual memory UI on top of Phase 2 + Phase 4.
7. Phase 6 (multi-harness packaging + CLI) lands once the skill catalog is final (Phase 1).
8. Phase 7 (HNSW + background workers) is optional polish; defer to v0.8.0 if cycle is tight.
9. Phase 8 (release gate) closes.

## Cross-phase risks (recap from comparison Section 13)

- Memory file architecture doubles the memory surface. Mitigate via deterministic merge precedence + meta-test.
- Compress tool changes prompt-prefix shape. Mitigate by Ollama not having provider-side cache; in-process tool-output cache unaffected.
- Numbered permission prompts change keyboard contract. Mitigate via Yes/No alias.
- Multi-harness packaging is one-way mirror. Document scope in dist/ READMEs.
- HNSW native dep. Optional dep + linear-scan fallback.
- Background workers must NOT fire on a timer; only post-N-edits.
