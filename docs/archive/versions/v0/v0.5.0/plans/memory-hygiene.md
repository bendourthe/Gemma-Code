**Hard Constraint**: 100% offline-first single-GPU. No runtime network egress, no cloud APIs. **Do not adopt** Foundry's `/foundry-ingest`, `/foundry-compile`, or `/foundry-ask` commands as Gemma slash commands (out of scope: knowledge management); the "no CI / no automation" discipline (Gemma actively benefits from CI); Obsidian-style plugin recommendations (Gemma is bound to VS Code); and the auto-generated *wiki* under `docs/` (a synthesized concept-wiki — different from the in-scope auto-generated *catalog* at `docs/index.md`, which is a per-module summary index).

**Goal**: Adopt all 6 in-scope items from the foundry-vault comparison so that Gemma's memory subsystem self-reports its health, consolidation discipline rejects single-source assertions by default, and project documentation encodes a who-writes-where contract plus a per-tool-call operation log and a regenerated module catalog.

## Overview

This plan adopts the 6 in-scope items from [docs/archive/versions/v0/v0.5.0/comparison/comparison-foundry-vault.md](../comparison/comparison-foundry-vault.md), grouped into 3 dependency-ordered phases. Phase 1 ships the `/memory lint` slash command (with a `--dry-run` alias) that walks every memory entry and emits a `memory-health.md` report covering stale entries, broken file-path references, embedding-failed rows, and duplicate facts — report-only, never destructive. Phase 2 hardens `MemoryConsolidator` with an N-corroboration rule (default N=2): a single-turn observation is recorded as a *candidate* with `corroboration_count = 1`; a fact is only promoted to retrievable semantic memory once N independent turns corroborate it. Phase 3 lands documentation discipline: a who-writes-where contract section in `CLAUDE.md`, an opt-in append-only `.gemma-code/operation-log.md` (grep-friendly, one line per tool call), and a regenerated `docs/index.md` per-module summary that contributors can read at a glance.

The user-visible delta is small but measurable. The agent's recall behavior shifts subtly: paranoid one-off observations stop being treated as facts. The user gains a `/memory lint` command they can invoke any time to see what's wrong with the memory store. Future contributors land in `docs/index.md` and see the project's module map at one screen. The operation log is opt-in (default off) and provides a forensic timeline for any single session.

Success is measured against three artifacts: a `memory-health.md` produced by `/memory lint` against a synthetic memory state with all four issue classes present (stale, broken-path, embedding-failed, duplicate); an end-to-end consolidation test exercising N=1, N=2, N=3 scenarios plus backfill correctness; and a 1-task golden eval (the "missed-fact" test) where the agent must NOT act on a single-source observation as if it were a corroborated fact.

### Sub-tasks

#### 1.1 — `MemoryHealthCheck` module + `/memory lint` slash command

**Objective**: Add `src/storage/MemoryHealthCheck.ts` that walks each memory layer and produces a structured report; wire it to `src/commands/CommandRouter.ts` as `/memory lint`.

**Prompt**:
> You are working on Gemma Code v0.5.0 (TypeScript VS Code extension; offline-first; uses Ollama + Gemma 4). Implement the memory health-check surface.
>
> Create `src/storage/MemoryHealthCheck.ts` exposing:
>
> - `class MemoryHealthCheck { run(opts?: { limit?: number; full?: boolean }): Promise<MemoryHealthReport> }`
> - `type MemoryHealthReport = { generatedAt: string; counts: { totalEntries, byLayer: Record<Layer, number> }; issues: { stale: StaleIssue[]; brokenPath: BrokenPathIssue[]; embeddingFailed: EmbeddingFailedIssue[]; duplicate: DuplicateIssue[] }; summary: string }`
>
> Default scope (cheap; runs in seconds): scan the most recent 1000 entries per layer; with `full: true`, scan everything.
>
> Issue classes:
>
> 1. **Stale**: any semantic-memory row whose `lastAccessedAt` is older than 60 days AND whose `accessCount` is 1 (never re-read after creation). Surface the row id, key, and age.
>
> 2. **Broken-path**: any memory entry whose body references a workspace-relative file path (regex match `\b[A-Za-z0-9_./\\-]+\.(ts|js|py|md|json|yaml)\b`) where the file no longer exists. Resolve relative to the workspace root; honor the `pathGuard.ts` rules. Surface the row id, the missing path, and the row's full body (truncated to 200 chars).
>
> 3. **Embedding-failed**: any semantic-memory row where the `embedding` column is NULL despite the embedder being configured (`gemma-code.embeddingModel` not empty). Surface the row id and key.
>
> 4. **Duplicate**: any pair of semantic-memory rows whose `key` is identical or whose body has Jaccard similarity > 0.9 (compute on word-level shingles; cap pairwise comparison at the recent-1000 set). Surface the older row id, the newer row id, and the similarity.
>
> Output: write a Markdown file to `<workspace>/.gemma-code/memory-health.md` (overwriting any prior report). Format: front-matter with `generatedAt`, then four sections (one per issue class) with tables. End with a summary line: `<N> issues across <M> entries (<percentage>% healthy)`.
>
> Wire the slash command in `src/commands/CommandRouter.ts`:
>
> - `/memory lint` runs `MemoryHealthCheck.run()` with default scope.
> - `/memory lint --full` runs with `full: true`.
> - `/memory lint --limit=N` runs with the requested limit.
> - On completion, post a one-line message to the chat: `Memory health report written to .gemma-code/memory-health.md (<N> issues found).`
>
> Constraints:
> - Offline-first: pure local SQLite + filesystem; no network calls.
> - Report-only: never modifies memory entries. Destructive cleanup (eviction, re-embed) is the responsibility of separate commands (`/cache reembed` from the parallel token-optimizer-adoption plan; future `/memory prune`).
> - Honor `secretPathDenyExtra`: do not include the contents of secret-path bodies in the report; substitute `<redacted: secret-path>`.
> - Total runtime budget for default scope: < 5 seconds against a 10K-row memory store.
>
> Tests:
> - `tests/unit/storage/MemoryHealthCheck.test.ts`: synthetic memory fixtures covering all four issue classes; assert each issue type is detected; assert the duplicate detector identifies a Jaccard ≥ 0.9 pair; assert no false positives on a clean fixture.
> - `tests/integration/memory-lint-end-to-end.test.ts`: invoke `/memory lint` through `CommandRouter`; verify the file is written to `.gemma-code/memory-health.md`; verify the chat message appears.
>
> Acceptance: full Vitest suite green; integration test green; `npm run lint` clean; `/memory lint` listed in `/help` output.

## Phase 2: Memory Consolidation Discipline

**Goal**: Add an N-corroboration rule to `MemoryConsolidator` so an episodic observation must appear in ≥ N independent turns before being promoted to a retrievable semantic fact. Default N=2; configurable via `gemma-code.memoryCorroborationThreshold`. Existing rows are backfilled to `corroboration_count = 1` so they aren't demoted by the new rule.

**Prerequisites**: Phase 1 (the `/memory lint` surface helps observe consolidation behavior post-rollout).

**Stability Gate**: `MemoryConsolidator` rejects promotion of a fact with `corroboration_count < threshold`; existing semantic-memory rows are backfilled correctly; new tests pass for N=1, N=2, N=3 scenarios; the missed-fact golden eval at `tests/golden/tasks/missed-fact.yaml` passes (the agent does NOT act on a single-source observation as if it were a corroborated fact); no regression on the existing 24 golden tasks.

#### 2.2 — `MemoryConsolidator` N-corroboration rule + setting

**Objective**: Modify `MemoryConsolidator` so a fact is only promoted to retrievable semantic memory once `corroboration_count >= threshold` (default 2); single-source observations remain in the table but are flagged as candidates with lower retrieval priority.

**Prompt**:
> Gemma Code v0.5.0 memory-hygiene adoption — Phase 2 step 2.
>
> Modify `src/storage/MemoryConsolidator.ts`:
>
> - Add a settings-backed threshold: `gemma-code.memoryCorroborationThreshold` (number, default 2, min 1, max 5). Document in `package.json` `contributes.configuration` with a clear `description` explaining the trade-off.
> - When consolidating a new observation:
>   - If a matching memory row exists (matched by key OR Jaccard similarity > 0.9 on body), increment its `corroboration_count` by 1.
>   - If no matching row exists, insert a new row with `corroboration_count = 1`.
> - When `UnifiedMemoryRetriever` queries semantic memory, it must:
>   - Treat rows with `corroboration_count >= threshold` as **facts** (full retrieval priority).
>   - Treat rows with `corroboration_count < threshold` as **candidates** (lower retrieval priority — return only when no fact-tier rows match the query).
>   - Surface the tier in the retrieved entry: `provenance.corroborationTier: 'fact' | 'candidate'`.
> - Emit metrics on `MetricsCollector`:
>   - `consolidator.observation_added` — every consolidation call
>   - `consolidator.candidate_promoted` — when an entry crosses the threshold
>   - `consolidator.candidate_returned` — when a candidate is included in retrieval (no fact-tier match)
>
> Update `MemoryStore`'s SELECT statements to ORDER BY `corroboration_count DESC` (after the existing similarity / recency ordering) so fact-tier rows surface first.
>
> Tests at `tests/unit/storage/MemoryConsolidator.corroboration.test.ts`:
> - N=1 (threshold=1): every observation is immediately a fact (legacy behavior preserved when threshold=1).
> - N=2 (default): single observation is candidate; second matching observation promotes to fact; metric `candidate_promoted` fires.
> - N=3: requires three matching observations.
> - Existing single-source rows backfilled to `corroboration_count=1` are candidates under default threshold; manually inserting a duplicate observation promotes them.
> - Retrieval ordering: under threshold=2, a fact-tier row is returned before a candidate-tier row for the same query.
>
> Constraints:
> - Settings change must take effect at the next consolidation call (no restart required).
> - The setting must be observable from the panel webview (existing settings surface) — no new UI work needed; just the JSON registration.
>
> Acceptance: full Vitest suite green; consolidator tests pass for N=1, N=2, N=3; retrieval-ordering test passes; `npm run lint` clean.

> Tests:
