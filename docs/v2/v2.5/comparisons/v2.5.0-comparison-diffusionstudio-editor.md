**Current project**: Nexus-AI (`nexus-coding` v2.4.1, VS Code extension + Tauri desktop + sidecar)
**Authored during**: v2.4.6 field-delivery cycle
**Adoption target**: v2.5.0
**Date**: 2026-09-05

## Step 3 - Classified differences

### External-only (`+`) - adoption candidates

**G-1. The CLI exposes only actuation, never observation.**
Nexus-AI's JSON control surface at `desktop/sidecar/src/controlSurface/jsonCliRoutes.ts` exposes exactly six routes: `session/new`, `session/send`, `session/list`, `models`, `generate/queue`, `generate/status`. Every one of them tells the app to *do* something. None lets an agent *read* what the app currently is. `dapi` splits its surface roughly evenly: `context`/`ctx` returns the current document state as structured JSON, `screenshot` and `capture` return pixels, `logs` returns recent app logs, `whoami` returns identity and auth state, and `report` returns a diagnostic bundle that deliberately still works when the app is down.

The consequence for Nexus-AI is concrete. An agent can call `nexus generate queue` and `nexus generate status`, but after a job completes it has no CLI path to inspect the artifact it just produced, read the app's current session or workspace state, or pull recent logs when something fails. It must ask the human.

**G-2. No skill teaches an external agent how to drive Nexus.**
Skill flow in Nexus-AI is strictly inbound: `nexus skills sync` fetches a catalog from Nexus-Hub and `modules/coding/skills/catalog` holds authoring skills (`commit`, `review-pr`, `generate-tests`, ...). Diffusion Studio ships the inverse: an `/editor` skill distributed *with the app* whose job is to teach Claude Code or Codex the `dapi` command vocabulary, so a coding agent that has never seen the product can drive it correctly on first contact. Nexus-AI has a genuinely useful CLI and no artifact that teaches an outside agent to use it.

**G-3. No per-command agent-readable CLI contract.**
The `reference/` tree is one markdown file per command group (`capture.md`, `check.md`, `context.md`, `export.md`, `fetch.md`, `fonts.md`, `logs.md`, `models.md`, `open.md`, `report.md`, `screenshot.md`, `voices.md`, `whoami.md`, plus `jsx/` and `media/`), written for an agent to load selectively. Nexus-AI's CLI contract lives in a single `HELP` string inside `bin/nexus.mjs` plus prose scattered across per-version plans. There is no place an agent can read to learn one command precisely.

**G-4. Output convention is JSON-first rather than JSON-on-request.**
`dapi` states its contract flatly: JSON on stdout, JSON Lines for collections so output streams, human-readable errors on stderr, exit 0 for success and 1 for any error. Nexus-AI defaults to human-formatted stdout and gates structure behind `--json` or `--format json`, and only on some subcommands (`skills audit`, `doctor`, `skills optimize`, `skills frontier` have it; `skills list`, `golden run`, `trace export` print prose only). An agent parsing `nexus skills list` today is scraping tab-separated text.

**G-5. Stable addressable IDs on every element.**
Diffusion Studio's compositions are JSX where "every element carries an ID for precise targeting during edits", which is what makes bidirectional canvas/code sync tractable: an agent names the exact node it wants to change instead of re-emitting the document. This is the source project's core architectural bet and the least directly portable item here, since Nexus-AI's studio is not a document editor. It is recorded for the addressability principle, not for adoption as-is.

### Current-only (`=`) - strengths to preserve

Nexus-AI is ahead on CI/CD depth, test strategy, security posture (`nexus.security.toml`, injection scanning on skill sync, `commandBlocklist.ts`, `ConfirmationGate.ts`, `BudgetMiddleware.ts`), and release documentation discipline (per-version plans, known-gaps, ADRs). None of this should be traded away for anything below. The local-first, zero-outbound posture in particular is a stronger stance than the source project takes and must survive every item in this plan.

### Both, different approach (`~`)

- **Diagnostics**: `dapi report` vs. `nexus doctor`. Functionally equivalent. `dapi report` explicitly tolerates the app being absent, which `nexus doctor` also does since it runs locally. No action.
- **Validation**: `dapi check` validates a document before export; `nexus check` runs deterministic source-code checks. Same name, different domain. No action, but the collision is worth noting if a document-check command is ever added.

### 5.1 Threat model comparison

| Axis | Diffusion Studio Editor | Nexus-AI (today) | Nexus-AI (after this plan) |
|---|---|---|---|
| New runtime dependencies | Electron, SolidJS, WebGPU, ffmpeg-class encoders | Tauri, Ollama, Python runtimes | **None added.** Every item reuses existing in-repo runtimes. |
| Outbound-call destinations | `dapi fetch` downloads assets; generative `models`/`voices` imply hosted inference | Ollama on loopback; Nexus-Hub for skill sync (signed, manifest-verified) | **Unchanged.** No new destination. |
| Credentials / API keys | Vendor account implied for generation and voices | Local sidecar token only (`--token`, `--host 127.0.0.1`, `--port 11500`) | **Unchanged.** Same loopback token. |
| Source code or prompts leaving the machine | Plausible for hosted generation paths | No | **No.** All adopted items are local-only. |
| New commercial third-party relationship | Yes, Diffusion Studio Inc. | No | **No.** |

The decisive finding: nothing recommended below requires adopting the source project's code, dependencies, or service. What is being adopted is a **CLI design contract** and a **documentation pattern**, both of which are ideas rather than integrations. The MPL-2.0 copyleft on the source therefore never attaches, because no source file is copied.

## Step 6 - Adoption sequence

**Phase A - Contract (skill-native, no new surface)**

1. **G-4 JSON-first output convention.** Define the contract once: JSON on stdout, JSON Lines for collections, human-readable errors on stderr, exit 0 success / 1 runtime error / 2 invalid invocation (the last already documented in `bin/nexus.mjs`). Add `--json` to the subcommands that lack it (`skills list`, `golden run`, `trace export`) before changing any default. Enables G-2 and G-3 by giving them a stable contract to describe.
2. **G-2 Self-driving skill.** Author a `nexus` skill teaching an external coding agent the command vocabulary, the loopback token and `--host`/`--port` flags, the exit-code contract from step 1, and the confirmation-gate boundary. Ship it in `modules/coding/skills/catalog`. Depends on step 1.

**Phase B - Documentation (re-full)**

3. **G-3 CLI reference tree.** One file per command group under `docs/reference/cli/`, agent-loadable, original content. Extract the `HELP` string in `bin/nexus.mjs` as the index. Depends on step 1 for the shared output/error contract; feeds step 4 by fixing the format new commands document themselves in.

**Phase C - Surface (re-full, gated)**

4. **G-1 Observation commands.** Add read routes to `jsonCliRoutes.ts` alongside the existing six, in ascending order of disclosure risk: `nexus context` (current session, workspace roots, active model) first, then `nexus logs` (recent sidecar logs, redacted), then media inspection over the existing OCR/audio/video runtimes. Each route reuses the existing loopback token and `WorkspaceScope` authorization. Depends on all of Phase A and B so every new command ships with its contract and its reference page.

Steps 1 and 3 can proceed in parallel with step 2 once the contract in step 1 is fixed. Step 4 must not start before Phase A lands, because shipping observation commands without the output contract or the skill reproduces exactly the discoverability gap this report identifies.

When chaining into `/plan from-comparison`, pass `reverse-engineer-first=true`.

## Step 7 - Risks and conflicts

| Item | Conflict / risk | Mitigation |
|---|---|---|
| G-4 | **Breaking change.** Flipping default stdout from prose to JSON will break any test, script, or doc that parses current output. `bin/nexus.mjs` has many prose `stdout.write` call sites. | Additive first: add `--json` everywhere it is missing and leave defaults alone in v2.5.0. Only consider flipping the default in a later major, and never mid-freeze. |
| G-1 | **Information disclosure.** New read routes expose workspace paths, prompt text, session titles, model identifiers, and potentially screen contents on the loopback control plane. | Inherit the existing loopback token and `WorkspaceScope` union-of-roots authorization without exception. Apply egress-redaction discipline to `logs` output. Treat `screenshot`/`capture` as a separate, later decision rather than folding it into the first tranche. |
| G-1 | **Surface growth on a frozen line.** Adds routes to `jsonCliRoutes.ts`, an actively maintained file in the field-reliability line. | This is precisely why the target is v2.5.0 and not v2.4.7. Do not land this while 2.4 is frozen. |
| G-2 | **Skill catalog is sync-managed.** `nexus skills sync` pulls from Nexus-Hub and verifies against `MANIFEST.sha256`; a hand-added local skill could be clobbered or fail verification. | Confirm whether the self-driving skill belongs in the synced catalog or in a repo-local skill root before authoring. This is an open question for the plan, not a blocker. |
| G-3 | **Documentation drift.** A per-command reference tree goes stale when commands change, and the existing single `HELP` string does not. | Keep `HELP` as the generated index or add a consistency check to the existing repository-check baseline. |
| All | **Scope creep into a rewrite.** The source project's agent-first design is attractive enough to invite over-adoption. | The recommended scope is a contract, a skill, docs, and read routes over engines that already exist. Nothing here is an architectural change. |

## NOT recommended

**G-5. Bidirectional canvas/code sync with stable per-element IDs.** `drop-outright`. This is Diffusion Studio's core architectural bet and it is inseparable from its domain: a video composition is a document tree that benefits enormously from every node being individually addressable and round-trippable between a canvas and JSX. Nexus-AI's studio is a generation and coding surface, not a document editor, so there is no equivalent document tree to address. Adopting the pattern would require inventing the document model first, which is a rewrite justified by nothing in this comparison. The transferable residue is the general principle that agent-facing state should be addressable rather than opaque, and that principle is already served by G-1's `context` command returning structured state.

**The source project's dependency stack.** Electron, SolidJS, the universal renderer, WebGPU, and the encoder packages are all `drop-outright`. Nexus-AI is a Tauri application with a settled stack and no video-composition requirement. Per the MCP Registry Policy's reverse-engineer-first tree, none of these clear even the first question, since no capability gap in this report requires them.

**Hosted generation and voice services.** The source project's `models`, `voices`, and `fetch` commands imply hosted inference. Nexus-AI is deliberately local-first with Ollama on loopback. Adopting any hosted-generation path would be `generation-as-service`, an explicit hard-no in the MCP Registry Policy, and would break the project's zero-outbound posture. Nexus-AI's own local `nexus models list` and `nexus generate queue` already cover this ground correctly.
