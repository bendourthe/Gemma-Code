**Seeded from**: [docs/v2/v2.5/comparisons/v2.5.0-comparison-diffusionstudio-editor.md](../comparisons/v2.5.0-comparison-diffusionstudio-editor.md)
**Goal**: An external coding agent that has never seen Nexus can install it, read one reference tree, load one shipped skill, and then both drive the app and observe its state through `nexus`, with every command emitting machine-readable JSON on stdout, human-readable errors on stderr, and a documented exit code.

## Overview

Nexus-AI already has a real agent control surface. `desktop/sidecar/src/controlSurface/jsonCliRoutes.ts` exposes six routes and `bin/nexus.mjs` fronts them alongside skills, memory, doctor, trace, golden, check, image, and video subcommands. The comparison against Diffusion Studio's `dapi` found that this surface is half-built in one specific way: every route actuates and none observes. An agent can start a session, send a turn, queue a generation, and poll its status, but it cannot read what the app currently is, pull recent logs when a job fails, or inspect the artifact it just produced. It has to ask the human.

Three smaller gaps compound that one. Output is prose-by-default with `--json` available on only some subcommands, so an agent parsing `nexus skills list` is scraping tab-separated text. The entire CLI contract lives in a single `HELP` string, so there is nowhere an agent can read to learn one command precisely. And skill flow is strictly inbound (`nexus skills sync` pulls from Nexus-Hub) with no artifact that teaches an outside agent to drive Nexus itself.

This plan closes all four in dependency order: fix the output contract first because everything else describes it, then write the reference tree, then ship the skill that points at the reference, then add the observation routes last so each one arrives with its contract and its documentation already in place. Nothing here adds a dependency, an outbound call, or a credential. The comparison's Step 5 assessment placed every adopted item in MCP Registry Policy bucket 1 or 2 (local-only, or LLM-native skill), and no source file from the external MPL-2.0 project is copied, so its copyleft never attaches.

Scope discipline matters here because the source project is seductive. Its bidirectional canvas/code sync and its Electron/SolidJS/WebGPU stack are explicitly out of scope and were dropped outright in the comparison. What is being adopted is a CLI design contract and a documentation pattern, both ideas rather than integrations.

No phase except the last pushes, opens a pull request, or starts remote CI. Each earlier phase ends with automated tests, session history, and one local commit. Package metadata stays at its current value until `/update release`.

## Why this is v2.5.0 and not v2.4.7

Every plan on disk from `v2.4.0` through `v2.4.6` is field-reliability patch work, and the 2.4 line is under a release freeze pending field testing on the operator host. This plan adds a new agent-facing read surface to `jsonCliRoutes.ts`, which is feature work of a different shape. Landing it as a 2.4 patch would mix new surface into a frozen corrective line and would put an information-disclosure route into a release nobody has finished validating. The adoption target was resolved to v2.5.0 in the comparison's Step 6.5 and confirmed with the operator.

Every open v2.4.x known-gap row (`MT-1` through `MT-7`, `WN-1`, `WN-2`) carries forward as still-open. This plan does not close them and does not reopen the field-delivery work. It starts only after the 2.4 line ships.

## Goals First

**Target problem**: Nexus has a capable local agent CLI that an outside agent cannot discover, cannot parse reliably, and cannot use to see anything. The product's own agent story stops at "send a request" and has no "read the result".

**Target persona**: A coding agent (Claude Code, Codex, or any CLI-driven assistant) running on the operator's machine on behalf of a privacy-focused Windows user, driving a locally installed Nexus desktop with no cloud dependency. Secondary persona: the operator themselves, scripting Nexus from PowerShell or bash.

**Observable definition of done**:

- Every `nexus` subcommand accepts `--json` and, with it, writes exactly one JSON value (or JSON Lines for a collection) to stdout and nothing else.
- Errors are human-readable on stderr. Exit is `0` success, `1` runtime error, `2` invalid invocation, documented in one place and true of every subcommand.
- `docs/reference/cli/` contains one page per command group, each stating the command's arguments, its JSON output shape, its error cases, and its exit codes. The `HELP` string in `bin/nexus.mjs` links to it and a repository check fails when a subcommand exists with no page.
- A skill ships in the repo that teaches an external coding agent the `nexus` vocabulary, the loopback token and `--host` / `--port` flags, the exit-code contract, and the confirmation-gate boundary. A fresh agent given only that skill can complete a scripted round trip without reading source.
- `nexus context --json` returns the running app's current state: active session id and title, workspace roots and primary root, selected model, and whether a generation job is in flight. It fails cleanly with exit `1` and a stderr message when the sidecar is not running.
- `nexus logs --json` returns recent sidecar log records as JSON Lines, redacted, bounded by `--lines`.
- `nexus media inspect <path> --json` returns duration, dimensions, and stream facts for an artifact Nexus produced, over the existing in-sidecar runtimes.
- Every new route requires the existing loopback token and is authorized against `WorkspaceScope` union-of-roots. A path outside the authorized roots is refused, not read.
- No new runtime dependency, no new outbound destination, and no new credential appear in `package.json`, the sidecar, or the installer.

**Explicitly out of scope**: `screenshot` / `capture` (a separate disclosure decision, deferred by design), bidirectional canvas/code sync, per-element addressable IDs, any hosted generation or voice service, and flipping the default stdout format from prose to JSON.

## Architecture Decisions

1. **The output contract is additive in v2.5.0.** `--json` is added everywhere it is missing and the prose defaults stay exactly as they are. Flipping the default would break tests, scripts, and documentation that parse current output, and there is no version of that change that is safe to make in the same release that introduces the flag. A default flip is a later-major decision and is recorded as a deliberate non-goal, not an oversight.

2. **JSON Lines for collections, one JSON value for singletons.** A collection command streams one object per line so an agent can consume it incrementally and so a large result does not have to be buffered. A single-record command emits one value. This mirrors the contract the comparison found in `dapi` and is the only shape decision that has to be made once and obeyed everywhere.

3. **Exit codes are already right and only need documenting.** `bin/nexus.mjs` already documents `0` success, `1` validation or sidecar/auth error, `2` invalid invocation or JSON schema error. The work is auditing that every subcommand actually obeys it, not inventing a new scheme.

4. **The reference tree is generated-adjacent, not generated.** One hand-written page per command group under `docs/reference/cli/`, with `HELP` remaining the authoritative index. A fully generated reference would drift less but would not carry the JSON output shapes and error cases an agent actually needs. Drift is contained by a repository check that fails when a subcommand has no page, not by generating prose.

5. **Observation routes are read-only and reuse the existing authorization.** Each new route mounts alongside the existing six in `jsonCliRoutes.ts`, requires the same loopback token, and authorizes paths against `WorkspaceScope` union-of-roots. No new auth mechanism is introduced, because introducing one would be a larger security change than the feature justifies.

6. **`context` before `logs` before `media inspect`.** Ordered by ascending disclosure. `context` returns state the agent already partly knows. `logs` can carry prompt fragments and paths and therefore needs redaction. `media inspect` reads files and therefore needs path authorization. Building them in that order means each new risk arrives on top of a surface already proven.

7. **`screenshot` and `capture` are deferred, not forgotten.** The source project exposes both. They expose whatever is on screen, which is a materially different disclosure class from structured state, and they deserve their own decision rather than being folded into this tranche. Recorded as a deferral, not dropped.

8. **The self-driving skill is authored after the reference tree.** The comparison's Step 6 put the skill in Phase A and the reference in Phase B. This plan swaps them so the skill can link to the reference pages rather than restate them, which keeps one source of truth for command detail and makes the skill a routing document. The dependency the comparison actually asserted (both depend on the output contract) is preserved.

## Phase 1: CLI Output Contract

**Goal**: Every `nexus` subcommand accepts `--json`, emits exactly one JSON value or JSON Lines stream on stdout under that flag, writes human-readable errors to stderr, and obeys the documented exit codes.
**Prerequisites**: None.
**Stability Gate**: A contract test enumerates every subcommand registered in `bin/nexus.mjs` and asserts each one accepts `--json`, writes parseable JSON to stdout, writes nothing non-JSON to stdout under that flag, and exits with a documented code. Adding a subcommand without `--json` fails that test.
**Verification Expectation**: Run `node bin/nexus.mjs skills list --json | node -e "JSON.parse(require('fs').readFileSync(0,'utf8'))"` and observe exit 0 with no parse error, then run `node bin/nexus.mjs skills list --json 2>/dev/null` against a machine with no synced catalog and observe a valid JSON value rather than the current prose fallback string. Exercise via [[functional-verification]].
**Recommended model tier**: strong
**Recommended effort level**: medium
**Rationale**: Mechanically wide (many call sites across a large CLI file) with a contract decision that binds every later phase, but low architectural risk because it is purely additive.

### Sub-tasks

#### 1.1 -- Write the output contract document

**Objective**: Fix the stdout, stderr, and exit-code contract in one authoritative place before any code changes.

**Build class**: load-bearing. Every later phase describes or obeys this document.

**Prompt**:
> Create `docs/reference/cli/contract.md` in the Nexus-AI repository. It must state, as normative rules: (1) under `--json`, stdout carries exactly one JSON value for a single-record command, or JSON Lines (one complete JSON object per line, newline-terminated) for a collection command, and nothing else -- no banners, no progress, no trailing prose; (2) without `--json`, stdout carries the existing human-readable output unchanged; (3) all diagnostics, warnings, and errors go to stderr in every mode; (4) exit codes are `0` success, `1` runtime error including sidecar-unreachable and auth failure, `2` invalid invocation including argument and JSON-schema errors -- these already appear in the `HELP` string in `bin/nexus.mjs`, so reuse that wording rather than inventing a new scheme; (5) a command that returns nothing under `--json` emits `null` or an empty JSON Lines stream, never an empty stdout with exit 0 and no explanation. Include a short worked example of each output shape. Do not change any code in this sub-task.

---

#### 1.2 -- Audit every subcommand against the contract

**Objective**: Produce a per-subcommand table of current behavior so the implementation work is enumerated rather than guessed.

**Prompt**:
> Read `bin/nexus.mjs` end to end and enumerate every subcommand reachable from the `HELP` string, including the pass-throughs to `bin/nexus-check.mjs`, `bin/nexus-image.mjs`, and `bin/nexus-video.mjs`. For each, record in a working table: does it accept `--json` or `--format json` today; what does it write to stdout in each mode; does it write any diagnostics to stdout rather than stderr; and which exit codes it can actually produce. Known starting points from the seeding comparison: `skills audit`, `doctor`, `skills optimize`, and `skills frontier` already have `--json`; `skills list`, `golden run`, and `trace export` print prose only. Do not assume that list is complete -- derive it from the file. Write the table into `docs/v2/v2.5/development/cli-contract-audit.md`. This sub-task changes no behavior.

---

#### 1.3 -- Add `--json` to every subcommand that lacks it

**Objective**: Close the gaps the audit found, additively, with prose defaults untouched.

**Failure modes**: On malformed input (an unparseable `--json` body or an unknown flag) the command writes a human-readable message to stderr and exits `2` without emitting partial JSON to stdout. When a dependency is unreachable or slow (the sidecar is down, or a loopback request exceeds its timeout) the command writes the reason to stderr and exits `1`; it never emits a partial JSON Lines stream and then fails silently, so a consumer that reads a complete line can trust it. When two operations conflict (a `--json` flag combined with an existing `--format table`) the explicit `--format` wins and the command warns on stderr, because silently ignoring one of two contradictory flags is the failure mode that produces an unreproducible bug report.

**Build class**: load-bearing.

**Prompt**:
> For every subcommand the Phase 1.2 audit marked as missing `--json`, add the flag to `bin/nexus.mjs` following `docs/reference/cli/contract.md`. Constraints: (1) do NOT change any existing default output -- a command invoked without `--json` must produce byte-identical stdout to what it produces today, because tests and scripts parse it; (2) move any diagnostic currently written to stdout onto stderr, in both modes; (3) collection commands (`skills list`, `session list`, `models list`, `memory audit`) emit JSON Lines, single-record commands emit one value; (4) where a JSON shape already exists for a command that has `--json` today, do not redesign it -- match it. Reuse the existing helpers in `core/cli/jsonCli.ts` rather than adding a parallel serialization path. Add or update unit tests under `tests/unit/` asserting both modes for each command touched.

---

#### 1.4 -- Contract test over the whole CLI surface

**Objective**: Make the contract enforceable so a future subcommand cannot silently omit `--json`.

**Failure modes**: On malformed input (a subcommand that cannot be introspected) the test fails with the subcommand name rather than skipping it, because a skipped case is indistinguishable from a passing one. When a dependency is unreachable (a pass-through CLI or the sidecar is absent) the test asserts the documented exit `1` and a non-empty stderr rather than being skipped. When two operations conflict (a subcommand appears in `HELP` but has no handler, or vice versa) the test fails and names both sides of the mismatch.

**Build class**: load-bearing.

**Prompt**:
> Add a contract test (Vitest, under `tests/unit/cli/`) that enumerates every subcommand from the `HELP` string in `bin/nexus.mjs` and, for each one, asserts: `--json` is accepted; stdout under `--json` parses as a single JSON value or as JSON Lines where every line parses; nothing non-JSON reaches stdout under `--json`; diagnostics reach stderr; and the exit code is one of `0`, `1`, `2`. Drive commands that need the sidecar against a stub rather than a live daemon. The test must FAIL when a subcommand is added to `HELP` without `--json`, so assert over the enumerated list rather than a hardcoded array of names. Verify the failure mode by temporarily adding a non-conforming subcommand, confirming the test goes red, and reverting.

## Phase 2: Agent-Facing CLI Reference Tree

**Goal**: `docs/reference/cli/` holds one page per command group, each stating arguments, JSON output shape, error cases, and exit codes, with the `HELP` string as index and a drift check that fails on an undocumented subcommand.
**Prerequisites**: Phase 1.
**Stability Gate**: A repository check enumerates subcommands from `HELP` and fails when any one has no reference page, or when a page documents a subcommand that no longer exists.
**Verification Expectation**: Open `docs/reference/cli/session.md` and run the exact command shown in its example against a running sidecar; observe stdout matching the documented JSON shape field for field. Exercise via [[functional-verification]].
**Recommended model tier**: standard
**Recommended effort level**: medium
**Rationale**: Documentation authoring against an already-fixed contract, with one small mechanical check; breadth is moderate and architectural risk is low.

### Sub-tasks

#### 2.1 -- Author the reference pages

**Objective**: One agent-loadable page per command group, written so an agent can learn a single command without reading the rest.

**Build class**: load-bearing.

**Prompt**:
> Create `docs/reference/cli/` with one markdown page per command group in `bin/nexus.mjs`: `skills.md`, `memory.md`, `doctor.md`, `trace.md`, `golden.md`, `session.md`, `models.md`, `generate.md`, `check.md`, `image.md`, `video.md`. Add `docs/reference/cli/README.md` as the index. Each page states, in this order: what the command group is for in one sentence; every subcommand with its exact flags and their types; the JSON output shape under `--json` as an annotated example (real field names, realistic values); every error case with the stderr message and the exit code it produces; and whether the command requires a running sidecar. Write original content describing Nexus's own commands -- do not copy text, structure prose, or field names from any external project. Cross-link `contract.md` for the shared output rules rather than restating them on every page. Each page must be independently useful when loaded alone, because that is how an agent will read it.

---

#### 2.2 -- Link the reference from `HELP` and add the drift check

**Objective**: Keep the index authoritative and make undocumented commands fail loudly.

**Failure modes**: On malformed input (a `HELP` string that cannot be parsed into subcommands) the check exits non-zero naming the parse failure rather than reporting a clean scan, so a broken parser cannot masquerade as full coverage. When a dependency is unreachable (the `docs/reference/cli/` directory is missing entirely) the check fails with that path named rather than treating zero pages as zero gaps. When two operations conflict (a page exists for a subcommand that `HELP` no longer lists) the check fails in both directions and names the orphaned page, because one-directional coverage checks let deleted commands keep stale documentation forever.

**Build class**: load-bearing.

**Prompt**:
> Add a pointer to `docs/reference/cli/README.md` at the end of the `HELP` string in `bin/nexus.mjs`. Then add a drift check to the existing repository-check baseline (the same gate that runs deterministic source checks -- see `bin/nexus-check.mjs`) that parses the subcommand list out of `HELP`, globs `docs/reference/cli/*.md`, and fails when a subcommand has no page or a page documents a subcommand absent from `HELP`. The check must report both directions with the specific names, not a count. Wire it so it runs in the same place the existing repository-check baseline runs.

## Phase 3: Self-Driving `nexus` Skill

**Goal**: A skill ships in the repository that teaches an external coding agent to drive Nexus through the CLI, so an agent given only that skill can complete a scripted round trip without reading source.
**Prerequisites**: Phases 1 and 2.
**Stability Gate**: The skill exists at its decided location, passes whatever validation the repository already applies to skills, and a documented round trip (start a session, send a turn, read the response, queue a generation, poll its status) is reproducible from the skill text alone.
**Verification Expectation**: Hand the skill file and nothing else to a fresh agent session and have it perform the documented round trip against a running sidecar; observe that it completes without opening `bin/nexus.mjs` or any sidecar source. Exercise via [[functional-verification]].
**Recommended model tier**: strong
**Recommended effort level**: medium
**Rationale**: Small surface but the content quality determines whether the phase's goal is met at all, and it opens with a placement decision that has a real wrong answer.

### Sub-tasks

#### 3.1 -- decision: does the self-driving skill live in the synced catalog or a repo-local skill root?

**Objective**: Settle where the skill lives before authoring it, because the two locations have different lifecycles and one of them can silently delete the file.

**Prompt**:
> This is a decision ticket. Do not author the skill until it is resolved, and do not start sub-tasks 3.2 or 3.3 before then.
>
> The question: `nexus skills sync` fetches a catalog from Nexus-Hub and verifies files against `MANIFEST.sha256`. A skill authored by hand into that synced tree may be overwritten on the next sync or may fail manifest verification. The repository also carries `modules/coding/skills/catalog/` and `.agents/skills/`, which have different lifecycles.
>
> Options to evaluate: (A) author it upstream in Nexus-Hub so it arrives through the normal sync path -- correct lifecycle, but the skill then ships on Hub's cadence rather than with the Nexus release that introduces the commands it documents; (B) place it in a repo-local skill root that `sync` does not manage -- ships with the release, but needs a confirmed non-managed location; (C) ship it in both with one designated canonical -- highest drift risk, likely wrong.
>
> Evidence that settles it: read `core/skills/NexusHubSyncer.ts` and determine exactly which directories `sync --apply` writes to and which it deletes from; read the manifest verification path to determine what happens to an unlisted file in a managed directory; and check whether `modules/coding/skills/catalog/` is inside or outside that managed set. Record the answer and the reasoning in `docs/v2/v2.5/development/skill-placement-decision.md`. This unblocks 3.2 and 3.3.

---

#### 3.2 -- Author the skill

**Objective**: Write the skill that makes Nexus drivable by an agent that has never seen it.

**Build class**: load-bearing.

**Prompt**:
> Author the self-driving skill at the location decided in 3.1. It must teach: the `nexus` command vocabulary at the group level, routing to `docs/reference/cli/` pages for per-command detail rather than restating them; how to reach the sidecar (`--host 127.0.0.1`, `--port 11500`, `--token`) and where the token comes from; the output contract from `docs/reference/cli/contract.md` (JSON on stdout under `--json`, JSON Lines for collections, errors on stderr, exit `0`/`1`/`2`); how to tell "the sidecar is not running" from "the request was rejected" from "the request was malformed" using exit codes and stderr; the confirmation-gate boundary -- which operations require user approval and must not be scripted around, per `src/tools/ConfirmationGate.ts` and `src/tools/commandBlocklist.ts`; and one complete worked round trip (start a session, send a turn, read the response, queue a generation, poll its status) with real commands and real expected output. State plainly that Nexus is local-first: no command in this skill sends anything off the machine. Keep it a routing document, not a duplicate reference.

## Phase 4: Observation Routes on the JSON Control Surface

**Goal**: `nexus context`, `nexus logs`, and `nexus media inspect` let an agent read the running app's state, its recent logs, and the artifacts it produced, over routes that reuse the existing loopback token and `WorkspaceScope` authorization.
**Prerequisites**: Phases 1, 2, and 3.
**Stability Gate**: All three commands return contract-conforming JSON against a running sidecar; each returns exit `1` with a stderr reason when the sidecar is absent; and `media inspect` refuses a path outside the authorized workspace roots rather than reading it.
**Verification Expectation**: Against a running sidecar with an active session, run `nexus context --json` and observe the returned session id and workspace roots matching what the desktop UI displays; then run `nexus media inspect` on a path outside every authorized root and observe a refusal on stderr with exit `1` and no file content in stdout. Exercise via [[functional-verification]].
**Recommended model tier**: frontier
**Recommended effort level**: high
**Rationale**: New authorization-bearing read surface with real information-disclosure blast radius, spanning the sidecar control plane, redaction, and path authorization.

### Sub-tasks

#### 4.1 -- `nexus context`: current app state

**Objective**: Give an agent one command that answers "what is the app right now".

**Failure modes**: On malformed input (unknown flags, or a `--session` id that does not exist) the command writes the reason to stderr and exits `2` for a bad flag or `1` for an unknown session, and emits no partial state object. When the dependency is unreachable or slow (the sidecar is down, or the loopback request exceeds its timeout) the command writes "sidecar not reachable at host:port" to stderr and exits `1`; it does not fall back to reading state off disk, because a stale answer presented as live state is worse than no answer. When two operations conflict (a session is being created or torn down while `context` reads) the route returns a consistent snapshot taken at one instant rather than fields read at different times, so an agent never sees a session id from before a switch alongside a workspace root from after it.

**Build class**: load-bearing.

**Prompt**:
> Add a `GET {prefix}/context` route to `desktop/sidecar/src/controlSurface/jsonCliRoutes.ts` alongside the existing six, and a `nexus context` subcommand in `bin/nexus.mjs` that calls it. The response is a single JSON object: active session id and title, workspace roots and primary root (from `WorkspaceScope` / `WorkspaceScopeStore`), the selected model id, and whether a generation job is currently in flight (from `StudioRuntime`). Reuse the existing loopback token check and the existing `ControlSurfaceRoute` shape -- do not introduce a new auth path. Take the snapshot at one instant so fields cannot disagree with each other. Follow `docs/reference/cli/contract.md` exactly and add the `context` entry to the reference tree and to the `HELP` string in the same change, so the Phase 2 drift check stays green. Add unit tests for the route (authorized, unauthorized, sidecar-absent) and for the subcommand's output shape.

---

#### 4.2 -- `nexus logs`: recent sidecar logs, redacted

**Objective**: Let an agent diagnose a failed job without asking the human to read a log file.

**Failure modes**: On malformed input (a non-numeric or negative `--lines`) the command writes the reason to stderr and exits `2`. When the dependency is unreachable or the log source is unavailable, the command exits `1` with a stderr reason and emits no lines; a truncated JSON Lines stream must never be presented as a complete one, so on mid-stream failure it writes the error to stderr and exits `1` rather than ending the stream cleanly. When two operations conflict (the log is being written while it is read) the route serves a bounded snapshot rather than tailing indefinitely, so the command always terminates.

**Build class**: load-bearing.

**Prompt**:
> Add a `GET {prefix}/logs` route and a `nexus logs [--lines N] [--json]` subcommand. Output is JSON Lines, one log record per line, newest last, bounded by `--lines` with a sane default and a hard maximum. Apply redaction before anything leaves the route: no absolute paths outside the authorized workspace roots, no token values, no full prompt text -- follow the egress-redaction discipline already used elsewhere in this repository and reuse its helper if one exists rather than writing a second redactor. Reuse the existing loopback token check. Add the `logs` entry to the reference tree and `HELP` in the same change. Add unit tests covering: bounded output, redaction of a seeded token and a seeded out-of-root path, `--lines` validation, and sidecar-absent behavior.

#### 4.3 -- `nexus media inspect`: artifact facts

**Objective**: Let an agent inspect the artifact it just generated, over runtimes that already exist in the sidecar.

**Failure modes**: On malformed input (a path that does not exist, or a file whose format the runtime cannot read) the command writes the reason to stderr and exits `1`, distinguishing "not found" from "unreadable format" in the message because an agent's next action differs between them. When the dependency is unreachable or slow (the OCR, audio, or video runtime is not provisioned, or probing exceeds its timeout) the command exits `1` naming the runtime rather than returning an empty object, so a missing runtime is never indistinguishable from a featureless file. When two operations conflict (the file is still being written by an in-flight generation) the command reports the artifact as incomplete rather than returning partial dimensions, because partial facts presented as final are the failure an agent cannot detect.

**Build class**: load-bearing.

**Prompt**:
> Add a `POST {prefix}/media/inspect` route and a `nexus media inspect <path> [--json]` subcommand. The route returns a single JSON object with the artifact's duration, dimensions, and stream facts. Implement it over the runtimes that already exist in the sidecar -- `desktop/sidecar/src/audio/sharedRuntime.ts`, `desktop/sidecar/src/video/VideoEnhancementRuntime.ts`, and `desktop/sidecar/src/ocr/sharedRuntime.ts` -- and do NOT add a new media dependency; this is wiring existing local engines to a new local route. Authorize the requested path against `WorkspaceScope` union-of-roots before touching the filesystem: a path outside every authorized root is refused with a stderr message and exit `1`, and the file is never opened. Reuse the existing loopback token check. Add the `media inspect` entry to the reference tree and `HELP` in the same change. Add unit tests covering: a valid in-root artifact, an out-of-root path refusal that asserts no read occurred, a missing file, an unreadable format, and an unprovisioned runtime.
