## Overview

This plan operationalizes the August 2026 multi-source comparison (`v2.1.0-comparison-open-local-ai-wave.md`). The comparison found three signals: the 30B-total / 3-4B-active MoE class is now the local agentic sweet spot (Muse Glimmer, Nemotron Lightning); routing is the new differentiator and is pure control logic over telemetry Nexus already collects (NeMo Switchyard); and the "local AI studio" category is converging, so Nexus must defend its moats (installer, catalog, harness selector, eval loop) while closing its two real gaps: local fine-tuning and Image Studio depth.

Delivery is entirely inside the existing desktop app and installer. No new outbound destinations, credentials, or third-party processors are introduced: adopted artifacts are Apache-2.0 / OpenMDW-1.1 open weights pulled through the existing installer/HF channel, and every external design (Switchyard heuristics, InvokeAI queue/metadata/SAM2 patterns, Buzz audit-log ideas) is reverse-engineered into lean local modules per the MCP Registry Policy. The one vendor-intrinsic addition, Unsloth Core as a provisioned training runtime, follows the Ollama precedent and is gated on an Apache/AGPL component-boundary verification before anything ships.

Success looks like: a 24 GB-tier user gets Muse Glimmer as their coding default (after local eval confirms vendor claims), long agentic sessions run routine steps on Lightning and escalate to the strong model only on measured difficulty without VRAM thrash, Image Studio generations carry recallable provenance and queue as batches, chat accepts screenshots and short videos, "replace the X" edits work without manual masking, and a user can fine-tune a small model on their own repos/chats and have it appear in their Ollama-served catalog -- all offline after weight download.

## Phase 2: Adaptive Model Routing (Switchyard-derived)

**Goal**: Reverse-engineer NeMo Switchyard's tuning-free routing heuristics into a local router stage: per-turn worker-to-strong escalation from tool-activity signals, cheap-first session policy, session affinity, and hysteretic anti-thrash scheduling on a single GPU.
**Prerequisites**: Phase 1 (Lightning worker model + harness profiles; local eval results).
**Stability Gate**: A long agentic session demonstrably starts routine steps on the worker model, escalates on induced difficulty (seeded error streaks), de-escalates after recovery, and never swaps models more than the hysteresis budget allows; all routing decisions are visible in telemetry.
**Recommended model tier**: frontier
**Recommended effort level**: high
**Rationale**: Concurrency-sensitive control logic spanning the DAG, harness selector, GPU scheduler, and telemetry, where subtle threshold bugs degrade every coding session.

### Sub-tasks

#### 2.1 -- Routing signal extraction from existing telemetry

**Objective**: Derive the three Switchyard-style signal families from data Nexus already collects: tool-error streaks, repeated-identical-action (unproductive-loop) detection, and progress-free step counts / prolonged exploration.

**Failure modes**: If telemetry events are missing or malformed for a turn (e.g. a crashed tool call), the signal extractor treats the turn as neutral rather than escalating on absent data; if TelemetryBus lags behind the AgentLoop, signals are computed on the last consistent window and marked stale; if two concurrent sessions interleave events, per-session scoping keys prevent cross-contamination.

**Build class**: load-bearing.

**Prompt**:
> Create a `RoutingSignals` module (suggested: `modules/coding/orchestration/routing/RoutingSignals.ts`) that consumes `core/telemetry/TelemetryBus.ts`, `core/observability/InferenceMetrics.ts`, and `src/tools/AgentLoop.ts` traces to produce per-session, per-turn signals: consecutive tool-error count, repeated-identical-action detection (hash of tool+args over a sliding window), and steps-without-progress (no file mutation, no test-state change, no new plan node over N steps). Pure functions over event windows; no new event sources. Unit-test each signal against synthetic event streams, including malformed/missing-event cases. Acceptance: signals computed deterministically from recorded fixture streams; stale/missing data yields neutral signals.

---

#### 2.2 -- Escalation policy engine (stage router + cheap-first + hysteresis)

**Objective**: Implement the decision layer: sessions start on the worker model (cheap-first); sustained-difficulty thresholds escalate a turn (stage router) or the session (escalation router) to the strong model; hysteresis and cooldown prevent thrash.

**Failure modes**: If the strong model is unavailable (not installed, tier-excluded), escalation degrades to staying on the worker with a surfaced notice instead of erroring; if signals conflict (error streak says escalate, cooldown says hold), cooldown wins and the deferred escalation is queued for the next eligible turn; if the policy config is malformed, the engine loads compiled defaults and logs the rejection.

**Build class**: load-bearing.

**Prompt**:
> Implement `EscalationPolicy` (suggested: `modules/coding/orchestration/routing/EscalationPolicy.ts`) consuming RoutingSignals: (1) cheap-first default -- planner/critic roles pin to the strong model, worker roles start on the `role: worker-candidate` model from Phase 1; (2) per-turn escalation when thresholds trip (defaults: 3 consecutive tool errors, 2 identical-action repeats, 8 progress-free steps -- all configurable); (3) session escalation on sustained difficulty (2 per-turn escalations within a window); (4) hysteresis: minimum turns-on-model before de-escalation, plus a session-level swap budget. Session affinity: a routed step stays on its model for KV-cache reuse until policy says otherwise. Expose every decision as a telemetry event (`routing.decision` with signal snapshot and reason). Wire into the planner/critic/worker DAG's model selection alongside the harness selector. Acceptance: decision unit tests cover escalate/hold/de-escalate/conflict/unavailable-model paths; DAG integration test shows role pinning + worker escalation end to end against stubbed models.

---

#### 2.3 -- GPU scheduler integration (single-GPU swap cost)

**Objective**: Teach the GPU scheduler that escalation events have a VRAM swap cost: batch escalations hysteretically, prefetch/evict model weights around predicted swaps, and refuse swaps that would OOM concurrent diffusion work.

**Failure modes**: If VRAM telemetry is unavailable mid-decision, the scheduler assumes worst-case occupancy and defers the swap; if a swap stalls (Ollama slow to load), the session continues on the incumbent model with the swap retried in the background rather than blocking the turn; if a routing swap and a diffusion job request VRAM simultaneously, the existing coding-over-diffusion priority applies and the loser is queued, not killed.

**Prompt**:
> Extend the GPU scheduler (`core/scheduler/`) with a model-swap cost model for routing escalations: consult live VRAM telemetry before honoring an EscalationPolicy decision; batch near-simultaneous escalation requests; keep the worker resident when headroom allows, evict when it does not; defer (never drop) decisions that would OOM active work. Emit `scheduler.swap` telemetry with outcome (honored / deferred / degraded). Acceptance: simulated single-GPU scenarios (worker+strong fit; worker+strong don't fit; diffusion job concurrent) each produce the documented outcome in integration tests with a mocked telemetry source.

---

#### 2.4 -- Routing observability panel

**Objective**: Surface routing decisions in the existing trace/telemetry UI so users can see which model handled each step and why.

**Failure modes**: If routing events are absent (feature off or old session replay), the panel renders an empty state, not an error; if the event stream is large, the panel virtualizes rather than blocking the UI thread; if decision reasons reference a model since uninstalled, the label degrades to the model id string.

**Prompt**:
> Extend the trace dashboard (`desktop/src/modules/coding/panels/TraceDashboardPanel.tsx` and the v1.16.0 `ModelAnalyticsSection.tsx`) with a routing lane: per-step model attribution, escalation markers with reason tooltips (signal snapshot), and per-session swap counts. Follow existing panel test patterns (`desktop/tests/`). Acceptance: component tests cover populated, empty, and uninstalled-model states; a replayed fixture session renders the full routing story.

## Phase 3: Image Studio Provenance + Generation Queue

**Goal**: Every generation carries embedded, recallable provenance; generations run through a persistent job queue supporting fire-and-forget batches and seed/prompt sweeps.
**Prerequisites**: None (independent of Phases 1-2; scheduled here per RE-first wave order).
**Stability Gate**: A generated image re-opened days later can reproduce its prompt/seed/settings via recall actions; a 20-job batch survives an app restart and completes; queue and scheduler never deadlock under concurrent coding load.
**Recommended model tier**: strong
**Recommended effort level**: medium
**Rationale**: Well-scoped features on existing pipelines; persistence-across-restart and scheduler interplay are the only elevated-risk seams.

### Sub-tasks

#### 3.1 -- Embedded generation metadata + recall actions (A6)

**Objective**: Embed full generation parameters (prompt, negative prompt, seed, model, sampler, tier, mode) in output image/video files and expose chat recall actions: Use Prompt / Use Seed / Use All / Remix.

**Failure modes**: If an output format cannot carry metadata (or a writer fails), the parameters are persisted in the local generation index keyed by content hash so recall still works; if a user imports an external image with no metadata, recall actions are hidden rather than erroring; if metadata schema versions differ between app versions, the reader accepts all known versions and ignores unknown fields.

**Prompt**:
> Embed generation metadata in Image Studio and Video Lab outputs (PNG tEXt/iTXt chunks; sidecar or container metadata for video), mirrored into the local generation index. Add recall actions to generated-media messages in the chat-style Studio UI: Use Prompt, Use Seed, Use All, and Remix (prefills a new message with all parameters editable). Metadata never leaves the machine; it is written to local files only. Acceptance: round-trip test (generate -> read back -> byte-equal parameters), external-image graceful degradation, recall actions produce the expected prefilled state, and `redactSecrets` is applied to any free-text fields before indexing.

---

#### 3.2 -- Persistent generation job queue + batch expansion (A7)

**Objective**: A durable queue in front of the diffusion pipelines: jobs persist across restarts, batches expand (N seeds, prompt matrix), progress streams into chat, and the GPU scheduler arbitrates against coding load.

**Failure modes**: If the app crashes mid-job, on restart the job is marked interrupted and re-queued (idempotent by job id), never duplicated; if the diffusion pipeline rejects a job (model uninstalled since queuing), the job fails with a per-job error and the queue continues; if a batch and an interactive generation contend, interactive jobs get priority within the existing coding-over-diffusion global policy.

**Build class**: load-bearing.

**Prompt**:
> Implement a persistent generation queue (SQLite-backed, suggested under `core/` alongside existing local stores): job schema (id, pillar, parameters, batch-expansion spec, state machine queued/running/interrupted/done/failed), batch expansion for seed ranges and prompt matrices, restart recovery, and cancellation. Integrate with the GPU scheduler's existing priority policy; stream per-job progress into the originating chat thread. Add queue-management UI affordances in the Studio (pending count, cancel, reorder). Acceptance: restart-recovery integration test, batch-expansion unit tests, priority test under simulated coding load, cancellation mid-run leaves consistent state.

## Phase 4: Multimodal Chat + Segmentation-Assisted Editing

**Goal**: The Chat pillar accepts image and video attachments with visual-token budgeting (model-agnostic, serving any VLM in the catalog); Image Studio gains SAM2-driven maskless editing ("replace the X").
**Prerequisites**: Phase 1 (catalog capability flags identify vision-capable models); Phase 3 recommended for the editing UX (recall/queue) but not blocking.
**Stability Gate**: A screenshot pasted into chat is answered by a vision-capable local model with the visual-token budget enforced; "replace the car with a truck" produces a SAM2 mask and a correct inpaint without manual masking; non-vision models cleanly reject attachments with guidance.
**Recommended model tier**: strong
**Recommended effort level**: high
**Rationale**: New ingestion path touching memory/retrieval layers plus a new local model integration (SAM2); broad surface but established patterns.

### Sub-tasks

#### 4.1 -- Chat attachment ingestion + visual-token budgeting (A8)

**Objective**: Image/video attachment path for the Chat pillar: ingestion, per-model capability negotiation (via the Phase 1 flags plus a `vision` flag), visual-token budget selection, and memory/retrieval handling of non-text turns.

**Failure modes**: If an attachment is malformed or an unsupported format, ingestion rejects it at the boundary with a user-visible reason (never passes bytes to the model); if the active model lacks vision, the UI offers switching to an installed vision-capable model or proceeding text-only; if an attachment would blow the context/VRAM budget, the budget selector downsamples or truncates video frames and says so, rather than OOMing.

**Build class**: load-bearing.

**Prompt**:
> Add a `vision: boolean` capability flag plus per-model visual-token budget metadata to the catalog schema (extending Phase 1's flag work). Build the Chat attachment path: paste/drag/attach images and short videos, format validation, frame sampling for video, visual-token budget selection (per-model presets with an Advanced override), and handoff to vision-capable models through the existing Ollama channel. Teach the four-layer memory and hybrid retrieval to store and index non-text turns (caption/summary text as the indexable surrogate, generated locally). Verify whether the Muse Glimmer Ollama GGUF ships its vision projector; if not, gate its `vision` flag off and document in known-gaps. Acceptance: end-to-end screenshot Q&A against a stubbed vision model, rejection paths for malformed files and non-vision models, budget enforcement test, retrieval returns the multimodal turn via its surrogate text.

---

#### 4.2 -- SAM2 catalog integration (local segmentation runtime)

**Objective**: SAM2 as an installer-provisioned local capability: weights in the catalog (tier-gated by its modest VRAM), loaded on demand for segmentation.

**Failure modes**: If SAM2 weights are missing at edit time, the feature degrades to the existing manual inpaint flow with an install prompt; if segmentation exceeds a latency budget or VRAM headroom, the request is queued behind the GPU scheduler rather than freezing the Studio; if segmentation returns no confident mask for the referenced object, the user is told and offered manual selection.

**Prompt**:
> Add SAM2 (Apache 2.0) to the catalog and installer as a utility model (not a chat model): tier-gated weights download, local runtime integration in the Python diffusion sidecar, and a segmentation service API (image + point/box/text-derived hint -> mask) mediated by the GPU scheduler. Acceptance: segmentation smoke test on fixture images, missing-weights degradation path, scheduler-mediated concurrency test.

---

#### 4.3 -- "Replace the X" chat-native editing (A9)

**Objective**: Resolve a natural-language edit request to a SAM2 mask and route through the existing inpaint pipeline, inline in the Studio chat.

## Phase 5: Local Fine-Tuning Pillar (Unsloth Core)

**Goal**: A license-gated fine-tuning capability: the installer provisions Unsloth Core (Apache 2.0 components only) as a managed runtime, Nexus provides original orchestration -- dataset builder from user repos/chats through `redactSecrets`, tier-gated base-model picker, QLoRA runs, golden-task eval gate, and GGUF-to-Ollama re-import.
**Prerequisites**: Phase 1 (catalog flags, quant references); Phase 2 recommended (routing benefits from tuned workers) but not blocking.
**Stability Gate**: On a 16 GB+ machine, a user fine-tunes a small base model on a local dataset end to end offline (post-provisioning), the eval gate blocks a regressed adapter, and the exported model serves through Ollama and appears in Settings > Models.
**Recommended model tier**: frontier
**Recommended effort level**: max
**Rationale**: New pillar spanning installer, a new provisioned Python runtime, GPU-heavy long-running jobs, privacy-sensitive dataset extraction, and a licensing gate -- the highest blast radius in the plan.

## Phase 6: Hardening + Depth Backlog

**Goal**: Governance and agent-surface hardening from the Buzz and InvokeAI comparisons: a locally-signed unified audit log with per-sub-agent identity, a headless JSON CLI over the sidecar, and explicit diffusion VRAM-budget knobs.
**Prerequisites**: Phase 2 (routing events feed the audit log), Phase 5 (training events feed it too).
**Stability Gate**: Every cross-pillar action (chat turn, tool call, routing decision, generation, training run) appears in the signed local audit log attributable to a distinct actor identity; the JSON CLI drives a coding session headlessly with token auth; diffusion pipelines honor explicit VRAM/RAM budget knobs.
**Recommended model tier**: strong
**Recommended effort level**: medium
**Rationale**: Additive, well-bounded modules over existing event streams; cryptographic signing and a new local API surface warrant care but not frontier-level novelty.

### Sub-tasks

#### 6.1 -- Signed local audit log + per-agent identity (A11, BZ1/BZ2)

**Objective**: An append-only, locally-signed (per-actor local keys) SQLite audit log unifying events across pillars, with sub-agents (planner/critic/worker) getting distinct identities and attribution. No Nostr, no network.

**Failure modes**: If signing keys are missing on first run, they are generated locally and stored via the credential vault (never plaintext); if an event burst exceeds write throughput, events buffer with backpressure and a dropped-event counter (auditable gap, never silent loss); if verification of a log segment fails (tampering/corruption), the UI marks the segment untrusted rather than hiding it.

**Prompt**:
> Implement a local audit log: append-only SQLite store subscribed to TelemetryBus event families (chat, tool calls, routing decisions, generations, training runs), each event signed with a per-actor Ed25519 key (app identity + one per sub-agent role) generated locally and stored in the credential vault. Provide a verification API and a simple viewer surface (filter by actor/pillar/time). Secrets pass through `redactSecrets` before persistence. Local-only by construction. Acceptance: signature round-trip and tamper-detection tests, per-actor attribution test across a replayed session, backpressure test with counted drops.

#### 6.2 -- Headless JSON CLI over the sidecar (A12, BZ3)

**Objective**: A `nexus` CLI subcommand surface (JSON-in/JSON-out) exposing sidecar operations -- start/continue coding sessions, list models, queue generations -- authenticated with the existing local bearer token.

**Failure modes**: If the sidecar is not running, the CLI reports a structured error with a start hint (exit code contract, JSON error body); if input JSON is malformed or fails schema validation, the CLI rejects with the validation detail before touching the sidecar; if two CLI calls mutate the same session concurrently, sidecar-side session locking serializes them.

**Prompt**:

Acceptance: schema-validation tests, auth-failure and sidecar-down paths, an end-to-end scripted session against a stubbed model, concurrent-mutation serialization test.
