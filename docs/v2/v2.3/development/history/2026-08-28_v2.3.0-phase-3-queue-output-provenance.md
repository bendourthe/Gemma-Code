## Durable child-job runtime

- Enhancement jobs share the existing Studio `GenerationQueue`, `GenerationDatabase`, and `GpuScheduler` instead of creating an independent queue or GPU admission path.
- Enqueue requires a completed video parent and an indexed source output whose immutable path, byte size, and content hash match the request. Missing, malformed, incomplete, non-video, or changed sources fail closed.
- Every child persists its parent job, source output, fixed `video2x` backend identity, immutable request, source snapshot, priority, internal VRAM estimate, attempt lineage, optional idempotency key, progress, cancellation flag, timestamps, output, and typed terminal error.
- Explicit idempotency keys return the same matching child while distinct requests receive collision-safe child and output identities. Cancellation remains durable and authoritative over a late backend or publication success.
- Claimed jobs enter the shared GPU scheduler and retain their scheduler handle until completion. Shutdown closes request intake, stops new pumping, marks running work interrupted, requests cancellation, waits for admitted work to settle, cleans eligible private media, and closes the shared database.
- Restart reconstruction never converts interrupted work into success. Before enhancement execution, listing, or cancellation resumes, the runtime reconciles only deterministic private roots owned by interrupted child ids and preserves absent, unrelated, symlinked, or identity-replaced paths. Terminal errors retain their exact stage, bounded diagnostics, retryability, and `terminationConfirmed` evidence.

## Validated output and provenance lifecycle

- The process factory accepts only explicit absolute Video2X, ffprobe, and ffmpeg executables, passes argv arrays directly with no shell, enforces bounded deadlines and cancellation, and fails closed on unsupported platforms or missing media tools.
- Media validation checks a readable video stream, container, duration, dimensions, frame rate, and expected transform before publication. Provenance embedding and final validation happen in private staging.
- The original source is hashed before and after enhancement and remains byte-identical. A derived output is promoted under a child-owned collision-safe name. Every post-link failure rolls back only the exact linked inode; an unrelated path replacement is preserved, and partial or rejected output remains outside normal success presentation.
- One database transaction records the published generation output, completed enhancement run, source-linked provenance, done job state, and `video.enhancement.completed` outbox event. Identity triggers prevent an output or provenance record from being attached to the wrong child. Once that transaction commits, success is authoritative and a fallible readback or final tracking cleanup cannot quarantine the referenced file.
- The durable published-file size is taken from the final remuxed file rather than the pre-provenance staged size, preventing metadata embedding from creating a false size mismatch.

## IPC, idempotency, and notification recovery

The strict protocol exposes `video.enhancement.capability`, `video.enhancement.enqueue`, `video.enhancement.list`, and `video.enhancement.cancel`. Preset selection and parent/source identity come from the client; backend identity and the 8 GB scheduling estimate remain server-owned so a renderer cannot bypass resource policy. Generic generation cancellation delegates enhancement children to the same authoritative runtime.

Phase 3 assumes the product architecture's single sidecar writer: one Studio runtime owns one `GenerationDatabase` and serializes queue mutations in-process. SQLite constraints and explicit idempotency keys protect same-writer retries and identity conflicts, but multi-process writers are not claimed or tested. Completion notifications use a durable outbox, but notification delivery is not the source of truth. If a renderer misses an in-memory completion notification after outbox delivery, `video.enhancement.list` polling reconstructs the authoritative child state and output from the database.

## Troubleshooting and corrections

- A cancellation race initially reported `expected "cancelled", received "failed"` when a durable cancellation arrived after media work but before atomic completion. The runtime now re-reads authoritative queue state in both rejected-completion and thrown-completion paths, persists cancellation, and discards the late publication.
- Provenance remuxing changed the file size after staged validation. Treating the pre-remux size as the published size made correct completion fail. Atomic completion now stats the final published file and records that durable size.
- Restart reconstruction originally lost terminal error stage and diagnostics. The additive database migration and persistence adapter now store and rehydrate stage, diagnostics, and termination evidence exactly.
- Review found that shutdown and cancellation could persist a terminal state before final native-process evidence arrived. Same-state compare-and-set enrichment now advances only stage, bounded diagnostics, and termination confirmation while preserving the original terminal cause and timestamps; active cancellation waits for bounded scheduler settlement, and a persisted cancellation wins late failure or success.
- Review also found that a crash could leave a deterministic Video2X child root that caused permanent `output_conflict` on retry. Memoized startup recovery now removes only owned interrupted roots before handlers expose or execute enhancement state, with real-filesystem preservation tests for unrelated and replaced paths.

## Deferred evidence, not blockers for Phase 4

- Phase 4 owns the Video Lab Enhance actions, preset selection, status, cancellation controls, output presentation, honest synthesized-detail copy, and accessibility tests. Its state recovery must poll `video.enhancement.list` rather than depend only on transient completion notification delivery.
- Phase 5 owns real packaged Windows and supported Linux Video2X, GPU, ffmpeg, and ffprobe probes plus perceptual quality, duration, resource, installer, and license evidence. The external backend remains candidate support until those gates pass.
- Multi-process sidecar writers are outside the current architecture and are not proven. If that architecture changes, database ownership and cross-process idempotency require a new concurrency review.
- Phase 6 owns whole-plan convergence, full aggregate gates, known-gaps reconciliation, independent review, the first push, pull request, and remote CI. No Phase 3 work was pushed.
