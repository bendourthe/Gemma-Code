## Overview

This plan repairs the v2.2.9 Windows wizard using defects an operator hit in one session: black name-row and progress-list fills, Inkling-Small marked as having 0 GB RAM next to a card that correctly reported 16 GB VRAM, a VS Code page that hid its own checkbox on 1.135.0 and parked Unsloth Core there, and a process close after Dependencies finished and Models showed "Waiting to start".

The work stays in `scripts/installer/` plus the shared catalog and the extension engine pin. It does not add Video Lab features and must not land inside the in-flight v2.3.0 video plan. Run it on a dedicated branch. Last-phase evidence for this plan is `docs/v2/v2.3/development/v2.3.1-last-phase-evidence.md` so it does not overwrite v2.3.0's evidence file.

Success is a packaged unsigned Windows wizard that: (1) survives the model step or fails in-window with a log path, (2) reports system RAM on RAM-gated cards, (3) has no window-color bars on catalog headers or install rows, (4) always shows a VS Code extension checkbox when Microsoft `code` is on PATH, with replace/upgrade when the extension is already installed, and (5) explains Unsloth Core on Configuration. EmbeddingGemma 300M (not 300B) stays opt-in unless a recorded decision plus a reindex story says otherwise.

## Goals First

**Target problem**: A privacy-first local studio is unusable on first run if the installer paints broken chrome, lies about RAM, disables the VS Code option the page exists for, and then closes while models are queued.

**Target persona**: A developer or creator installing Nexus on a Windows laptop with one consumer NVIDIA GPU who wants honest hardware gating and a wizard that either finishes or fails with a visible log.

**Observable definition of done**: On a 16 GB VRAM host with normal system RAM, Inkling-Small is Compatible (patient-tier), catalog and installing lists use card surfaces rather than black bars, the VS Code checkbox is visible and tickable when `code` is present, Unsloth is explained on Configuration, and starting a multi-model install cannot silently destroy the process.

**Strategy grounding**: No `STRATEGY.md` or version-scoped strategy anchor exists. Scope is grounded in AGENTS.md (local-first studio, installer in `scripts/installer/`) and the 2026-08-28 field review. No `docs/solutions/` store exists.

## Phase 1: Honest host RAM and disk fields

**Goal**: RAM-gated catalog cards show real system RAM; disk remaining is not reused as RAM.
**Prerequisites**: None.
**Stability Gate**: On a fixture host with 32 GB RAM, 16 GB VRAM, and 200 GB free disk, Inkling-Small badges Compatible and Gemma 4 26B still reports the VRAM shortfall; `free_disk_gb` equals the install-path probe.
**Recommended model tier**: strong
**Recommended effort level**: high
**Rationale**: Several related files and a user-visible hardware gate, but the fix is wiring an already-computed HostProfile field.

### Sub-tasks

#### 1.1 -- Thread RAM onto installer state

**Objective**: `InstallerState` carries `total_ram_gb` from `detect_host()`, never from disk.

**Failure modes**: malformed CIM/sysctl output stays 0 and the badge says RAM is unknown rather than inventing a number; unreachable PowerShell/WMI falls back to a ctypes/GlobalMemoryStatusEx (Windows) or `/proc/meminfo` (Linux) probe, then 0 with unknown copy; disk probe and RAM probe must not write the same field if one fails and the other succeeds.

**Build class**: load-bearing.

**Prompt**:
> Add `total_ram_gb: int = 0` to `scripts/installer/src/nexus_installer/installer_state.py`. In the wizard shell (GPU page completion and/or a single `detect_host()` call already used by the Review guard), copy `HostProfile.total_ram_gb` onto that field. Strengthen `_detect_windows_total_ram_gb` so a windowed frozen process does not depend only on PowerShell CIM: prefer a ctypes `GlobalMemoryStatusEx` (or equivalent) and keep PowerShell as fallback. Do not log raw command output that might include machine inventory beyond the integer GB. Acceptance: a unit test feeds a fake 32 GB RAM host and the catalog page reads 32, not `free_disk_gb`.

## Phase 2: Install thread crash containment

**Goal**: Starting the model step cannot close the wizard with no error surface.
**Prerequisites**: Phase 1.
**Stability Gate**: A injected exception in `InstallEngine.run` during the model step leaves the window up, emits `install_finished(False, ...)`, and writes a log path; model row updates only occur on the GUI thread.
**Recommended model tier**: frontier
**Recommended effort level**: max
**Rationale**: Cross-cutting thread affinity, windowed PyInstaller, and a P0 process-death failure.

### Sub-tasks

#### 2.1 -- Fail closed on the install QThread

**Objective**: `_InstallThread.run` never lets an exception kill the process silently.

**Failure modes**: malformed state still finishes with `install_finished(False)` and a one-line reason; a hung puller is cancellation (`cancel()`), not this handler; two overlapping `start_installation` calls remain idempotent via `_has_started`.

**Build class**: load-bearing.

**Prompt**:
> Wrap `InstallEngine.run` from `_InstallThread.run` in try/except BaseException (log, then re-raise KeyboardInterrupt/SystemExit after signaling). Always emit `install_finished` with success=False and the exception type plus message (no token, no argv). Mirror the headless `run_step` guard so GUI and headless share one helper if that is smaller than duplicating. Acceptance: a test thread whose `run` raises RuntimeError still emits `install_finished` and does not call `sys.exit`.

---

#### 2.2 -- GUI-thread telemetry

**Objective**: `model_started` / progress / completed / failed never touch widgets from a `ThreadPoolExecutor` worker.

**Failure modes**: a worker that cannot queue to the GUI thread records the event in state and retries once, then marks the row failed rather than emitting from the worker; a slow GUI does not block pulls beyond the existing progress throttle; cancel during queue drain does not double-complete a row.

**Build class**: load-bearing.

**Prompt**:
> `ModelStepRouter` calls `events.started` from pool threads. Keep compute on the workers. Marshal Qt signal emits onto the `InstallEngine` QObject thread (QueuedConnection from the engine QThread, or a single slot that the engine invokes with `QMetaObject.invokeMethod`). Do not call `PhaseGroup.ensure_model_row` from a non-GUI thread. Acceptance: a test that stubs the router to call `started` from a dummy thread fails if the installing page slot would run on that thread; after the fix it runs on the QApplication thread.

---

#### 2.3 -- Visible crash log

**Objective**: A windowed build writes the last exception where Resume/Complete can show it.

**Failure modes**: log write failure still shows an in-memory message box; secrets (HF token) must not appear in the crash file (reuse recorder field allowlist); a second crash overwrites atomically, no partial JSON.

**Prompt**:
> When `install_finished` fires with an engine exception, write the reason into the existing install state file / log path (`background/state_store.py`) and show it on Complete or a modal before navigating away. Windowed `sys.stderr` is None; do not rely on it. Acceptance: tests assert the crash reason is in the state log and `hf_token` is not.

---

#### 2.4 -- Testing and Stabilization

**Objective**: Generate and run all tests for this phase. Iterate until the phase is stable before advancing to Phase 3.

**Prompt**:
> Generate automated tests for QThread exception containment, queued model signals, and crash-log redaction. Run installer pytest for engine, installing page, and background recorder. Record CI IMPACT: same installer pytest path; no new pipeline job. After tests pass, `/generate-session-history` for Phase 2, then ONE local commit. Do NOT push, do NOT open a pull request, and do NOT start remote CI.

## Phase 6: Architecture Refactor, Known-Gaps Reconciliation, and CI/CD

**Goal**: Leave the project well-organized, its known gaps reconciled, its living docs architecture current, and its pipeline reconciled against the canonical contract, with independent evidence that the plan Goal landed, then publish and integrate the completed branch.
**Prerequisites**: All prior phases.
**Stability Gate**: `docs/v2/v2.3/development/v2.3.1-last-phase-evidence.md` exists with one quoted section per duty below. A missing Goal, a Goal-review miss without a recorded known-gap, or a missing evidence section blocks `/update release`.
**Recommended model tier**: frontier
**Recommended effort level**: max
**Rationale**: Repo-wide refactor, Goal-vs-codebase review, known-gap reconciliation, and release gating carry high context volume and blast radius.

Use `docs/v2/v2.3/development/v2.3.1-last-phase-evidence.md` (not the unprefixed v2.3.0 evidence file).

#### 6.5 - Terminal CI/CD reconciliation
**Objective**: The repository's pipeline is compared field by field against the canonical contract, and every difference is either applied with approval or recorded as a known gap.
**Prompt**:

Quote the per-field comparison result in the evidence file under `## CI/CD coverage`.
