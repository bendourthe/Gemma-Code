## Section 1: Executive Summary

Thinking Machines' Inkling-Small (released 2026-07-30, nicknamed "Tiny Titan" in circulating coverage) is an open-weights, Apache-2.0, Mixture-of-Experts multimodal model: 276B total / 12B active parameters, native text + image + audio input, text output, up to 1M-token context, with community GGUF quantizations (74.8 GB and up) already runnable via llama.cpp / Ollama / LM Studio. It is exactly the kind of artifact the Nexus doctrine welcomes: local open weights, permissive license, no API key required.

The friction is physics, not policy. Even the 1-bit dynamic GGUF (74.8 GB) exceeds every consumer GPU Nexus targets under its single-GPU ceiling (README.md design principle 3), so Inkling-Small can only enter the catalog through the existing disk-offload "patient tier" (`core/registry/patientTier.ts`) or a high-RAM CPU path. The more broadly adoptable signal is the modality direction: Nexus's chat surfaces gained image attachments in v1.15.0 Phase 5 (`desktop/src/shared/chat/types.ts:34`), but the Chat pillar has no vision-model routing and no audio input at all, and the catalog schema has no per-model input-modality field to gate such UI.

Five insights survive extraction; four become adoption candidates (catalog modality metadata, vision-chat routing, audio-input bridge via the already-curated local STT models, and a patient-tier Inkling-Small catalog entry). Two access paths are rejected by name under the MCP Registry Policy: the hosted Tinker platform / Playground and hosted Tinker fine-tuning.

**Overall recommendation: adopt the modality-metadata and multimodal-chat-input work as the durable wins, list Inkling-Small as an opt-in patient-tier catalog entry for high-RAM hosts, and reject every hosted Tinker access path outright.**

## Section 4: Gap Analysis

### 4a: Adoption candidates (from insights)

- **A1 -- `modalities` catalog field (from I5).** Add an input-modalities array (e.g. `["text","image","audio"]`) to the `catalog.json` schema and `core/registry/catalog.ts` types so the chat shell can enable/disable image and audio attachment controls per selected model.
- **A2 -- Vision-chat routing (from I2).** Extend the Chat pillar to pass image attachments (already carried by `ChatMessage.attachments`) through to vision-capable local models served by Ollama, instead of confining attachments to the Image Studio / Video Lab surfaces.
- **A3 -- Audio-input bridge (from I3).** Add audio attachment to `MediaComposer.tsx` and route it through the already-curated local faster-whisper STT (catalog `task: "audio"`) as transcribe-then-chat; native audio-token reasoning waits on a model that fits the hardware ceiling.
- **A4 -- Inkling-Small patient-tier catalog entry (from I1, I4).** Curate `inkling-small` as an opt-in, never-default entry tagged `patient-tier` (`core/registry/patientTier.ts:23`), sourced from the unsloth GGUF line, with honest sizeGB (74.8+ GB) and the sub-1-tok/s latency warning; weights pull via the installer's existing HF weights puller (`scripts/installer/src/nexus_installer/engine/hf_weights_puller.py`) or `ollama pull` once upstream support lands.

### 4b: Strengths to preserve (Nexus-side)

- Hardware-aware curation discipline: per-VRAM-tier defaults (`core/registry/recommended.json`), best-of-family collapse, releaseDate/origin/license pills -- Inkling-Small must enter through this gate, not around it.
- The patient tier's explicit latency honesty (`PATIENT_TIER_LATENCY_WARNING`, `patientTier.ts:33-35`) -- a 75 GB+ MoE must never be presented as an interactive default.
- Hybrid retrieval + compaction as the long-context answer that actually fits consumer hardware.
- Zero as-a-service posture: local weights yes, hosted endpoints no.

## Section 9: Risks and Explicit Rejections

General considerations:

- A4's honest framing is the main product risk: at 74.8 GB minimum and sub-interactive speeds on consumer hardware, Inkling-Small must ship behind the patient-tier warning, or it becomes a support burden that discredits the catalog's "it just works" promise.
- GGUF multimodal support for this model is not yet confirmed in quantized form (unsloth card is silent on image/audio in GGUF); A4 may land as text-only until llama.cpp support for its multimodal projector is verified. Document that gap in the catalog entry copy.
- The 1M-context claim should not tempt a raw-context feature: KV-cache memory at that length is data-center-scale. Nexus's retrieval + compaction path remains the answer.

### Items explicitly NOT recommended for adoption

- **N1 -- Hosted access via the Tinker platform / Tinker Playground.** The announcement's primary access path (chat with the model on Thinking Machines' hosted platform) is generation-as-a-service: prompts, images, and audio would leave the machine to a third-party processor. **Rejected** by name under the **MCP Registry Policy** hard-no on generation-as-service (AGENTS.md; README.md design principle 1, local-first). Local open weights are the only sanctioned access path.
- **N2 -- Hosted fine-tuning of Inkling-Small on Tinker.** Fine-tuning as a hosted service requires shipping training data off-machine and opening a commercial relationship with the vendor. **Rejected** under the same **MCP Registry Policy** clause; any future fine-tuning interest routes through local tooling against the Apache-2.0 weights.
