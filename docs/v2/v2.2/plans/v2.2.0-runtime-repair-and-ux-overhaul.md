# Plan - Runtime Repair and UX Overhaul

**Project**: Nexus AI Studio
**Version**: v2.2.0
**Slug**: runtime-repair-and-ux-overhaul
**Plan Type**: Feature / Enhancement
**Created**: 2026-08-21
**Goal**: A fresh install of Nexus AI Studio is fully functional out of the box (sidecar up, all downloaded models visible and usable, Nexus-Hub harness present), models switch intelligently on a single GPU, and the app presents a modern chat-first UI with a compact sidebar, integrated GPU monitor, redesigned chatbot, modernized settings, and local data export/import.

## Overview

The v2.1.0 installer reports success, but the installed app is functionally inert: the Tauri shell never packages the Node sidecar (`tauri.conf.json` has no `bundle.resources`), spawns bare `node` from PATH instead of the installer-provisioned Node, never ships `core/registry/catalog.json` into the sidecar bundle, and never connects the provisioned diffusion Python venv. Every IPC call returns `sidecar-not-running`, so Image Studio / Video Lab show no models despite 9 of 10 models verified on disk, the Skills page misreports "not yet synced", and the Nexus-Hub harness never arrives (it is a best-effort runtime fetch that also depends on the sidecar). This plan repairs that plumbing first, so the app becomes usable in the earliest phases.

On the repaired foundation, the plan then delivers the smart single-GPU model-switching policy (no switch on tab click; switch on submit; confirm only when another model is busy; scheduler-mediated cross-model use during agentic tasks), rebuilds the Local Chatbot as a modern chat-first module with persistent storage, optional projects/folders organization, and auto-generated chat titles, and modernizes the shell: brand header removed from the sidebar, compact icon-only sidebar mode, GPU monitor integrated into the sidebar, a unified composer with embedded +/mic/send controls, an Ask-Inbox notification bell, modernized settings controls, User Profile retired into Settings, and a data export/import feature for machine-to-machine transfer.

Success looks like: install on a clean machine, open the app, and every tab works immediately - chat responds and titles itself, Image Studio and Video Lab list and run the downloaded models with the smart switch policy, the Agentic tab exposes the full Nexus-Hub command/skill surface, and the whole UI reads as one modern design system.

## Field evidence (2026-08-22)

A rebuilt installer now runs `--healthcheck` (Phase 1.4 landed enough to fail loudly). The Complete page reports:

`Installed (health check FAILED -- fail: sidecar request error: The pipe is being closed. (os error 232) | stderr: [ / / Nodejs v22.11.0] -- the app backend cannot start`

That changes the Phase 1 diagnosis. Provisioned Node 22.11.0 **does** start. The child then dies, so the next JSON-RPC write hits a closed stdin (Windows `ERROR_NO_DATA` 232). Restart backend uses the same spawn path and cannot recover. The likely crash is still boot-time: `better-sqlite3` is external and must sit next to `sidecar/dist/main.js` in the NSIS resource tree; esbuild already documents that missing native addon as "the sidecar died at startup before answering a single request." Healthcheck currently joins only the last three stderr fragments, which is why the UI shows garbage instead of the real stack.

In the running app (same session):

- Settings Models shows the honest banner "The Nexus backend could not start" plus Restart / Show details. Installed/Available/External remain 0.
- GPU footer reads "GPU: unavailable" (expected while the sidecar is dead).
- Sidebar still shows the logo plus "Nexus AI Studio" wordmark (duplicate of the title bar). Compact toggle exists but the rail is still icon-plus-label, not the default icon-only bar.
- `ADMIN_ENTRIES` still contains **User Profile** pointing at `/profile`, which only `<Navigate>`s to Settings. User instruction: **delete the nav item**. Do not keep a tab whose only job is to open Settings.
- Approvals is a sidebar bell. Opening it shows a "Pending approvals" dialog with the same 232 error. The popover has **no X, no Esc, no click-outside**. It is `position: absolute; bottom: calc(100% + 4px)` over the bell, so the toggle target is covered and the box cannot be dismissed from any tab.

User instruction: modernize **every** leftover native control on every Settings tab, not only the Models filters.

## Locked product decisions

Confirmed with the user on 2026-08-21, amended 2026-08-22 from the post-install session:

- **GPU switching**: smart policy. Tab clicks never load or unload. Submits classify: resident -> proceed; both models fit with >= 2 GB VRAM headroom -> co-reside via the existing `GpuScheduler.enqueuePanel`, no dialog; GPU idle -> auto-switch with a status chip; another module's job busy -> confirm dialog with a "remember for this session" option. Unknown/null VRAM telemetry -> confirm, never a silent swap. Agentic cross-model tool calls use the same gate, automated once consented.
- **Voice**: folded into the composer mic button (click = push-to-talk; menu holds Voice loop / VAD / Hold to talk). Persona moves to a per-chat settings popover, persisted.
- **Ask Inbox**: leaves the nav. A quiet bell (badge only when pending > 0) is allowed; **the popover must be dismissable** (X, Escape, click-outside) and must never cover its own toggle. Sidecar-down: do not auto-open, do not pin a red 232 dialog on every tab; the existing Settings backend banner is enough. Full list lives under Settings > Approvals. No auto-approve. Schedules stay in Settings.
- **User Profile**: **remove the sidebar item entirely**. No tab that redirects to Settings. Display name lives under Settings > General (or a Profile *settings section*, not a second nav entry). Silent `/profile` bookmark redirect is fine.
- **Sidebar**: brand block removed (title bar keeps the single brand, without the accent-reactive outline); compact icon-rail is the **default**, persisted, with expand toggle.
- **Settings chrome**: every Settings tab (Models, Skills, Skill Optimizer, Credentials, Local API, Fine-tuning, MCP, Security, Data, Approvals, General) uses the shared Select / SearchInput / Button / Switch primitives. No leftover native search boxes, flat text fields, or unstyled Preview buttons.
- **Hub harness**: available offline via a checksummed bundled snapshot, refreshed by installer-time fetch when online and by Sync thereafter; user-authored skills are never wiped by a re-sync.
- **Release**: one plan, v2.2.0, plumbing phases first.

## Phase 1: Sidecar Packaging and Runtime Wiring Repair

**Goal**: The installed (NSIS-packaged) app reliably spawns the Node sidecar with its catalog and connects it to the installer-provisioned Node and diffusion Python runtimes.
**Prerequisites**: None.
**Stability Gate**: On this Windows host after rebuild, Complete shows sidecar ok (not os error 232); Restart backend is unnecessary because the child stays alive; `ipc_call("models.list")` returns catalog rows. A sabotaged native-addon tree still fails the health check, but the verdict includes the child exit code and a readable stderr tail (not three slash-joined fragments).
**Recommended model tier**: frontier
**Recommended effort level**: high
**Rationale**: Cross-layer packaging work (Tauri config, Rust spawner, esbuild, NSIS payload, installer engine) with high blast radius and no existing test coverage.

### Sub-tasks

#### 1.1 - Bundle the sidecar and catalog into the Tauri app

**Objective**: `sidecar/dist/main.js`, its `wasm/` grammars, and `catalog.json` ship inside the installed app and resolve via `BaseDirectory::Resource`.

**Failure modes**: If the resource is missing at runtime (corrupt install), `Sidecar::spawn` must surface a user-visible fatal state (Phase 2.2 renders it), not a silent stderr line; if the catalog file is unreadable or fails schema parse, `resolveCatalog()` must log and report a distinct `catalog-load-failed` status through `models.list` rather than silently returning `{ models: [] }`; concurrent spawn attempts (retry button + startup) must be idempotent via a spawn mutex.

**Build class**: load-bearing.

**Prompt**:
> In the Nexus-AI repo, make the packaged Tauri app self-contained for the sidecar. (1) `bundle.resources` must ship the **entire** `desktop/sidecar/dist/` tree: `main.js`, `package.json` (`type: commonjs`), `catalog.json`, `wasm/`, **and** `dist/node_modules/better-sqlite3` (plus `bindings` and `file-uri-to-path`) that esbuild already copies. The 2026-08-22 field failure is Node 22.11.0 starting then dying; the esbuild file already states that bundling the sqlite wrapper without the `.node` binary kills the sidecar before the first RPC. A packaging test must unzip/list the NSIS/Tauri resource dir and assert `better_sqlite3.node` sits next to the bundle Node can resolve from `main.js`. (2) `Sidecar::spawn_with` must set the child cwd to the directory that contains `main.js` so native `require` resolution cannot miss the copied addon. (3) Keep `NEXUS_CATALOG_PATH` and the `catalog-load-failed` status. Acceptance: healthcheck on this host is sidecar ok; deleting only the native addon from a fixture bundle reproduces 232 (or a spawn crash) with a stderr line that names better-sqlite3, not `[ / / Nodejs v22.11.0]`.

---

#### 1.2 - Spawn the provisioned Node runtime

**Objective**: The Rust spawner uses the installer-provisioned Node (`%LOCALAPPDATA%\Nexus\runtime\node\node.exe` on Windows, per-OS equivalents), falling back to PATH `node` only in dev.

**Failure modes**: Provisioned Node missing or non-executable -> try PATH `node`, and if both fail record a structured `sidecar-spawn-failed:<reason>` state queryable over a new `ipc_status` command instead of the bare `sidecar-not-running` string; Node present but sidecar crashes on boot (exit within 3 s) -> capture last stderr lines into the status; two spawns racing (auto-restart + manual retry) -> single-flight guard.

**Build class**: load-bearing.

**Prompt**:
> In `desktop/src-tauri/src/sidecar.rs` and `lib.rs`, replace `Command::new("node")` with a resolution chain: (1) explicit `NEXUS_NODE_PATH` env var, (2) a Node runtime bundled with the app itself (prefer a Node SEA binary or Tauri `externalBin` sidecar next to the resources - this makes the app independent of the installer's PATH handling, since Windows GUI processes often do not inherit a freshly-written user PATH), (3) the installer-provisioned runtime path (Windows `%LOCALAPPDATA%\Nexus\runtime\node\node.exe`; mirror the per-OS paths written by `scripts/installer/src/nexus_installer/engine/node_provisioner.py`, read via `~/.nexus/runtime.json`), (4) PATH `node` (dev fallback). If a stale runtime.json points at an uninstalled Node, fall through the chain and report which candidates failed. Store spawn outcome (which node, which script path, failure reason, last stderr tail on early exit) in `AppState`, expose it via a new `sidecar.status` Tauri command, and add a `sidecar.restart` command with a single-flight guard. Keep `sidecar-not-running` as the IPC error string for compatibility but make the richer status available to the frontend. Add Rust unit tests for the resolution chain (temp dirs standing in for the provisioned path). Acceptance: on a machine without system Node, the packaged app spawns the provisioned Node; `sidecar.status` reports the resolved path; deliberate misconfiguration produces a reasoned failure status.

#### 1.3 - Connect the diffusion Python runtime

**Objective**: The sidecar's diffusion runtime spawns the installer-provisioned venv Python (`%LOCALAPPDATA%\Nexus\python\venv`) instead of bare `python`, so image/video generation can actually run in an installed app.

**Failure modes**: Venv missing (user skipped diffusion provisioning) -> `image.generate` / `video.generate` return a typed `runtime-unavailable` error the studios can render with a "provision in installer/settings" hint; venv present but import fails or process exits early -> capture stderr tail into the job failure; two generate jobs racing for the runtime -> existing GpuScheduler single-active-job invariant applies, verify it holds through the new spawn path.

**Build class**: load-bearing.

**Prompt**:
> Wire the diffusion runtime to the provisioned environment. (1) Define a small runtime-config contract: the installer (`scripts/installer/src/nexus_installer/`) writes `~/.nexus/runtime.json` recording `nodePath`, `diffusionPython`, `diffusionCwd`, `modelsRoot`, and Ollama binary info after provisioning. (2) The sidecar reads it at boot (`desktop/sidecar/src/main.ts`) and passes `NEXUS_DIFFUSION_PYTHON` / `NEXUS_DIFFUSION_CWD` into the existing `runtimeFactory.ts` resolution (which already honors those vars, defaulting to bare `python`). (3) Ship the `runtimes/diffusion/` Python sources with the installer payload (they are not in the NSIS bundle today) and record their location in runtime.json. (4) Typed `runtime-unavailable` error when config or venv is absent. Add tests: sidecar unit tests with a fake runtime.json; installer pytest asserting runtime.json contents. Acceptance: packaged app on a provisioned machine runs an image generation end to end; with the venv renamed away, the studio shows the typed error, not a crash or hang.

#### 1.4 - Installer health check that proves the app works

**Objective**: The installer's first-run health check fails when the sidecar cannot spawn or answer, instead of passing whenever the process survives 5 seconds.

**Failure modes**: App starts but sidecar dead -> health check reports the `sidecar.status` failure reason and marks install failed with remediation text; health-check IPC times out (slow disk cold start) -> retry with backoff up to 30 s before failing; app cannot start at all -> existing failure path retained.

**Build class**: load-bearing.

**Prompt**:
> Keep `--healthcheck` (already invoked by `first_run_health_check`). Fix the verdict so a dead child is diagnosable: include `exitCode`, `nodePath`, `scriptPath`, and at least the last 20 stderr lines as a JSON array (the Complete page must not `" / ".join` three fragments into `[ / / Nodejs v22.11.0]`). Before the first `models.list` write, `try_wait` the child; if it has already exited, fail immediately with that stderr instead of writing to a closed pipe (the 232). Retry/backoff stays for slow starts only while the process is still alive. `sidecar.restart` must use the same spawn_with cwd/resources; it cannot succeed until 1.1 ships the native addon. Acceptance: this host's next installer either prints sidecar ok, or prints a single readable reason that names the missing file or thrown exception.

**Objective**: Node 22.11.0 starting is not success. The child must still be running when the first JSON-RPC line is written, and Restart backend must not be a no-op of the same crash.

**Failure modes**: Native `.node` ABI mismatch vs bundled Node 22 -> rebuild better-sqlite3 against that Node before packaging, fail the sidecar build if `npm rebuild` was skipped; unhandled exception at `main.ts` import time (scheduler, serving bind, sqlite open) -> process.exit after writing the stack to stderr, never a silent 232; `rl.on("close")` firing because stdin was not piped correctly in `--healthcheck` -> do not treat healthcheck as a TTY; CREATE_NO_WINDOW / GUI PATH are already out of the picture on this host (Node was found).

**Build class**: load-bearing.

**Prompt**:
> Treat the 2026-08-22 Complete-page 232 as the Phase 1 acceptance bug. (1) After `Command::spawn`, wait until stderr shows `[nexus-sidecar]` or 500 ms of liveness (`try_wait` is None) before `writeln` of `models.list`. (2) If the child exits, surface `fail: sidecar-exited:<code>` plus full stderrTail; never map that to "no models installed". (3) Confirm `tauri.conf.json` resources include `sidecar/dist/node_modules/**` (not only main.js). (4) Set cwd to the script directory. (5) Add a desktop/installer test: spawn fixture `main.js` that `require('better-sqlite3')` against a missing addon and assert the healthcheck verdict contains the module name. Acceptance: Restart backend on this machine either brings models.list back or the banner Show details names the real crash; it must not remain "The pipe is being closed."

## Phase 2: Model Availability End to End

**Goal**: Every model the installer downloaded (HF weights and Ollama pulls) is detected, listed, and runnable in the app, and every empty or error state tells the truth.
**Prerequisites**: Phase 1.
**Stability Gate**: On the reference machine (RTX 3080, models from `dist/nexus-install-models-log.txt`), Image Studio lists realvisxl-v5 + sana-1.6b-2k, Video Lab lists ltx-video + wan2.1-t2v-1.3b + sana-video-2b-720p, Settings > Models shows correct installed counts, and a killed sidecar produces a "sidecar unreachable - restart" state, never "no models installed".
**Recommended model tier**: strong
**Recommended effort level**: high
**Rationale**: Focused reconciliation and UI-truthfulness work on a now-working substrate; moderate complexity, well-localized files.

### Sub-tasks

#### 2.1 - Fix installed-model reconciliation

**Objective**: The weights-dir probe matches what the installer actually wrote, and a non-default models root is honored.

**Failure modes**: Weights dir contains an id-sanitized name (`safe_dir_name` output with `.`/`:` replaced) -> probe matches by applying the same sanitization to catalog ids, plus a marker-file fallback (`model-id.txt` written by the installer); models root missing/unreadable -> probe returns empty with a surfaced `weights-root-missing` warning, not a crash; probe racing a mid-download model -> only directories whose files pass the existing verification manifest count as installed.

**Build class**: load-bearing.

**Prompt**:
> Fix installed-model detection. (1) In `core/registry/installedProbe.ts`, the weights probe compares raw catalog ids against directory names, but `scripts/installer/src/nexus_installer/engine/hf_weights_puller.py` writes `safe_dir_name(id)` directories (dots/colons sanitized) - reproduce the exact sanitization in TypeScript and compare sanitized-to-sanitized; also have the installer write a `.nexus-model-id` marker file in each weights dir and prefer marker-based matching. (2) Honor `modelsRoot` from `~/.nexus/runtime.json` (Phase 1.3) in `createModelsRuntime()` (`desktop/sidecar/src/handlers.ts` currently calls it with no args) and add a `NEXUS_MODELS_ROOT` env override; use one shared resolver for the installer's `models_root` and the sidecar's default. (3) Resilience: when catalog load has failed (Phase 1.1 status), synthesize installed rows directly from the `weights/` tree and Ollama `/api/tags` instead of returning nothing - degraded metadata beats an empty list, and the catalog-load-failed banner still shows. (4) Cover ids `wan2.1-t2v-1.3b`, `sana-1.6b-2k`, `qwen2.5-coder:14b` in unit tests against fixture dirs. Acceptance: with fixture weights dirs named per the installer, all five diffusion models flip to installed; a custom models_root install is detected; an empty catalog plus a weights tree still lists those ids as installed (degraded).

**Build class**: load-bearing.

**Prompt**:

#### 2.3 - Ollama version compatibility and failed-pull recovery

**Objective**: The installer detects when the pinned Ollama is too old for a catalog model (the gemma-4-12b `412` failure) and upgrades or surfaces retry, and the app can retry failed pulls.

**Build class**: load-bearing.

**Prompt**:
> Handle Ollama version drift. Note: `ollama_installer.py` already carries a `MIN_OLLAMA_VERSION` floor (0.32.15 per the v2.1 changelog pin) and catalog entries may already declare `minOllamaVersion` - verify what exists before adding anything; the field evidence (this host's gemma4:12b HTTP 412) proves the enforcement path does not fire for a pre-existing older Ollama install. Acceptance: a simulated 412 against an old pre-existing Ollama triggers the upgrade path and the retry succeeds in tests; the install summary names the failed model with a retry button rather than a log line.

## Phase 3: Nexus-Hub Harness Provisioning and Skills Surface

## Phase 4: Smart Single-GPU Model Orchestration

**Goal**: Model switching on a single GPU follows the agreed smart policy: never on tab click, on submit with confirm-only-when-busy, automatic with a toast when idle, and scheduler-mediated cross-model use during agentic tasks.
**Prerequisites**: Phases 1-2 (models must load and list correctly).
**Stability Gate**: Clicking between tabs never changes GPU residency; submitting an image prompt while the GPU is idle swaps models with a status chip (or co-resides silently when both models fit with 2 GB headroom); submitting while an agentic task is generating raises a confirm dialog whose "remember for this session" suppresses repeats; an agentic task can invoke image generation and the scheduler swaps/co-resides and restores models automatically.
**Recommended model tier**: frontier
**Recommended effort level**: high
**Rationale**: Policy layer over concurrent scheduler/VRAM machinery where wrong sequencing corrupts user sessions; high-risk concurrency semantics.

### Sub-tasks

#### 4.1 - Switch-policy engine over GpuScheduler

**Objective**: A `ModelSwitchPolicy` layer that classifies every model-requiring action as no-op (resident), co-reside (both fit in VRAM), auto-switch (GPU idle), or confirm-required (another model busy), reusing `core/scheduler/GpuScheduler.ts`, `enqueuePanel` co-residency, and `modelSwap.ts`.

**Failure modes**: Telemetry stream absent/null free-VRAM -> classify as `confirm` (never a silent swap and never an indefinite defer - the user decides when the machine cannot); the busy job finishes between classification and user confirm -> re-classify on confirm so the dialog resolves as auto-switch (no stale confirm); two surfaces submitting simultaneously -> classification and enqueue are atomic within the scheduler's queue lock so exactly one confirm dialog can win; requested model not installed -> typed not-installed error, no queue entry.

**Build class**: load-bearing.

**Prompt**:
> Implement `core/scheduler/ModelSwitchPolicy.ts` on top of the existing GpuScheduler + modelSwap: input (targetModelId, requestingModule, currentResidency, freeVram, sessionRememberSet, activeJobs), output one of `resident | coreside | auto-switch | confirm { busyWith } | defer { reason }`. Rules: tab navigation never calls it (audit desktop routes to confirm no load fires on mount - the studios currently only list, keep it that way; `setForegroundModule` stays a scheduling hint, never a load trigger); generation/chat submits and agentic cross-model tools call it; if the requested and resident models both fit with >= 2 GB VRAM headroom, return `coreside` and admit via the existing `enqueuePanel` co-residency path (no dialog); `confirm` only when an active job from another module is running or when free VRAM is unknown; a "remember for this session" flag on confirm suppresses future dialogs for that modality pair this session; re-classify at confirm time; after an honored swap with `keepWorkerResident: false`, reuse the existing `unloadOllamaModel` path. Emit scheduler telemetry events for every decision. Unit-test the matrix (idle/busy x resident/non-resident x fit/no-fit x remember x same/other module x telemetry-null, confirm-time re-classify race, not-installed). Acceptance: full decision-matrix tests green; no code path loads a model from a route mount.
