## 2. Chronological Steps

### 2.1 Explorer-backed transcripts

**Plan specification**: Persist completed turns through the explorer client, hydrate on open, and keep failures visible without losing the working in-memory conversation.

**What happened**: The async explorer contract now exposes `appendMessage` and `listMessages`. ChatPage hydrates only the opened chat, waits for that hydration before accepting a new turn, writes user and terminal assistant rows, and never persists pending placeholders. Version guards prevent a late response for one chat from replacing another chat's transcript.

**Key files changed**: `desktop/src/modules/chat/ChatPage.tsx`, `desktop/src/modules/chat/chatExplorerClient.ts`, `desktop/src/modules/chat/types.ts`

### 2.2 Context replay across renderer and sidecar lifetimes

**Plan specification**: A restored transcript must not continue against an empty LLM context.

**What happened**: `chat.session.start` accepts up to 500 persisted user and assistant rows. ChatPage supplies visible history when a session is first created and retries once with that same history if a restarted sidecar rejects the old process-local session id. Retrieved memory is inserted only for the current request and is not appended to the durable session history.

**Key files changed**: `desktop/src/modules/chat/chatIpcClient.ts`, `desktop/sidecar/src/protocol.ts`, `desktop/sidecar/src/chat/sessionManager.ts`

### 2.3 Durable episodic memory composition

**Plan specification**: Production App must not rely only on `InMemoryMemoryHub`, and later turns must receive relevant durable context.

**What happened**: App uses a narrow renderer IPC facade. The sidecar composes the existing `EpisodicMemory` store at `~/.nexus/memory.db`, redacts on write, filters results to the active chat scope, and supplies relevant content to ChatSessionManager. Retrieval failures do not block generation.

**Key files changed**: `desktop/src/modules/chat/memoryIpcClient.ts`, `desktop/src/App.tsx`, `desktop/sidecar/src/chat/memoryRuntime.ts`, `desktop/sidecar/src/handlers.ts`, `desktop/sidecar/src/main.ts`

## 5. Plan Discrepancies

The older Phase 4 prose treated transcript persistence as sufficient. The verification addendum correctly identified that `sessionIdsRef` is renderer-local and sidecar sessions are process-local, so history replay and restart recovery were required to preserve actual model context.

---

## 6. Assumptions Made

- **Explorer rows are the visible transcript source of truth**: episodic memory supplements future turns but does not replace or duplicate the chat log.
- **Replay is bounded**: the protocol accepts at most 500 user and assistant rows, matching the explorer hydration limit.
- **Memory retrieval is advisory**: a memory database error must not prevent a user from receiving a chat response.
