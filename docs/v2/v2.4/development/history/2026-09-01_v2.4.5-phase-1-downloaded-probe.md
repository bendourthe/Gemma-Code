## 2. Chronological Steps

### 2.1 Probe and report types (T001)

**What happened**: Before writing anything, the premise was checked rather than assumed. The operator asked whether repeated installs had been downloading the same models again and consuming disk each time. Measured on the host:

```
$ du -sh ~/.nexus/models/weights/*
70G  inkling-small        44G  wan2.1-t2v-1.3b       18G  sana-video-2b-720p
13G  realvisxl-v5        8.8G  ltx-video            6.7G  juggernaut-xl-v9
6.3G unlimited-ocr-3b    6.1G  sana-1.6b-2k         2.9G  faster-whisper-large-v3
1.4G sana-1.6b-int4      313M  kokoro-82m
$ ls ~/.nexus/models/_tmp        # empty
$ find ~/.nexus/models/weights/inkling-small -type f | wc -l
4
```

Eleven distinct directories, each present once, no partial or temp leftovers. `inkling-small` is a legitimate three-part GGUF split totalling ~74.7 GB, not a duplicate. `hf_weights_puller._install_file` already hashes any file it finds and logs `already present and verified; skipping`, so the downloader was never the problem.

That relocated the defect. `evaluate_install_guard` receives `state.selected_models_gb`, which `_ModelSelection.total_gb` computes as a sum of catalog sizes with no filesystem reference. The wizard was refusing an install over 194.4 GB it was not going to fetch.

`InstalledReport` is a frozen dataclass carrying `downloaded`, `pending`, `downloaded_gb`, `pending_gb`, and `probe_errors`. `downloaded_gb + pending_gb` conserves the selection total by construction, since both are summed from the same `sizes_gb` mapping - a test pins that, because a picker footer and a Review page that disagree about what was selected would be worse than the original bug.

Sizes are passed in as a mapping rather than read from the catalog inside the probe. The picker already parses `sizeGB` into `CatalogModel.size_gb` and displays it on every card; deriving a second, independently-parsed number here would let the estimate drift from the pills the user is reading.

### 2.2 Two stores, because the selection spans two protocols (T001, T002)

**What happened**: The selection is not homogeneous. `model_router.protocol_for` routes each entry to `huggingface` or `ollama`, and those land in different places. Of the operator's 14 models, `embeddinggemma`, `gemma-4-12b-it-gguf`, and `gpt-oss:20b` are ollama-protocol and live in `~/.ollama/models`, not the weights tree. A detector covering only the weights tree would have under-reported and left the guard wrong for exactly the chat models most users select first.

Huggingface detection reuses the puller's own `model_weights_dir` / `safe_dir_name`, so there is one definition of where weights live. It prefers the `.nexus-model-id` marker the puller writes, because `safe_dir_name` maps `:` and `/` to `-` and is therefore lossy: two ids can collide on one directory. A marker naming a different id means the directory belongs to someone else, and the model is reported absent rather than claiming another model's weights. A test covers that collision.

Ollama detection prefers `GET /api/tags`, the same endpoint `ollama_installer.py` and `main.py` already call, with the 2s budget `main.py` uses. When that fails it reads the on-disk manifest path instead, derived from `ollama_target_for`. The path mapping had to cover both shapes actually present on the host: `registry.ollama.ai/library/<name>/<tag>` for a bare target, and `hf.co/<owner>/<repo>/<quant>` for an HF-GGUF-via-ollama entry, which is what `gemma-4-12b-it-gguf` resolves to.

Two deliberate properties, both documented at the top of the module:

- **Presence, not verification.** Nothing is hashed. Verifying 176 GB would take minutes on the picker's load path and would duplicate what `_install_file` already does per file during the install, where a mismatch triggers a re-download. Being wrong here costs a slightly optimistic estimate; it cannot produce a broken install.
- **Fail open.** Unreachable Ollama, unreadable models root, malformed manifest - each degrades that model to "not downloaded" and appends a line to `probe_errors`. That reproduces the old over-cautious behavior, which is safe. A probe that could raise on the picker's load path would turn a convenience feature into a wizard that will not open.

One bug was found and fixed during review rather than by a test: `selection` is typed `Iterable[str]` and is walked twice (once to decide whether an Ollama call is needed, once for the main loop), so a generator argument would have been exhausted by the first pass and the second would have seen an empty selection. It is materialized once at entry, and a test now passes a generator.

### 2.3 Testing and stabilization (T003)

**What happened**: 21 cases in `scripts/installer/tests/test_installed_models.py`, all on `tmp_path` fixtures so a developer's own model store cannot make them pass or fail. Coverage: huggingface present / missing / empty-directory / nested-file / marker-match / marker-collision; the three manifest path shapes; an unreachable Ollama returning an empty set rather than raising; API-path and disk-path detection; an uncatalogued id (the real `qwen3-coding:30b-a3b-offload`, which is absent from `catalog.json` and pulls verbatim); a generator selection; an unreadable models root failing open; and a corrupt manifest still counting as present, since presence is the question.

The load-bearing case is `test_reproduces_the_field_case`: eleven models totalling ~178 GB on disk plus one 18 GB model absent, asserting `pending_gb == 18.0`. That is the number the guard should have been comparing against free disk all along.

## 6. Assumptions Made

- A model directory holding at least one regular file at any depth counts as downloaded. An interrupted download leaves an empty directory, which is correctly reported absent, but a partially-complete tree reports present and is repaired by `_install_file` during the install.
