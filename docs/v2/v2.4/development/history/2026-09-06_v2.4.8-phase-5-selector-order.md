# Development Log: v2.4.8 Phase 5 - Selector order and default

**Date**: 2026-09-06
**Operator**: Benjamin Dourthe
**Assisted by**: Claude Fable 5.1
**Objective**: Every model selector lists the installer's most-recommended model first and selects it by default when no favorite is stored.
**Outcome**: A shared `pickerOrder` (catalog tier, then snapshot rank, then newest, then VRAM, then name) drives the switcher and the default resolver; the default honors a snapshot pick only when the catalog endorses it; and the installer's snapshot writer now names the picker's own top pick per task instead of the first selected id of the right type.

## 2. Chronological Steps

### 2.1 The plan's diagnosis was incomplete

**What happened**: The plan attributed screenshot 5 to a missing snapshot falling back to alphabetical order. Reading the operator's actual `~/.nexus/selected-models.json` showed otherwise:

```json
"recommendedByTask": {
  "chat": "embeddinggemma",
  "agentic": "gpt-oss:20b",
  "image": "juggernaut-xl-v9",
  "video": "sana-video-2b-720p"
}
```

`orderedIds` was already in picker display order (`gemma-4-12b-it-gguf, inkling-small, gpt-oss:20b, lfm2.5:2.6b, ...`). Screenshot 5 is the Agents picker: `recommendOrderForTask` puts the agentic pick first, then the ordered ids, which reproduces the screenshot exactly. The Chat recommendation was an embedding model, which the Chat picker simply filtered out.

The root cause is the installer's `_recommended_by_task` in `runtime_provisioner.py`: it took the first selected id whose catalog type mapped to the task, and it mapped `embed` to `chat`. For an all-models selection that yields `embeddinggemma` for chat and the first `task: "agentic"` entry (gpt-oss) for agentic, while the picker itself ranks the tagged Gemma 4 12B first on both tabs.

### 2.2 Desktop picker order (T020)

**What happened**: `pickerOrder(models, { hostVramGB, recommendOrder })` in `catalogTabs.ts` sorts owned rows the way the installer picker displays them: over budget last (when host VRAM is known), catalog tier (required, recommended, other), snapshot rank, newest release, highest VRAM, name. No family collapse and no VRAM-floor hiding, since nothing on disk may vanish from a picker. `QuickModelSwitcher` uses it and stops discarding `hostVramGB`. A stale snapshot that names an untagged model can now only break ties inside a tier.

### 2.3 Default resolver (T021)

**What happened**: `installedForTask` returns `pickerOrder` with the snapshot's ids as the rank, so `ready[0]` is the top recommendation. `resolveDefaultId` keeps every existing rule and adds one: when the snapshot pick carries no `required` / `recommended` tag and some ready row does, the first tagged row wins. A tagged snapshot pick, or a catalog with no tagged rows, behaves exactly as before, so the four page call sites are unchanged. With the operator's stale snapshot, Agents now opens on Gemma 4 12B; the Chat pick (`embeddinggemma`) is not in `ready` and falls through to `ready[0]`, also Gemma 4 12B.

### 2.4 Installer snapshot writer (T021, installer side)

**What happened**: `_recommended_by_task` now mirrors the picker: an entry's tabs come from `task` then `type` (`embed` maps to Embeddings, never Chat; a chat model with `agentic: true` also sits on Agentic), and the pick per task is the selected entry with the best `(tier, newest release, selection order)` key. The operator's selection therefore writes `chat` and `agentic` as `gemma-4-12b-it-gguf`, `image` as `juggernaut-xl-v9` (tagged), and `video` as `sana-video-2b-720p`. Four pytest cases cover the operator selection, embeddings never becoming a chat pick, untagged fallback by newest then order, and uncatalogued ids being skipped.
