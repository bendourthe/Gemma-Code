## 2. Chronological Steps

### 2.1 Why video failed

`torch.nn.RMSNorm` exists from torch 2.4. diffusers 0.36's SANA-Video pipeline imports it. The diffusion venv on the operator host carries `2.3.0+cu121` because both lock files (`scripts/installer/build/versions.lock.json` and `runtimes/diffusion/runtime-lock.json`) pin `torch==2.3.0`, and every readiness probe (installer smoke, sidecar `status()`, runtime `torch_cuda_state`) checked only that a CUDA torch was importable and saw a device. So the runtime said `ready` and the first video generate raised inside the pipeline import. This is the second field report of the same symptom; the v2.4.3 SANA-Video work never had a torch floor.

### 2.2 Lock bump with verified wheels

Both lock files now pin `torch==2.5.1`, `torchvision==0.20.1`, `torchaudio==2.5.1` on every target (`win-x64-nvidia`, `linux-x64-nvidia`, `mac-arm64-apple`). The two CUDA targets carry twelve `referenceArtifacts` (cp311 and cp312, three packages, two platforms) whose `sha256` came from the `#sha256=` fragments on `download.pytorch.org/whl/cu121` and whose `size` came from a HEAD request against the `download-r2.pytorch.org` mirror the lock already uses. The provisioner refuses a manifest whose artifacts are unverified, and the repair path verifies size and hash before install, so a wrong number fails closed. `runtimeRequirements` (diffusers 0.36.0, transformers 4.53.2, and the rest) are unchanged; neither declares a torch upper bound.

The manifest fingerprint changes with the lock, so a re-run of the installer re-provisions the venv rather than reusing the cached one.

### 2.3 A torch floor on all three layers

| Layer | Change | Effect |
|---|---|---|
| Installer `diffusion_venv_provisioner._smoke` | `MIN_TORCH_VERSION = (2, 4)`, `torch_too_old()`; a ready smoke with an older torch becomes `failed / TORCH_TOO_OLD / retryable` | the provisioner reinstalls instead of recording `ready` |
| Sidecar `runtimeFactory.status()` | a `ready` record whose `torch_version` is below 2.4 is `repairable / TORCH_TOO_OLD` with a plain-language message | Settings > Video offers Repair, which installs the lock's 2.5.1 stack in place |
| Runtime `pipelines/base.py` | `torch_cuda_state()` returns `torch-too-old`; `accelerator_not_ready` and `classify_runtime_not_ready` map it to a typed `RuntimeNotReady` that names the version, the floor, and the fix | a generate on a stale venv fails before the pipeline import with "repair the media runtime from Settings > Video or re-run the installer", not an AttributeError |

Unparseable versions are never "too old" on any layer, so the guard cannot mask the other probes.

### 2.4 Loading model state

`real_execute` emits `base.emit_stage(job_id, "loading")` before each `_load_*` pipeline call and `"generating"` once `_move_pipe` has put it on the device, through a sink `main.py` installs onto the existing `progress` notification. The sidecar already forwarded `stage`. On the desktop, `ChatMessage.progress` gains `stage`; the Image and Video pages keep the last explicit stage per message (heartbeats carry none) and default to `loading`; `isLoadingModel()` in `MessageBubble` is true for a studio pending message with no event yet, or with stage `loading` and no counted step; the orb then shows a fixed `Loading model...` caption (new `caption` prop on `AgentStateOrb`) under the `model-loading` activity and switches to the studio captions on `generating` or the first counted step.
