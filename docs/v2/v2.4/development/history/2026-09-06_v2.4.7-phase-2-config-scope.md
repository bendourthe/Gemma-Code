## 2. Chronological Steps

### 2.1 Derive required components (T006)

**What happened**: The answer to "do we need all these" came from tracing what each option gates, not from taste. Three of the eight were load-bearing:

- **Ollama** serves every `ollama`-protocol model, which is all chat and most embedding models.
- **The Python environment** runs every `huggingface`-protocol model: image, video, audio, document.
- **The desktop app** is the product.

Unchecking any of them broke a model the user had selected two steps earlier, and the wizard said nothing at all. That is the failure mode this phase removes.

`engine/required_components.py` resolves them from the selection. Two details matter. An id absent from the catalog counts as requiring Ollama, because unknown ids route to `ollama pull` verbatim under the `--model` override contract -- missing that would ship an install whose only model cannot be served. And the resolver returns a reason per component, because a list shown instead of asked still has to explain itself; an unexplained "will be installed" is just a differently-opaque decision.

`apply_required_components` folds the result into `components_to_install` additively and idempotently. The engine contract is unchanged: that list is still exactly what the installer executes, and install order is preserved so the step sequence does not shift.

### 2.2 Will be installed list (T007)

**What happened**: The three checkboxes became a read-only list rendering each component with its reason beneath it. It is recomputed in `showEvent` rather than `__init__`, because the model picker precedes this page -- computing it at construction would render it against an empty selection and always show only the desktop app.

The Ollama URL field is hidden when the selection does not require Ollama, since a URL for a daemon that will not be installed is noise.

### 2.3 Remove the settings toggles (T008)

**What happened**: "Enable thinking mode" and "Enable persistent memory" are gone. They set `state.enable_thinking` and `state.enable_memory`, gate no install step, and are changeable in Settings afterwards. Only the questions were removed: the state fields, their defaults, and the config writer are untouched, so first-run behavior is identical. A test asserts exactly that, because "we removed the toggle" and "we changed the default" would look the same to a user otherwise.

### 2.4 Testing and stabilization (T009)

**What happened**: 12 cases in `test_required_components.py` cover each protocol combination, the uncatalogued id, the empty selection, reason presence, install ordering, and the fold's additivity and idempotence.

Three existing tests in `test_pages_qt.py` asserted the removed checkboxes. They encoded the old contract, so they were rewritten to the new one rather than deleted: the toggles are absent, the derived components land in `components_to_install`, and the two settings defaults are unchanged.

One test I wrote was wrong and was removed rather than forced. `test_required_components_survive_optional_choices` seeded `components_to_install` with `"extension"` and expected it to survive page construction. It does not -- the VS Code sub-page manages that entry itself and drops it when VS Code is not detected, which is pre-existing behavior and nothing to do with this phase. Additivity is a property of `apply_required_components`, so it is tested there directly, where the assertion is actually about the code under test.
