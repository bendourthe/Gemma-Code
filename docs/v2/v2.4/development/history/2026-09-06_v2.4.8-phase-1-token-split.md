## 2. Chronological Steps

### 2.1 Reading the numbers back (T001)

**What happened**: The screenshot's thinking text is 215 bytes. `Math.ceil(215 / 4)` is 54, which is exactly the reasoning figure the tooltip showed. That left 72 as the value Ollama actually reported in `eval_count`, and `eval_count` counts every generated token, thinking included. The sidecar had reported the total as output and then added the estimate on top, so the reasoning tokens were counted twice and the nine-token reply was credited with 72.

The reply text was available at the same call site and unused.

### 2.2 Proportional split (T001)

**What happened**: `turnUsageFromCollected(usage, thinkingText, replyText)` now treats the provider's completion count as the truth for the whole turn:

- An explicit `reasoning_tokens` is subtracted: `output = max(total - reasoning, 0)`. OpenAI's `completion_tokens` includes reasoning, so returning both unchanged was the same double count on the other wire.
- With only a total and non-empty thinking, `reasoning = round(total * thinkBytes / (thinkBytes + replyBytes))` and `output = total - reasoning`, so the two sum to the total exactly and the ratio follows the text.
- No thinking: reasoning null, output equals the total, as before.
- Nothing reported: the bytes/4 estimate survives with null output, byte-for-byte the previous behavior. That is the only case the estimate was written for.

### 2.3 Handler passes the reply (T002)

**What happened**: `chatMessageHandler` already accumulated `thinking`; it now accumulates the visible reply alongside it and passes both to the split on the success and error paths. No protocol field changed, so persisted sessions and the IPC schema are untouched.

### 2.4 Tests (T003)

**What happened**: `desktop/tests/serving-chatCore.test.ts` gained a `v2.4.8 token split` block:

| Case | Expectation |
|---|---|
| Screenshot: 215 thinking bytes, 32 reply bytes, `eval_count: 72` | reasoning 63, output 9, sum 72 |
| Totals 1, 7, 72, 1001 with the same text | parts always sum to the total |
| No thinking, `eval_count: 40` | reasoning null, output 40 |
| Thinking, empty reply, `eval_count: 20` | reasoning 20, output 0 |
| `completion_tokens: 3, reasoning_tokens: 6` | output floored at 0 |
| Nothing reported | reasoning `ceil(215 / 4) = 54`, output null |

The pre-existing fixture paired `eval_count: 4` with `reasoning_tokens: 6`, a combination no real backend emits. It now reads `eval_count: 10, reasoning_tokens: 6`, which yields the same output of 4 by subtraction rather than by coincidence.
