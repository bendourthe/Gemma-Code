# v2.4.1 correction Phase 4 - models, data, and training settings

## Outcome

Phase 4 closes T069-T075. Settings now groups downloaded models first, compatible non-downloaded models second, and incompatible models last. Each group preserves the same required, recommended, release-date, name, and id ordering used by the installer. Archived chats now live inside Data, and the former Fine-tuning surface is an explanatory Training workflow that consumes the desktop's live GPU vendor and VRAM snapshot.

## Shared model ordering

- `core/registry/model-display-order.fixture.json` is consumed by both TypeScript and Python parity tests. It separately records installer recommendation order and Settings availability-group order.
- `settingsModelDisplayOrder` and Python `settings_display_order` use downloaded, compatible, and incompatible buckets, then the canonical installer comparator inside each bucket.
- Models displays subtle `Downloaded`, `Available to download`, and `Incompatible` headings only when the current filtered tab contains more than one group.
- The registry DTO has no model-runtime health field, so this phase does not infer or label a synthetic `Needs repair` state. Installed state remains evidence from the registry probe.

## Data and Training

- The standalone Archived chats Settings tab is removed. Data embeds the existing pillar-grouped archive list and restore workflow; legacy `?tab=archives` and `initialTab="archives"` values migrate to Data.
- Training explains that local QLoRA adapts a supported local model to user examples. Unsupported hosts receive a capability explanation and no training actions.
- The composition root forwards live telemetry GPU vendor and VRAM into Models and Training. While telemetry is unresolved, Training says `Detecting training hardware...` and never displays a fabricated `0 GB` capability.
- The `tuning.status` and `tuning.provision` contracts accept that verified snapshot, so the sidecar hardware gate and provisioner evaluate the same host facts shown in the desktop.
