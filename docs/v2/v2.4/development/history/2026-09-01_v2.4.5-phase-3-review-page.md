## 2. Chronological Steps

### 2.1 Two-column model list (T010)

**What happened**: `_rebuild_summary` built the list as a `<br>`-joined run in a single label, which wasted the pane's horizontal space and pushed a 14-model selection well past the fold. It now renders an HTML table with two 50%-width cells per row.

The split is down the middle rather than alternating, so each column reads top-to-bottom in `_ordered_selection` order - the order the engine will actually install them. Alternating would have interleaved the sections. An odd count leaves one trailing empty cell, which a test pins.

The existing `_restack_columns` narrow-width behavior is untouched: below 560px the whole facts/models split still stacks, and the table simply becomes narrower.

### 2.2 Per-model marks (T011)

**What happened**: Each row is prefixed with a check for a downloaded model and a down-arrow for a pending one. The check reuses the `SUCCESS`-colored mark the component list already uses, so the page keeps one visual language, and the two glyphs differ in shape rather than only in color. A one-line legend sits above the list so the marks explain themselves rather than needing a manual.

An id missing from the report renders as pending, never unmarked, which is the conservative reading.

### 2.3 Pending-only estimate under the models (T012)

**What happened**: `Estimated disk usage` moved out of `facts_html` (the left column, beside install path and GPU) into the model column, directly under the list. It is a statement about the models, so it belongs with them.

The number changed meaning: it is now `pending_gb + 2 GB` overhead rather than `selection_gb + 2 GB`. The install-time heuristic keys off pending too, with a new "under 5 minutes" band, because a download of zero is not a 10-15 minute install.

Both numbers are shown. Displaying only "~2 GB" after the operator selected 194 GB would invite the opposite worry - that the selection had been silently dropped - so the already-downloaded total is stated beside the estimate, and the header gains an "N already downloaded, M to download" suffix when any are present.

**One correctness gap surfaced through an existing test.** `test_multi_selection_summary` sets `selected_models_gb` with no installed-report, and initially produced a "~2 GB" estimate: an empty report was being read as "nothing left to download". That is wrong for every path that never opens the picker, including the headless `--model` override. An unpopulated report means *unknown*, and the safe reading of unknown is "assume nothing is present" - the pre-v2.4.5 behavior. The page now falls back to `selected_models_gb` when the report has neither downloaded nor pending entries, and a test pins that. This was a real defect the test caught, not a test that needed loosening.

That same existing test also asserted the old header format `(~9.6 GB download)`. Since the size deliberately moved under the list, the assertion was rewritten to the new contract rather than preserved.
