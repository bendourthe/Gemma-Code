## 2. Chronological Steps

### 2.1 Job worker and heartbeats (T018)

**What happened**: `main.dispatch` called each handler to completion and only then returned to the `for raw in sys.stdin` loop. A Wan run is minutes of CUDA work inside that call, so for those minutes the runtime read nothing: `health`, a cancel, and every other request queued behind the job. From the outside, a runtime that is working correctly and a runtime that has died look identical.

The fix keeps the wire contract exactly as it was. A new `serve(stream, handlers)` owns the loop and, for any method outside `CONTROL_METHODS`, hands the line to a worker thread instead of running it inline. JSON-RPC correlates responses by `id`, so answering out of order is not a protocol change - it is what the protocol is for. `health` and `version` stay on the reader thread deliberately: they are microsecond lookups and they are the question "are you alive", which is precisely the question that must not queue behind the work being asked about.

Three details that are easy to get wrong and are handled explicitly. `_emit` now takes a lock, because two threads writing line-delimited JSON concurrently can interleave into one unparseable line and take the channel down permanently. A malformed line has no method to route on, so it stays on the inline path and produces the same parse error it always did. And when stdin closes, `serve` joins outstanding workers rather than returning immediately, so a job the caller is still waiting on is not truncated at end of input.

`heartbeat_while` emits a `progress` notification every two seconds for the life of a job. Diffusers exposes no step callback on every pipeline used here, so this is a liveness signal rather than a percentage - it carries `jobId`, `method`, and elapsed seconds. It is a notification (no `id`), so nothing is waiting on it and an ignoring client is unaffected.

**Scope note**: the plan also described changing the accept to return a bare `jobId` before the work finishes. That already exists one layer up - `enqueueInteractive` in the Node sidecar returns a job envelope immediately and the UI polls `drainEvents`. Adding a second job protocol inside Python would have duplicated it. The actual defect was the blocked reader, and that is what changed.

### 2.2 UI stays pending and alive (T019)

**What happened**: The pending path was inspected rather than modified. `patchMessage` clears `pending` only on a completion carrying usable bytes or on an error, and the empty-media case already writes a failure sentence rather than a silent success - the v2.4.2 honesty gate this plan does not reopen. `data-orb-paused` is driven by reduced-motion, visibility, and the motion budget, never by job state, so the orb keeps animating for the whole job. A test now pins that for a pending video message, since a paused orb is indistinguishable from a frozen shell.

GPU headroom was left alone. `workingMemReserveGB` and the offload strategy are existing knobs, and lowering quality on a 16 GB host to buy compositor VRAM is a product decision this phase has no evidence to make. Whether the packaged freeze is fully explained by the blocked reader or partly by compositor starvation is an operator observation, recorded as a known issue rather than guessed at here.

### 2.3 Studio caption pool (T020)

**What happened**: Image and Video pending showed one static "Shaping...", which during a multi-minute job reads as a stuck word rather than progress. `STUDIO_PENDING_CAPTIONS` (Creating / Crafting / Generating) and `useStudioCaptionRotator` mirror the chat rotator exactly - shuffled once per bubble, same interval, first caption under reduced motion - and `isStudioActivity` selects the pool. Both hooks are called unconditionally in `AgentStateOrb` to satisfy the hooks rule; only one result is read. The chat pool is untouched, because its words describe reasoning and these describe rendering. `mapping.ts` keeps `label: "Shaping"` for the `shaping` engine state, which drives the particle grammar and is not user-visible text.

### 2.4 Testing and stabilization (T021)

**What happened**: `tests/python/diffusion/test_main_liveness.py` drives `serve` with a fake slow handler. The load-bearing case holds a job inside its handler, sends `health`, and asserts a `result` for it comes back before the job is released - which fails against the old inline dispatcher, since the reader would not have reached the second line. A first draft of that test asserted only that both events had been set; it would have passed against the old code too, so it was deleted rather than kept as reassurance. The rest cover the control-method split, heartbeat shape and stop, the unchanged parse error, and the end-of-input join.

Five desktop cases pin the studio pool: its exact contents, that image and video draw from it and never the chat pool, that the chat pool is unchanged, that a shuffle is a permutation, and that a pending studio orb reports `data-orb-paused="false"`.

Five existing tests asserted the literal string "Shaping..." and were updated to the pool. One of them also asserted `queryByText("Generating...")` was null, meaning "no second status label beside the orb"; since "Generating..." is now one of the orb's own captions, that assertion was rewritten against the composer rather than deleted.

## 5. Plan Discrepancies

- The plan asked for a Python-side accept returning a bare `jobId` before the work finishes. That contract already exists in the Node sidecar (`enqueueInteractive` plus `drainEvents`), so implementing it again in Python would have added a second job protocol without fixing anything. The blocked reader was the real defect and is what changed; the JSON-RPC request and response shapes are unchanged.
- The plan suggested documenting a GPU headroom choice. No headroom value was changed, so there is nothing to document; the open question is recorded as a known issue instead.

---

## 6. Assumptions Made

- Threads, not processes, are sufficient. The blocking call is CUDA work inside PyTorch, which releases the GIL, so a worker thread genuinely lets the reader run.
- Concurrent GPU jobs remain serialized by the existing GpuScheduler upstream; this phase does not add parallelism to the GPU itself, only to the reader.
