## 2. Chronological Steps

### 2.1 Selection-scoped sizes on state (T001)

**What happened**: The contradiction in the screenshot had one cause. The picker probes the whole catalog:

```python
selection=list(self._catalog)   # every model, not the selection
```

That is correct and must stay: every card needs to know whether to show a Downloaded pill, including cards the user has not selected. The consequence is that the report's `pending_gb` means "every un-downloaded model in the catalog" (157 GB) and `downloaded_gb` means "every downloaded one" (233.2 GB). Those are not selection sizes, and three places were reading them as if they were.

`_update_selection_state` now computes the pending total over the selection and writes `state.pending_models_gb` in the same block that writes `selected_models_gb`, so the two cannot drift. `InstallerState.pending_models_gb` was declared in v2.4.5 and never written; it is now the single selection-scoped figure.

The probe's `selection` argument is deliberately unchanged.

### 2.2 Consumers read the scoped figure (T002, T003)

**What happened**: Three consumers moved, and finding the third was the point of the exercise.

`pending_download_gb` returns `state.pending_models_gb`, keeping its unknown-report fallback intact: a report the probe never populated still falls back to the whole selection, because the safe reading of unknown remains "assume nothing is present". That path matters for the headless `--model` override, which never opens the picker.

`review.py` calls the same helper rather than reading the report, and derives the already-downloaded total as `selected_models_gb - pending`. Routing Review through the guard's own helper means the card and the gate cannot disagree by construction.

`InstallerState.can_select_model` was the third, and it was found by a test rather than by reading. It credited back `installed_report.downloaded_gb` - catalog-wide - so a host with a large downloaded catalog could offset an arbitrarily large selection and the picker would accept anything. It now subtracts the scoped pending figure directly.

### 2.3 Testing and stabilization (T004)

**What happened**: Four existing v2.4.5 tests failed immediately, and that failure is the whole story of this phase. Their fixtures set report sizes but never the state field, because when they were written the report *was* the source of truth. More importantly, every one of them built a report covering exactly the selection - so catalog-wide and selection-scoped values coincided, and the defect was invisible to a green suite through two releases.

Both fixture helpers were rewritten so the report is deliberately catalog-wide: it carries extra ids and sizes 500 GB larger than the selection. Any consumer that reverts to `report.pending_gb` now fails loudly instead of passing by coincidence.

`test_selection_scoped_sizing.py` adds 13 cases on that same property. The load-bearing ones:

- `test_returns_the_selection_scoped_figure_not_the_catalog_one` asserts the report's own `pending_gb` is 175.0 and the helper returns 18.0, so the two are pinned apart.
- `test_the_catalog_figure_refuses_a_host_the_truth_would_allow` evaluates the guard twice at 100 GB free - once with the truth (allowed) and once with the catalog figure (refused).
- `test_a_large_downloaded_catalog_does_not_offset_the_selection` covers the `can_select_model` regression.
- `test_counts_and_sizes_agree` asserts the screenshot's contradiction directly: if the card says `0 to download`, the size must say `~2 GB`.

Two of my own new tests failed first and both were my error, not the code's. `test_reading_the_catalog_figure_would_have_refused_it` assumed the bad number would refuse the operator's host; it does not - 157 + 10 fits in 201.7, which is precisely why the wizard reached Review at all. The test now evaluates both numbers at 100 GB free and asserts they disagree, which is the honest claim. The second had an incoherent fixture: it declared zero pending while leaving a selected id out of the `downloaded` set, so the per-id counts contradicted the sizes for a reason unrelated to the defect. The helper now derives set membership from the pending size.

## 6. Assumptions Made

- A selected id absent from the catalog contributes 0 GB to the pending total. It routes to `ollama pull` verbatim and the catalog has no size for it, which is the pre-existing behavior for `selected_models_gb` too.
