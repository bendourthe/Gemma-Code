**Goal**: Before v2.4.1 is released, a clean or repair installation on a supported Windows NVIDIA host must recover safely from interrupted runtime work and produce one valid local image and one valid local video from the packaged application; the installer and desktop must then present truthful, compact, and consistent authorization, warnings, model ordering, transcript metadata, archived data, training capability, and Agents workspace controls.

## Overview

This is a corrective continuation of the completed [v2.4.1 field-reliability plan](v2.4.1-field-reliability-chat-archives-models-workspaces.md), not a rewrite of its T001-T047 evidence. The latest field run proves that the desktop and selected models install, but it also exposes a release-blocking runtime invariant: `runtime.json` remains in `repairing` with `REPAIR_BUSY`, while the lock file contains PID `18096` and no such process is alive. The current PID-only exclusive file has no owner start-time validation or stale-lease reclamation, so an interrupted installer can disable image and video generation indefinitely while falsely claiming another repair is active.

The same log proves that the repeated `Could not update the installer window.` messages are not download failures. All selected models completed, but background model callbacks enqueue work back to the `InstallEngine` thread while its synchronous `run()` method is occupying that thread. Failed UI marshalling is then written into `model_failures`, turning a telemetry defect into misleading product warnings.

The Hugging Face 404 is catalog drift. `sana-1.6b-int4` points to a removed repository and is marked gated, while the maintained INT4 repository `nunchaku-ai/nunchaku-sana` is public and contains `svdq-int4_r32-sana1.6b.safetensors`. That model should not ask for authorization. A clearer guided flow is still required for genuinely gated repositories and must derive its steps from live, build-validated catalog metadata.

Desktop issues share two causes: policy is duplicated or applied at the wrong layer, and request-level telemetry is displayed as if it belonged to one message. Model Settings does not partition downloaded rows ahead of compatible catalog rows. Assistant token chrome adds request prompt tokens, estimated reasoning, and backend completion totals even when those totals include hidden reasoning. The plan separates durable contracts first, then changes presentation.

## Goals First

**Target problem**: Repeated v2.4.x iterations have not produced a single image or video on the field host, while several screens report misleading readiness, warnings, ordering, and token details that make it difficult to distinguish a real failure from a display defect.

**Target persona**: A privacy-focused Windows user with a consumer NVIDIA GPU who expects a local installer and desktop application to work without manual runtime archaeology, while retaining honest degraded behavior on unsupported hosts.

**Observable definition of done**:

- A dead or reused repair-lock owner is detected and reclaimed safely; a genuinely live repair remains mutually exclusive.
- `runtime.json` transitions atomically through explicit states and cannot remain `repairing` after its owner exits without a recoverable diagnostic.
- The packaged installer repairs the field host's stale state and the packaged desktop generates a decodable PNG and a playable video using installed local models.
- Image proof records dimensions, format, non-zero pixels, and SHA-256; video proof records codec, duration, frame count, dimensions, and SHA-256 through `ffprobe` or an equivalent local parser.
- The installer never calls the run successful when a selected media capability is unavailable; it offers a bounded repair/retry path with the actual failure code.
- Successful model downloads cannot become failures because a UI progress callback was missed.
- Warning summaries use warning color and icons, distinguish required failures, optional skips, and telemetry notices, and never show internal marshalling language to users.
- SANA uses a working, pinned, public repository and does not open an authorization dialog. Every genuinely gated row passes an automated repository/access-page preflight before packaging.
- The gated dialog is a numbered flow: optional free account creation, required license authorization, required sign-in, then a prominent monospace device code with Copy and accessible status.
- Settings Models groups downloaded and ready rows first, compatible not-downloaded rows second, and incompatible rows last; each group uses the same recommendation and tie-break ordering as the installer.
- Archived chats are inside Settings > Data. Fine-tuning is not a dead top-level tab: eligible hosts see an actionable Training surface; unsupported or unprobed hosts get an honest capability state without a fake `0 GB` reading.
- User bubble metadata shows only that message's input-token count and no hover-only breakdown. Assistant bubble metadata shows reasoning plus visible output only; request/context input remains available in Activity telemetry, not the bubble.
- Token counts are tokenizer-backed when the runtime supports it; estimates are explicitly labelled and never presented as exact. The supplied reasoning and final-response fixture produces counts consistent with the visible text.
- Time and token total render inside each bubble above the text. The pending animation has a safe left inset and no enclosing message bubble. Plain message clicks do not open a duplicate right panel.
- Agents resolves its initial model from the installed recommendation snapshot before presenting a selection, places workspace folders and Chat/Memory/Activity in one compact row, and renders session history beneath that row in the same main pane.
- Chat, Memory, and Activity remain only when they have actionable content and include concise purpose text; unknown legacy tab ids fall back to Chat.

**Success metrics**:

- Zero stale-lock false positives across dead PID, reused PID, malformed lease, crash, cancel, and genuine concurrent-repair fixtures.
- Zero successful model installs classified as failed because of UI telemetry.
- 100% catalog URL/file preflight success for every selectable Hugging Face row in the release artifact.
- 100% Python/TypeScript ordering parity over installed, compatible, incompatible, recommendation, date, and name fixtures.
- Exact role-correct token display in protocol, persistence, hydration, and UI tests.
- One observed packaged PNG and one observed packaged video on the target host before publication.

**Strategy grounding**: No `STRATEGY.md` or version constitution was found. The plan follows the repository's local-first product identity, truthful evidence tiers, module authorship contract, and rule against generation-as-a-service. No `docs/solutions/` entry was found for the stale repair lease or token-provenance issue.

## Architecture Decisions

1. **Owner-aware repair lease**: Replace the PID-only sentinel with a versioned JSON lease containing PID, process start identity, creation time, host/boot identity when available, target environment, and nonce. Reclaim only after proving the owner is absent or mismatched. Never delete a lock based only on age.
2. **Atomic runtime state machine**: `unavailable -> repairing -> ready | failed` is written atomically with lease identity, attempt id, timestamps, smoke evidence, and actionable failure code. Startup reconciles a stale `repairing` record before the UI consumes it.
3. **Packaged artifact proof is the release bar**: Unit and mock-CUDA tests are necessary but insufficient. The release remains blocked until the exact installer and installed desktop produce validated local image and video artifacts on the field host.
4. **Catalog access is build-validated data**: Hugging Face repository, revision, exact file paths, license, and gated status are checked by a read-only preflight. A public repository never opens the gated dialog. A missing or 404 row is not selectable in a release build.
5. **UI telemetry cannot determine install outcome**: Download/install result is owned by the model worker result. Qt signals report progress only. Missed visual updates may produce a diagnostic log entry, never `failed_models`.
6. **One model rank tuple**: Settings rank is `(availability bucket, recommendation rank, release date descending, folded display name, id)`. Installer rank omits only the availability bucket and uses the identical remaining tuple and shared fixture.
7. **Message usage is role-local**: User messages own visible input tokens. Assistant messages own visible reasoning and visible answer tokens. Request prompt/context totals live in turn telemetry and Activity. Estimated values carry provenance and never masquerade as exact counts.
8. **One-pane Agents composition**: The workspace control, tabs, history, and active tab content share the main pane. History is a collapsible section below the header, not a second permanent rail.
9. **Capability-aware Training surface**: Fine-tuning is renamed to Training. It is shown in primary Settings navigation only when hardware detection is valid and the host is eligible or the user enables advanced capabilities. Unknown hardware is `Detecting` or `Unavailable`, never `0 GB`.

## Phase 1: Installer Transaction Integrity and Repair Lease

**Goal**: Make interrupted diffusion repair self-healing and keep UI telemetry failures from changing installation results.
**Prerequisites**: Preserve copies of the field `runtime.json`, stale lock, and installer log as sanitized test fixtures; retain the current installed environment until the reproduction is captured.
**Stability Gate**: A dead or reused lease owner is reclaimed; a live owner is not; runtime state reaches one terminal value per attempt; successful model results remain successful even if every UI callback is dropped.
**Recommended model tier**: frontier
**Recommended effort level**: max
**Rationale**: Cross-process ownership, crash recovery, atomic state, and Qt threading are release-critical concurrency boundaries.

### 1.1 - Field reproduction contract (T049)

**Objective**: Turn the exact stale `REPAIR_BUSY` field state into deterministic regressions.

**Prompt**:
> Add sanitized fixtures for a stale PID-only lock, a versioned lease whose PID is dead, a PID reused by a different process start identity, a malformed lease, and a genuinely live owner. Reproduce startup reconciliation and an interrupted installer between `repairing` and `ready`. Assert current behavior fails for the stale cases before changing production code.

**Failure modes**: Missing or malformed fixtures fail loudly; slow process inspection is bounded; tests never terminate unrelated processes and use child processes created by the fixture only.

### 1.2 - Owner-aware repair lease (T050)

**Objective**: Replace the permanent exclusive sentinel with safe mutual exclusion and stale-owner recovery.

**Prompt**:
> Replace `environment_lock` with a versioned JSON lease written through exclusive create and flushed before work begins. Record PID, process start identity, creation time, target path, attempt id, and random nonce; include boot/host identity where the platform exposes it. On collision, read and validate the lease, verify both PID and start identity, and reclaim only when the owner is absent or mismatched. Use compare-before-delete so one process cannot remove another process's replacement lease. Preserve a bounded wait for a confirmed live owner and remove the lease in `finally` only when nonce ownership still matches.

**Failure modes**: Malformed leases are quarantined with a diagnostic and replaced atomically; process-inspection denial returns an actionable `REPAIR_OWNER_UNKNOWN` without deletion; concurrent stale reclaim has one winner; cancel/crash cannot delete a newer owner's lease.

### 1.3 - Atomic runtime-state reconciliation (T051)

**Objective**: Ensure installer and sidecar see one truthful repair state.

**Prompt**:
> Version the runtime contract and write it by temp-file plus atomic replace. Persist attempt id, lease nonce, owner identity, state, timestamps, component readiness, and smoke evidence. On installer or sidecar startup, reconcile `repairing`: if the matching owner is live, report busy; if stale, move to a recoverable failed state and allow a new repair; if the environment already passes smoke, promote to ready. Never persist `diffusionPython: null` with a ready media capability.

**Failure modes**: Truncated JSON preserves the last valid backup and reports `RUNTIME_CONTRACT_INVALID`; slow smoke checks time out; concurrent readers never observe a partially written file; stale attempts cannot overwrite a newer terminal result.

### 1.4 - Qt result/telemetry separation (T052)

**Objective**: Stop dropped progress notifications from creating fake model failures.

**Prompt**:
> Replace `QMetaObject.invokeMethod(self, ..., QueuedConnection)` callbacks targeting the blocked engine thread with a dedicated QObject signal bridge whose receiver lives on the GUI thread, or emit thread-safe Qt signals directly from workers. Model completion/failure state must be committed exactly once from the worker result before UI delivery. A missed progress render logs an internal diagnostic only; it never writes `model_failures`, `failed_models`, or completion warnings.

**Failure modes**: Malformed worker events are rejected without changing a prior terminal result; a closed window drops telemetry safely; simultaneous cancel/completion resolves once; high-frequency progress is coalesced without losing terminal events.

### 1.5 - Concurrency and crash regression suite (T053)

**Objective**: Prove lease ownership, state transitions, and model result integrity under adverse timing.

**Prompt**:
> Add process-level and Qt tests for dead owner, reused PID, malformed lease, live owner timeout, two reclaimers, crash before cleanup, cancel during repair, stale contract with ready environment, UI receiver destruction, 100 parallel model completions, and delayed progress after completion. Assert no fake `Could not update the installer window.` user outcome remains.

### 1.6 - Testing and Stabilization (T054)

**Prompt**:
> Run focused installer process/Qt tests, Ruff, typing for touched modules, and a local repair smoke against a disposable environment. Record commands, counts, support tier, and CI IMPACT in `docs/v2/v2.4/development/history/2026-08-30_v2.4.1-correction-phase-1-runtime-integrity.md`. Create one local ASCII-only commit. Do not push or start remote CI.

## Phase 3: Working Image and Video Generation

**Goal**: Make the installed media stack produce real, validated output and provide a recoverable user path when readiness fails.
**Prerequisites**: Phases 1-2, pinned media manifests, and a disposable test generation directory.
**Stability Gate**: Automated installed-contract tests pass; on the target packaged Windows host, the exact installed desktop creates one validated PNG and one validated video after clean or repair setup. Failure to obtain both blocks publication and cannot be deferred as a cosmetic known gap.
**Recommended model tier**: frontier
**Recommended effort level**: max
**Rationale**: CUDA/Python ABI compatibility, multi-gigabyte manifests, sidecar process lifecycle, media encoding, cancellation, and packaged hardware behavior form the highest-risk release path.

### 3.1 - One readiness and repair API (T062)

**Objective**: Give Image Studio and Video Lab the same truthful runtime contract.

**Prompt**:
> Add a sidecar media-runtime service that reads and reconciles the versioned installer contract, validates executable and manifest paths, exposes typed `ready`, `repairable`, `repairing`, and `failed` states, and launches one bounded repair attempt through the installed provisioner. Image and Video handlers must consume this service instead of interpreting files independently. Return actionable codes and progress; do not tell the user to rerun the entire installer when an in-place repair is safe.

## Phase 5: Transcript Layout and Token Provenance

**Goal**: Make transcript chrome compact and trustworthy by displaying only the tokens attributable to each visible message.
**Prerequisites**: Existing separate `reasoningText`, token fields, session persistence, and shared MessageBubble.
**Stability Gate**: The supplied `Hi`/reasoning/answer fixture produces role-correct counts; time/tokens are inside the bubble above content; pending status is fully visible; plain messages have no selection/preview behavior.
**Recommended model tier**: frontier
**Recommended effort level**: high
**Rationale**: Protocol and persistence compatibility plus provider-specific usage semantics make this more than a visual adjustment.

### 5.1 - Request versus message usage schema (T076)

**Objective**: Stop attaching context-window prompt tokens to the assistant message.

**Prompt**:
> Version the chat protocol and persistence so a turn records request usage separately from message usage. Request usage may contain system, history, attachment, cache, and current-user prompt totals for Activity analytics. User message usage contains only tokens for that user message. Assistant message usage contains reasoning and visible answer tokens only, plus provenance (`provider`, `tokenizer`, `exact|estimated`, raw counters). Migrate older rows without rewriting their uncertain totals as exact.

**Failure modes**: Missing/malformed usage omits chrome; older cumulative totals retain a legacy/estimated marker; slow tokenizer work cannot block streaming text; concurrent chunks merge monotonically by turn id.

### 5.2 - Honest token accounting (T077)

**Objective**: Count the text actually displayed and explain unavoidable estimates.

**Prompt**:
> Prefer runtime/provider tokenizer counts for current user text, emitted reasoning text, and visible final output. When the backend reports only cumulative `prompt_eval_count`/`eval_count`, retain those as request telemetry and separately tokenize the split reasoning/output text. If no tokenizer is available, estimate each visible segment independently, set `tokensEstimated=true`, and use copy that says `estimated`. Never derive reasoning from byte length while displaying it as exact, and never include reasoning tokens again in visible output.

**Failure modes**: Unicode, emoji, empty output, missing reasoning, streaming revisions, provider totals that include reasoning, and tokenizer failure preserve text and mark usage unavailable/estimated honestly.

### 5.3 - Metadata inside bubbles (T078)

**Objective**: Put the time and discrete token label above text inside each bubble.

**Prompt**:
> Move `BubbleMeta` to the top of the `<article>` before content. Keep time left and italic `(X tokens)` right. For user messages, total equals only user input and has no title, hover breakdown, or focus stop. For assistant messages, total equals reasoning plus visible output; hover/focus detail lists only those two fields and whether either is estimated. Keep reasoning disclosure collapsed above the assistant bubble and do not count request input in its label.

**Failure modes**: Missing time or tokens leaves the other aligned; one-token grammar remains correct; narrow bubbles wrap metadata without overlapping text; assistive names do not duplicate visible content.

### 5.4 - Remove redundant message preview (T079)

**Objective**: Stop ordinary clicks from opening a duplicate right panel.

**Prompt**:
> Remove `onSelectMessage`, plain-message button semantics, selected preview state, and the ChatPage `PreviewPane` path for text messages. Preserve explicit media click-to-lightbox, fullscreen/download/copy, and any true file/artifact preview opened by a dedicated action. Delete obsolete tests or components only when no other surface consumes them.

**Failure modes**: Links, code selection, and reasoning disclosure remain clickable without opening a panel; media clicks open one lightbox; keyboard focus no longer lands on the whole bubble.

### 5.5 - Uncropped pending status (T080)

**Objective**: Keep the no-bubble generation animation fully inside the transcript at every pane width.

**Prompt**:
> Add a dedicated assistant status lane with at least one spacing token of left inset, `box-sizing: border-box`, safe overflow, and a bounded max width. Keep the orb/pill background owned only by the status component and no article/bubble wrapper. Verify collapsed history, expanded history, narrow window, 100-200% zoom, and reduced motion. Do not center the status like media generation.

**Failure modes**: Long localized captions truncate or wrap without clipping the orb; reduced motion retains a visible static state; rapid pending-to-answer transition does not shift the transcript horizontally.

### 5.6 - Transcript regression suite (T081)

**Objective**: Pin the user's exact example and message interaction contract.

**Prompt**:
> Add a fixture with user `Hi`, the supplied reasoning text, and final `Hello! How can I help you today?`. Assert user-only input metadata, assistant reasoning/output total, tokenizer or explicit estimated provenance, exact absence of assistant input in the tooltip, metadata position inside article, reasoning collapsed by default, no whole-message button, no PreviewPane, and non-negative bounding rectangles for the pending orb at narrow widths.
