**Field evidence**: Packaged v2.4.6 installer, operator screenshots 1-4 (2026-09-06). Screenshot 3 shows the Review page reporting `Models: 7 selected (7 already downloaded, 0 to download)` beside `Estimated disk usage: ~157 GB to download / 233.2 GB already downloaded` -- two mutually exclusive claims on one card. Screenshots 1, 2 and 4 are layout and scope feedback on Install Path, Configuration, and Review.
**Goal**: The installer states one consistent size for a selection, asks only the questions a user can meaningfully answer, and presents Install Path, Configuration and Review at a density that fits the window. The Review estimate and the disk guard both size the selected models rather than the whole catalog; the Configuration step drops preference toggles that are not install decisions and derives the components a selection requires; Install Path uses its full width with Browse inside the field; and Review presents a model summary with counters, category chips, and a single-line storage figure.

## Overview

v2.4.6 shipped and merged (PR 62, 42 checks green, `8499c05d`). Field-testing its installer produced four screenshots. Three are density and scope feedback. One is a defect, and it is a defect this project introduced in v2.4.5.

**The defect.** The Review card claims `7 already downloaded, 0 to download` and `~157 GB to download` at the same time. The counts are computed per id in `review.py` against `installed_report.is_downloaded`, so they are scoped to the selection and correct. The sizes are read straight off `installed_report.pending_gb` and `downloaded_gb`, which are **catalog-wide**, because the picker deliberately probes every catalog entry:

```python
# typed_catalog.py:1188
report = probe_installed_models(
    selection=list(self._catalog),   # every model, not the selection
    ...
)
```

Probing the whole catalog is correct -- every card needs to know whether to show its Downloaded pill. Reading that report's *sizes* as if they described the selection is not. `~157 GB` is every un-downloaded catalog model; `233.2 GB` is every downloaded one.

This is not confined to the Review text. `pending_download_gb` returns the same catalog-wide `report.pending_gb`, and that value feeds the install guard, the picker footer, and `can_select_model`. The guard is therefore demanding headroom for models the user did not select. The operator had 201.7 GB free so it passed; with less free space it would have refused an install that downloads nothing, which is the exact v2.4.5 defect wearing a different mask.

v2.4.5's tests missed it because every fixture built a report whose `downloaded`/`pending` sets matched the selection, so catalog-wide and selection-scoped sizes coincided. A fixture with a catalog wider than the selection is the missing case.

`InstallerState.pending_models_gb` was declared in v2.4.5 and never written. It is the correct home for the selection-scoped figure.

**The scope question.** The operator asked whether all eight Configuration options are needed. They are not, and two of them are not install decisions at all. Tracing what each gates:

| Option | What it gates | Verdict |
|---|---|---|
| Install Ollama | Every `ollama`-protocol model (all chat/agentic) | Load-bearing |
| Create Python virtual environment | The diffusion runtime for every Image/Video/Audio model | Load-bearing |
| Install the Nexus desktop app | The product itself | Load-bearing |
| Add Start Menu shortcut | A shortcut | Optional |
| Replace the VS Code extension | The extension install | Optional |
| Install Unsloth Core | QLoRA fine-tuning runtime; already opt-in and VRAM-gated | Optional |
| Enable thinking mode | `state.enable_thinking` -- a config value, no install step | **Not an install decision** |
| Enable persistent memory | `state.enable_memory` -- a config value, no install step | **Not an install decision** |

Unchecking a load-bearing component silently breaks models the user selected two steps earlier, and the wizard says nothing. The two settings toggles ask about runtime preferences at the worst possible moment and are changeable in Settings afterwards.

This plan derives the three load-bearing components from the model selection and presents them as a "will be installed" list, drops the two settings toggles, and leaves the three genuine choices as choices.

This is a v2.4 cycle on a new branch off `develop` at `8499c05d`. It does not reopen the v2.4.6 delivery, density, or session-identity work. Nothing in the 2.4 series is released; the package version stays 2.4.1 and no version bump belongs to this plan.

No phase except the last pushes, opens a pull request, or starts remote CI. Each earlier phase ends with automated tests, session history, and one local commit. The final phase rebuilds the installer so the operator can field-test it.

Discovery interview: skipped as a live questionnaire. The operator supplied four annotated screenshots, a target mockup, and an explicit scope question in one message, and approved the recommendation that answered it. Assumptions are listed under Architecture Decisions.

## Goals First

**Target problem**: The installer reports two contradictory sizes for one selection and sizes its disk guard from the wrong one; it asks eight configuration questions of which two are not install decisions and three are load-bearing enough that answering them wrongly breaks the install; and three wizard pages waste horizontal space.

**Target persona**: The operator re-running the packaged installer on the same Windows / NVIDIA host across plan cycles (RTX 3080 Ti Laptop, 16 GB VRAM, ~200 GB free), who has most models already downloaded and needs the wizard to be both correct and quick to read.

**Observable definition of done**:

- With 7 models selected and all 7 already on disk, the Review card reads `0 to download` **and** an estimated download of ~2 GB (overhead only). The two figures never disagree.
- With a catalog wider than the selection, `pending_download_gb` returns the size of the un-downloaded **selected** models, not of the un-downloaded catalog.
- The install guard, the picker footer, and `can_select_model` all use that same selection-scoped figure.
- Estimated installation time is derived from the selection-scoped pending size, so an all-downloaded selection does not read as a 10-15 minute install.
- Install Path: the field spans the full page width and Browse sits inside it.
- Configuration: "Enable thinking mode" and "Enable persistent memory" are gone from the installer. Ollama, Python environment, and desktop app appear as a derived "will be installed" list, not as checkboxes. The VS Code extension, Start Menu shortcut, and Unsloth remain user choices.
- Configuration: the Ollama URL field sits in the left column at single-column width, directly beneath the Ollama row, with no separate "Ollama URL" heading. The blue VS Code detection paragraph is gone.
- Review: install path, components, GPU, estimated storage and estimated installation time occupy the left column. Estimated storage renders on one line.
- Review: the model summary is visually distinct from the per-category lists -- counters for selected / ready / to download, and category chips -- per the screenshot 4 mockup.
- A user whose selection needs Ollama is told so; the wizard never silently installs a chat model with no runtime to serve it.

## Architecture Decisions

1. **The probe keeps its catalog-wide scope; the sizes become selection-scoped at the point of use.** Narrowing the probe to the selection would break the picker, which needs a Downloaded pill on every card including unselected ones. The report's `downloaded` and `pending` sets stay catalog-wide and remain correct for that job. What changes is that nothing reads `report.pending_gb` as a selection size.

2. **`InstallerState.pending_models_gb` becomes the single selection-scoped figure.** It already exists and is dead. The picker computes it in `_update_selection_state`, which is the one place that already knows both the selection and the per-model sizes, and writes both it and `selected_models_gb` together so they cannot drift.

3. **`pending_download_gb` reads the state field, not the report.** Its unknown-report fallback is unchanged: a report the probe never populated still falls back to the full selection total, because the safe reading of unknown remains "assume nothing is present".

4. **The regression test uses a catalog wider than the selection.** That single property is what v2.4.5's fixtures lacked. Every new sizing test builds a report covering more models than the user selected, so catalog-wide and selection-scoped values are forced apart and a reversion cannot pass.

5. **Load-bearing components are derived, not asked.** `requires_ollama(selection)` and `requires_python_env(selection)` resolve from each selected model's protocol and type, and the desktop app is always installed. They render as a read-only "Will be installed" list with a one-line reason each. This removes the failure mode where unchecking a box two steps after picking a model breaks that model with no warning. The engine contract is untouched: `components_to_install` is still the list the installer executes; it is now populated from the selection instead of from checkboxes.

6. **The two settings toggles leave the installer entirely.** `enable_thinking` and `enable_memory` gate no install step. Their state fields and their defaults stay exactly as they are, so first-run behavior does not change and the app's Settings surface still owns them. Only the installer's questions go.

7. **Unsloth, the VS Code extension, and the shortcut stay checkboxes.** Each is a genuine choice with a real cost the user may decline, and none of them breaks a selected model when unchecked.

8. **Review's left column carries the facts; the right column carries the models.** Estimated storage and installation time move left because they are install facts alongside path, components and GPU. Storage renders on one line, with the already-downloaded total as secondary text rather than a second full-width row.

9. **The model summary gets its own visual level.** Screenshot 4's mockup is the target: a counter row (selected / ready / to download) reading as a summary, then category chips. The chips reuse the existing category vocabulary; nothing new is invented. This is styling over the same data the page already renders, so it carries no new state.

10. **Install-time heuristic keys off the corrected pending size.** With the size bug fixed, the existing "under 5 minutes" band finally fires for an all-downloaded selection, which is what screenshot 3's `10-15 minutes` got wrong.

## Phase 1: Selection-Scoped Sizing

**Goal**: One number describes a selection, and every consumer reads it.
**Prerequisites**: None.
**Stability Gate**: Tests built on a catalog wider than the selection prove `pending_download_gb`, the Review estimate, the picker footer and `can_select_model` all report selection-scoped sizes, and that the guard neither over-refuses nor under-refuses.
**Recommended model tier**: frontier
**Recommended effort level**: max
**Rationale**: This is a correctness defect in the gate that decides whether an install may start, and the previous fix for the same symptom was itself incomplete.

### Sub-tasks

#### 1.1 - Selection-scoped sizes on state

**Objective**: The picker publishes `pending_models_gb` alongside `selected_models_gb`.

**Failure modes**: A selected id absent from the catalog contributes 0 and must not raise. The two fields must be written together so they cannot disagree. `installed_report` keeps its catalog-wide sets, since the picker's pills depend on them.

**Prompt**:
> In `_update_selection_state`, compute the pending total as the sum of `size_gb` for selected ids not in `installed_report.downloaded`, and assign `state.pending_models_gb` in the same statement group that assigns `state.selected_models_gb`. Do not narrow the probe's `selection` argument; the picker needs the catalog-wide report.

#### 1.2 - Consumers read the selection-scoped figure

**Objective**: `pending_download_gb`, the Review estimate, the footer and `can_select_model` agree.

**Failure modes**: The unknown-report fallback must survive: a report the probe never populated still falls back to the full selection total. The headless `--model` path never opens the picker, so `pending_models_gb` is 0 there and must not be read as "nothing to download".

**Prompt**:
> Change `pending_download_gb` to return `state.pending_models_gb` when the report is populated, keeping the existing unknown fallback. Point `review.py` at the same helper rather than at `report.pending_gb` / `report.downloaded_gb`, deriving the already-downloaded total as `selected_models_gb - pending`. Verify `can_select_model` credits back only selected downloaded models.

#### 1.3 - Testing and Stabilization

**Prompt**:
> Generate `scripts/installer/tests/test_selection_scoped_sizing.py`. Every fixture MUST use a catalog strictly wider than the selection, which is the property v2.4.5's tests lacked. Cover: all-selected-downloaded reports ~0 pending; a partially-downloaded selection; the field case (7 selected, 7 downloaded, a catalog holding 157 GB of other un-downloaded models) asserting the estimate is overhead-only and the guard passes; an unknown report still falling back; and an oversized genuinely-new selection still blocking. Run installer pytest and ruff. CI IMPACT: `installer-tests.yml` already scopes `scripts/installer/**`. Session history `docs/v2/v2.4/development/history/2026-09-06_v2.4.7-phase-1-selection-sizing.md`. One local commit. Do not push.

## Phase 2: Configuration Scope

**Goal**: The installer asks only what a user can meaningfully decide, and never lets a component choice silently break a selected model.
**Prerequisites**: Phase 1.
**Stability Gate**: Tests prove Ollama and the Python environment are derived from the selection, the desktop app is always present, the two settings toggles are gone from the page while their state defaults are unchanged, and `components_to_install` still drives the engine.
**Recommended model tier**: frontier
**Recommended effort level**: high
**Rationale**: This changes what the installer installs, not merely how it looks; a wrong derivation silently removes a runtime a selected model needs.

### Sub-tasks

#### 2.1 - Derive required components

**Objective**: A pure resolver maps a model selection onto the components it requires.

**Failure modes**: An uncatalogued id routes to ollama verbatim and therefore requires Ollama. An empty selection still requires the desktop app. A host with Ollama already installed still lists it as required but satisfied. Image/Video/Audio models require the Python environment; chat-only selections do not.

**Prompt**:
> Add `scripts/installer/src/nexus_installer/engine/required_components.py` exposing `required_components(selection, catalog) -> RequiredComponents` with the component ids and a one-line human reason each. Route on `model_router.protocol_for` and the catalog `type`. No Qt import. Keep `components_to_install` as the engine's contract; populate it from this resolver plus the user's optional choices.

#### 2.2 - Will be installed list

**Objective**: Required components are shown, with their reason, not asked.

**Failure modes**: The list must update when the selection changes. Optional choices (extension, shortcut, Unsloth) stay checkboxes and must not move into the list. An already-installed Ollama should read as satisfied rather than as pending work.

**Prompt**:
> Replace the Ollama / venv / desktop checkboxes with a read-only "Will be installed" list rendering each required component and its reason. Keep the section heading. Recompute on show, since the picker precedes this page.

#### 2.3 - Remove the settings toggles

**Objective**: The installer stops asking about runtime preferences.

**Failure modes**: `state.enable_thinking` and `state.enable_memory` keep their current defaults and are still written to the app config, so first-run behavior is unchanged. Any test asserting the toggles exist is rewritten to assert the state defaults instead.

**Prompt**:
> Delete `_thinking_toggle` and `_memory_toggle` and their rows. Do not touch the state fields, their defaults, or the config writer.

#### 2.4 - Testing and Stabilization

**Prompt**:
> Generate `scripts/installer/tests/test_required_components.py` and update the configuration page tests. Run installer pytest and ruff. CI IMPACT: `scripts/installer/**` already covered. Session history `docs/v2/v2.4/development/history/2026-09-06_v2.4.7-phase-2-config-scope.md`. One local commit. Do not push.
