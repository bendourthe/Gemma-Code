# Plan -- Installer Already-Downloaded Model Detection

**Project**: Nexus AI Studio
**Version**: v2.4.5
**Slug**: installer-already-downloaded-models
**Filename**: v2.4.5-installer-already-downloaded-models.md
**Plan Type**: Bug fix / UX enhancement
**Status**: Planned
**Created**: 2026-09-01
**Field evidence**: Packaged v2.4.4 installer rebuild, operator screenshot (2026-09-01): Review step 5 of 7 refused to proceed with `Insufficient disk space (need 204.4 GB free, have 201.0 GB)` for a 14-model selection, on a host where 176 GB of those exact models were already downloaded and verified on disk.
**Goal**: The installer counts only what it still has to download. Models already present in either store are detected, auto-selected, and marked as downloaded in the picker and on the Review page; the Review page lists models in two columns with a distinct mark for pending downloads and shows an estimated disk usage computed from pending models alone; and the final install guard is fed the remaining-download size, so re-running an install on a host that already holds its models is never blocked by a space check for bytes it will not fetch.

## Overview

The operator rebuilt the installer at the end of the v2.4.4 cycle and could not install with it. The wizard demanded 204.4 GB of free space against 201.0 GB available, for a selection whose weights were already sitting on disk from previous runs.

The first question to settle was whether repeated installs had been duplicating downloads and consuming the disk. **They had not.** Measured on the host:

```
$ du -sh ~/.nexus/models/weights/*
70G  inkling-small        44G  wan2.1-t2v-1.3b       18G  sana-video-2b-720p
13G  realvisxl-v5        8.8G  ltx-video            6.7G  juggernaut-xl-v9
6.3G unlimited-ocr-3b    6.1G  sana-1.6b-2k         2.9G  faster-whisper-large-v3
1.4G sana-1.6b-int4      313M  kokoro-82m
$ ls ~/.nexus/models/_tmp        # empty
```

Eleven distinct directories, each present once, no partial or temp leftovers. `inkling-small` is genuinely ~74.7 GB (a three-part GGUF split), not a duplicate. The download engine is already correct: `hf_weights_puller._install_file` hashes any file it finds and logs `already present and verified; skipping`.

So this is not a storage-leak bug. It is a **precheck that measures the wrong quantity**. `evaluate_install_guard` receives `selected_models_gb`, which `_ModelSelection.total_gb` computes as the sum of every selected model's catalog size with no reference to the filesystem. The wizard therefore blocks an install that would download a few GB, on the grounds that it cannot fit 194.4 GB it is not going to fetch.

This plan makes "already downloaded" a first-class fact the wizard carries, and threads it through the three places that consume a size: the picker footer, the Review page, and the install guard.

This is a v2.4 cycle on a new branch off `develop`. It does not reopen the v2.4.4 transcript, restyle, SANA-pin, liveness, or Settings work. Nothing in the 2.4 series is released; the package version stays 2.4.1 and no version bump belongs to this plan.

No phase except the last pushes, opens a pull request, or starts remote CI. Each earlier phase ends with automated tests, session history, and one local commit. The final phase rebuilds the installer so the operator can field-test it.

Discovery interview: skipped as a live questionnaire. The operator supplied the screenshot, the reproduction, and five explicit requirements in one message. Assumptions are listed under Architecture Decisions.

## Goals First

**Target problem**: The installer's disk precheck counts models it will not download, so an operator who has already downloaded 176 GB of models cannot re-run the installer without manually deselecting them or freeing space that does not need freeing.

**Target persona**: The operator re-running a rebuilt installer on the same Windows / NVIDIA host across plan cycles (this host: RTX 3080 Ti Laptop, 16 GB VRAM, ~200 GB free of 1.6 TB), who has accumulated the full model set from earlier installs and expects the wizard to notice.

**Observable definition of done**:

- With every catalog model already on disk, the Review page reports a pending download of ~0 GB and the Install button proceeds. The guard does not fire.
- A model present in `~/.nexus/models/weights/<safe-dir>` (huggingface protocol) is detected as downloaded.
- A model present in the Ollama store (ollama protocol) is detected as downloaded, via `/api/tags` when Ollama is running and via on-disk manifests when it is not.
- Detection never blocks or slows the wizard: an unreachable Ollama, an unreadable models root, or a missing catalog entry degrades to "not downloaded" rather than an error dialog, and the wizard still opens.
- Already-downloaded models are selected when the picker first loads, and carry a visible Downloaded mark distinct from the existing Required / Recommended / Compatible badge.
- The Review page lists models in two columns and marks each one: a check for already downloaded, a distinct mark for pending download.
- The Review page shows the estimated disk usage under the model list, computed from pending models only, and states the already-present size separately so the number is explainable rather than merely smaller.
- `evaluate_install_guard` is called with pending-download GB. Its existing reserve behavior is unchanged for a genuinely-too-large selection: selecting more new models than fit still blocks.
- Re-running the installer a second time with no new selections downloads nothing and is never refused for space.

## Architecture Decisions

1. **Detection is a pure module, not a method on a Qt page.** A new `engine/installed_models.py` exposes a `DownloadedProbe` returning a frozen `InstalledReport` (`downloaded: frozenset[str]`, `pending: frozenset[str]`, `pending_gb`, `downloaded_gb`, `probe_errors`). Every consumer -- picker, Review, guard -- reads that one object. This keeps the logic unit-testable without a Qt event loop, which is how `install_guard.py` is already structured and why it has real tests.

2. **Two stores, because the selection spans two protocols.** `model_router.protocol_for` routes each catalog entry to `huggingface` or `ollama`, and the two land in different places. Detecting only the weights tree would under-report: of the operator's 14 models, `embeddinggemma`, `gemma-4-12b-it-gguf`, and `gpt-oss:20b` are ollama-protocol and live in `~/.ollama/models`. A detector that missed them would leave the guard wrong for exactly the chat models most users select.

3. **Huggingface detection reuses the puller's own path helpers.** `resolve_models_root(state)` + `model_weights_dir(root, id)` + `safe_dir_name(id)` already define where weights land, and `.nexus-model-id` is already written into each directory as a marker precisely because `safe_dir_name` is lossy for ids containing `:` or `/`. Detection prefers that marker and falls back to the directory name, mirroring what the app's own probe does. Re-deriving the path independently would create a second source of truth that silently drifts.

4. **Ollama detection prefers the API and falls back to disk.** `GET {ollama_url}/api/tags` is authoritative and the installer already calls it in two places. When Ollama is not running the probe reads `~/.ollama/models/manifests/**` instead, matching on the `ollama_target_for` tag (`registry.ollama.ai/library/<name>/<tag>`, or `hf.co/<repo>/<quant>` for HF-GGUF-via-ollama entries). Both paths are best-effort.

5. **Presence, not verification.** The probe answers "is this model already here", not "is every byte correct". A sha256 pass over 176 GB would take many minutes and would duplicate what `_install_file` already does per file during the actual install, where it belongs. A model whose files are present but corrupt is therefore reported as downloaded, and the install still repairs it -- `_install_file` re-downloads on a digest mismatch. The cost of being wrong here is a slightly optimistic estimate, not a broken install.

6. **Fail open, never block the wizard.** Every probe failure -- unreachable Ollama, permission error on the models root, malformed manifest -- degrades that model to "not downloaded" and appends a line to `probe_errors`. The result is the current (over-cautious) behavior, which is safe. A detector that could throw on the picker's load path would turn a cosmetic feature into a wizard that will not open.

7. **Auto-select downloaded models, but do not lock them.** The operator asked for already-downloaded models to be selected on load. They stay unlockable: a user may deselect one to skip its verification pass. Required models (the embedding model) keep their existing locked-on behavior, which this plan does not touch. Auto-selection applies only to the initial load, so it never fights a user who deselects and moves between tabs.

8. **The Downloaded mark is a separate pill, not a replacement badge.** `_card_status` resolves one status badge with an existing priority (Required > incompatible > Recommended > Compatible), and overloading it would mean losing a hardware-incompatibility warning on a model that happens to be downloaded -- the one case where the warning matters most. Downloaded renders as an additional pill in the existing `_FlowLayout` name row, which already wraps.

9. **The guard receives pending GB; its semantics are unchanged.** `evaluate_install_guard` keeps its signature and its reserve arithmetic. Only the value passed as `selection_gb` changes, from `state.selected_models_gb` to the report's `pending_gb`. This keeps the existing guard tests meaningful and makes the fix one substitution at the call site rather than a rewrite of the check.

10. **Both sizes are stated on Review, not just the smaller one.** Showing only "~2 GB" after the operator selected 194 GB of models invites the opposite worry -- that the selection was silently dropped. The Review page shows the pending estimate as the headline figure and the already-present total beside it, so the number reconciles against what the user chose.

## Phase 1: Downloaded-Model Probe

**Goal**: One tested, pure function answers "which of these selected models are already on disk, and how many GB remain to download".
**Prerequisites**: None.
**Stability Gate**: Unit tests cover huggingface-present, ollama-present-via-API, ollama-present-via-manifest, absent, unknown-catalog-id, unreachable Ollama, and unreadable models root, with no Qt import in the module.
**Recommended model tier**: frontier
**Recommended effort level**: high
**Rationale**: This module is the single source of truth every later phase reads; a wrong answer here silently corrupts the picker, the Review page, and the guard at once.

### Sub-tasks

#### 1.1 - Probe and report types

**Objective**: A frozen `InstalledReport` and a `DownloadedProbe` that resolves a selection against both stores.

**Failure modes**: An id absent from the catalog routes to ollama verbatim (the `--model` override contract) and must not raise. A model with a zero catalog size must not make `pending_gb` negative. `probe_errors` must never contain a raw traceback.

**Prompt**:
> Add `scripts/installer/src/nexus_installer/engine/installed_models.py`. Define a frozen `InstalledReport` dataclass with `downloaded`, `pending` (both `frozenset[str]`), `downloaded_gb`, `pending_gb`, and `probe_errors: tuple[str, ...]`. Define `probe_installed_models(*, selection, catalog, models_root, ollama_url, ...) -> InstalledReport`. Route each id with `model_router.protocol_for`. For huggingface, reuse `hf_weights_puller.model_weights_dir` / `safe_dir_name` and treat a directory containing at least one regular file as present, preferring the `.nexus-model-id` marker over the directory name. Import nothing from Qt. Sizes come from the catalog, so `downloaded_gb + pending_gb` equals the selection total.

#### 1.2 - Ollama backend with fallback

**Objective**: Ollama-protocol models are detected whether or not the daemon is running.

**Failure modes**: A timeout must not stall the picker; cap it at ~2s like `main.py` does. A malformed `/api/tags` body degrades to the disk path rather than raising. The manifest path must match `ollama_target_for` semantics, including `hf.co/<repo>/<quant>` entries, not just `library/<name>/<tag>`.

**Prompt**:
> Resolve each ollama-protocol id to its pull target with `model_router.ollama_target_for`. Query `GET {ollama_url}/api/tags` with a short timeout and match the returned names. On any failure, fall back to scanning `~/.ollama/models/manifests` for the manifest path the target implies. Record one human-readable line in `probe_errors` when the API path fails, and never raise out of the probe.

#### 1.3 - Testing and Stabilization

**Prompt**:
> Generate `scripts/installer/tests/test_installed_models.py` covering both stores, both ollama paths, and every failure mode, using `tmp_path` fixtures rather than the real home directory. Run installer pytest and ruff. CI IMPACT: `installer-tests.yml` already scopes `scripts/installer/**`; no workflow change. Session history `docs/v2/v2.4/development/history/2026-09-01_v2.4.5-phase-1-downloaded-probe.md`. One local commit. Do not push.

## Phase 2: Picker Marks and Auto-Selection

**Goal**: The model picker shows which models are already downloaded and starts with them selected.
**Prerequisites**: Phase 1.
**Stability Gate**: Tests prove a Downloaded pill renders alongside (not instead of) the existing status badge, downloaded models are selected on first load, a user deselection survives a tab change, and a probe returning nothing leaves current behavior untouched.
**Recommended model tier**: strong
**Recommended effort level**: high
**Rationale**: Qt widget work across an existing card layout with a locked-badge priority that must not regress.

### Sub-tasks

#### 2.1 - Carry the report on state

**Objective**: The probe runs once per wizard session and is readable by every page.

**Failure modes**: Running the probe per card would hit the filesystem hundreds of times. A stale report after the user changes the install path must be refreshed, since `models_root` moves with it.

**Prompt**:
> Add an `installed_report` field to `InstallerState` defaulting to an empty report. Populate it when the picker page loads and re-populate when `models_root` changes. Keep `selected_models_gb` as the full selection total so no existing consumer changes meaning; expose pending size as a separate field.

#### 2.2 - Downloaded pill

**Objective**: A card for an already-present model says so.

**Failure modes**: The pill must not displace a hardware-incompatibility warning. `_FlowLayout` already wraps, so the name row must not overflow at the narrowest wizard width. Colors come from the existing palette constants, not new literals.

**Prompt**:
> In `_ModelCard`, add a `Downloaded` pill via the existing `_pill` helper into the name row when the model id is in `state.installed_report.downloaded`. Leave `_card_status` and its badge priority untouched. Give the pill a stable object name or property so tests can find it without matching on styling.

#### 2.3 - Auto-selection on load

**Objective**: Downloaded models start checked.

**Prompt**:
> On the picker's first population, add every id in `installed_report.downloaded` to the selection before computing the initial total, then mark the page as initialized so later rebuilds do not re-apply it. Do not change the Reset-to-recommended control's meaning.

## Phase 4: Guard Fed Pending Size

**Goal**: The install proceeds when the bytes are already on disk, and still refuses when they genuinely are not.
**Prerequisites**: Phase 3.
**Stability Gate**: Tests prove the guard receives pending GB, the reproduction case (194 GB selected, 176 GB present, 201 GB free) passes, an oversized genuinely-new selection still blocks, and `can_select_model` no longer charges the user for a model already on disk.
**Recommended model tier**: frontier
**Recommended effort level**: high
**Rationale**: This is the phase that decides whether an install is allowed to start; a wrong relaxation here lets a real out-of-space install begin and fail halfway through a 70 GB download.

### Sub-tasks

#### 4.1 - Guard call site

**Objective**: `evaluate_install_guard` measures the remaining download.

**Failure modes**: The guard's reserve arithmetic and its zero-free-disk branch must not change. A probe that failed entirely reports nothing downloaded, so the guard falls back to today's conservative behavior rather than waving an install through.

**Prompt**:
> In `window.py`, pass the pending-download GB from `state.installed_report` as `selection_gb`. Leave `evaluate_install_guard` itself untouched so its existing tests keep their meaning. Where the message names a remedy, keep it accurate for the new quantity.

#### 4.2 - Footer and per-model affordability

**Objective**: The picker footer and `can_select_model` agree with the guard.

**Failure modes**: `can_select_model` currently subtracts the whole selection; charging a user for a model already on disk would let the picker refuse a selection the guard would then allow. The unknown-disk branch (`free_disk_gb <= 0` returns True) stays.

**Prompt**:
> Update `disk_aware_footer` to display pending size, and `InstallerState.can_select_model` to charge only models not already downloaded. Keep the OS reserve semantics identical.

#### 4.3 - Testing and Stabilization

**Prompt**:
> Extend `scripts/installer/tests/test_install_guard.py` and `test_installer_state.py`, including a regression test named for the field reproduction (194.4 GB selected / 176 GB present / 201.0 GB free must pass). Run installer pytest and ruff. CI IMPACT: `scripts/installer/**` already covered. Session history `docs/v2/v2.4/development/history/2026-09-01_v2.4.5-phase-4-guard.md`. One local commit. ## Phase 5: Evidence, Known Gaps, CI/CD, Integration, and Installer Rebuild

**Goal**: Leave the project well-organized and its gaps reconciled, publish and integrate the completed branch, then rebuild the installer so the operator can field-test this cycle and the four before it.
**Prerequisites**: All prior phases.
**Stability Gate**: `docs/v2/v2.4/development/last-phase-evidence-v2.4.5-installer-downloaded.md` exists with one quoted section per duty. A missing Goal, a Goal-review miss without a recorded known-gap, or a missing evidence section blocks the rebuild.
**Recommended model tier**: frontier
**Recommended effort level**: max
**Rationale**: Repo-wide refactor, Goal-vs-codebase review, known-gap reconciliation, release gating, and the installer rebuild that is this cycle's actual deliverable to the operator.

**Objective**: Reconcile this version and every other still-open known-gaps file.

Write the disposition into the evidence file under `## Known-gaps reconciliation`.

#### 5.5 - Terminal CI/CD reconciliation
**Objective**: The pipeline is compared field by field against the canonical contract, and every difference is applied with approval or recorded as a known gap.
**Prompt**:
> Invoke [[cicd-architect]] in existing-pipeline comparison mode and run its six steps in order: DETECT, COMPARE against every canonical field, PROPOSE each difference with cost and risk, obtain explicit APPROVAL per change, APPLY approved changes and re-run the local gate, and RECORD declined or environment-only differences as known gaps. Two v2.4.4 findings are already open and carry forward unless fixed here: `ci.yml` has no always-resolving aggregate required check, and it declares no top-level `permissions:` block. QG-1 (develop-targeted PR coverage) was closed in v2.4.4 and should be confirmed still in force. Run the cross-installer parity gate, which is directly relevant this cycle. Quote the per-field result under `## CI/CD coverage`.

#### 5.6 - Independent Goal-vs-codebase review
**Objective**: Prove the plan Goal landed in the codebase, not that checkboxes were ticked.
**Prompt**:

#### 5.7 - Human/manual testing suggestions (last phase only)
**Objective**: Ask a human to exercise only what automated tests cannot cover.
**Prompt**:
> Emit operator items for the rebuilt installer. This cycle: (1) the Review page shows two columns, a check on each already-downloaded model, a distinct mark on pending ones, and an estimate under the list that reflects pending only; (2) the Install button proceeds on the host that previously refused with 204.4 GB; (3) a deliberately oversized new selection still refuses, so the guard was not simply disabled; (4) with Ollama stopped, chat models are still detected as downloaded. Carry forward every open v2.4.4 operator item, since this rebuild is the first chance to observe them: transcript gutters and pill glow, hairline and title inset and bulk actions, restyle black fur, SANA import plus a Wan and SDXL re-smoke on the 0.36.0 pin, Wan liveness and studio captions, and Settings density and Details.

#### 5.8 - Testing and Stabilization
**Objective**: Prove the refactor preserved behavior and the complete LOCAL gate is green before anything is published.
**Prompt**:
> Run the full local validation/test suite (root lint, `tsc -b`, `npm run check`, root vitest, desktop vitest, `tests/python` pytest, installer pytest, ruff), confirm the refactor changed no behavior, and iterate until clean. Quote the suite under `## Full-suite testing and stabilization`. Generate a session-history entry for this phase.

#### 5.9 - Publication and integration
**Objective**: Publish the completed branch once, validate the merge result remotely, and merge on green.
**Prompt**:
> Create the final local commit. Present the resolved branching model, remote, branch name, and pull-request target, and obtain EXPLICIT approval before the plan's first branch push. The v2.4.4 QG-1 fix means a develop-targeted pull request now runs the full merge-result gate, so required checks are meaningful. Wait until every required check reaches a terminal state. A red check REOPENS this phase: classify, reproduce locally, apply the narrow fix, re-run the local gate, update known gaps and session history, and push again with approval. Never re-run a red check without a local reproduction. Merge only after every required check is green and the user approves. Quote the required-check results under `## Publication and integration`.

#### 5.10 - Installer rebuild for field testing
**Objective**: Hand the operator a rebuilt installer carrying every 2.4 cycle, so the app and installer can finally be tested.
**Prompt**:
> After the integration merges green, rebuild from the integrated branch: `powershell -File scripts/build-vsix.ps1 -SkipTests`, then `powershell -File scripts/installer/build/build-windows.ps1 -SkipSign`, then `powershell -File scripts/installer/build/smoke-windows-exe.ps1`. Verify the artifact carries this cycle's code by extracting the embedded PyInstaller archive rather than grepping the compressed exe (the v2.4.4 lesson: a byte-grep of a onefile finds nothing and proves nothing). Confirm `runtime-lock.json` still pins `diffusers==0.36.0`. Record the artifact path, byte size, and SHA-256 in the evidence file under `## Installer rebuild`, along with the source commit. Do NOT bump the package version, create a tag, or run `/update release`: nothing in the 2.4 series releases until the operator confirms field testing passed, and this repository's semantic-release automation makes a manual bump actively harmful (see the v2.4.4 last-phase evidence).
