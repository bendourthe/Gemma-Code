# v1.7.0 -- Known Gaps, Deferrals, and Carryovers

**Status**: in progress (Phase 3 of 6 closed 2026-06-30). v1.7.0 is the "local skill self-optimization loop + opencode harness hardening" cycle ([plans/adoption-self-optimizing-skills.md](plans/adoption-self-optimizing-skills.md), derived from [comparison-self-optimizing-skills.md](comparison-self-optimizing-skills.md) (primary, S1-S6) and [comparison-opencode.md](comparison-opencode.md) (secondary, O-A)). Phase 1 ships S1: a TS-native golden-task **live runner** that revives the golden suite as a working evaluator (the optimization loop's hard prerequisite, and a restoration of the live golden runs deleted by [ADR-0001](../../../adr/0001-python-backend-disposition.md)) -- four vscode-free `modules/coding/evaluation/` modules (a declarative `success_criteria` evaluator, a copy-into-temp + `git init` snapshot materializer, a dependency-free YAML-subset task loader, and a runner that materializes -> runs the agent via an injected driver -> evaluates -> emits a scored `GoldenTaskResult`) (SO001, closed 2026-06-29). Phase 2 ships S4: the regression-safety scaffolding the optimizer cannot be trusted without -- a locked train/validation/test split (additive `split` field + a deterministic default-by-category assignment) whose `test` split is structurally unreachable from the optimizer loader (`optimizerVisibleTasks` + `assertNoTestSplit` guard), a pure held-out `validationGate` comparator (strict aggregate-improvement + per-task regression tolerance over scored batches, reusing `RegressionReport`), and a content-addressed, redaction-on-write `RejectedEditBuffer` (`core/memory/`, keyed by `skillId + editHash`, edit/trajectory text stored via `ArtifactStore` so it never lands on disk unredacted) (SO002, closed 2026-06-30). Phase 3 ships S2 + S6: the bounded-edit `SkillOptimizer` (the headline loop -- rollout the train split -> reflect on failing trajectories via the existing `ReflexionEngine`/`CriticAgent` -> propose a bounded add/delete/replace skill edit under a textual learning-rate budget -> accept only on a held-out `validationGate` win -> buffer rejects -> overwrite only after explicit human approval, the whole loop capped by the v0.3.0 runaway `BudgetMiddleware`) plus the optimizer-quality A/B (`SkillOptimizerAb` reusing the Fusion F4 `PanelAbHarness` + a net-win default gate); built as eight vscode-free `modules/coding/skilloptimizer/` modules, opt-in default-off (SO003 + SO004, closed 2026-06-30). This file is appended phase-by-phase; items move to `## 2. Resolved` when closed; the `## 3. Summary` is recomputed each pass.

### Phase 2 follow-ups (forward-tier, not defects)

| `SO002.P2.A` | P3 | NI | The `validationGate` gates on the aggregate **pass rate** plus per-task **pass->fail** regressions only; it does not gate on time/token regressions the way the Python `tests/golden/framework/regression.py` baseline comparator also does. | `SO002.P2.B` | P3 | DF | The `RejectedEditBuffer` is append-only (like the `ArtifactStore` it composes): there is no garbage collection of an edit's stored content when an index row is later removed, so orphaned blobs could accumulate under the buffer dir. Tier: record/has/get/list + round-trip `supported`; orphan reclamation `future`. | When a buffer-prune or retention surface lands (or as a periodic sweep), add a mark-and-sweep that walks live index `artifactRef`s and unlinks unreferenced blobs, mirroring the `AS005.P3.A` / `CommandCompressor.pruneOldTees` discipline. |
| `SO002.P2.C` | P3 | NI | No corpus task YAML declares an explicit `split` this phase; every task's split is derived by `assignDefaultSplits` (round-robin within category by sorted id). That guarantees each split spans multiple categories but does not difficulty-stratify (the `tags` carry easy/hard but the default ignores them). The explicit per-task `split` field + override path is built and unit-tested, just unused by the shipped corpus. Tier: deterministic representative-by-category default + explicit override `supported`; difficulty-stratified / curated splits `future`. | If split balance by difficulty matters once the optimizer runs, either pin `split:` on the harder tasks in the corpus YAML (honored automatically) or extend `assignDefaultSplits` to stratify by a difficulty tag while preserving determinism. |
