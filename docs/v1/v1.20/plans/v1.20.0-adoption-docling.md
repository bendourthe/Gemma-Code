## Overview

This milestone operationalizes Section 7 of the Docling comparison in reverse-engineer-first order (Section 6 / MCP Registry Policy). The comparison's product answer is the cycle's invariant: **do not run Docling as the default handler when a user attaches, uploads, or pastes a file.** Chat already parses PDF and images through RapidOCR (every OS) and Unlimited-OCR (NVIDIA), with parsed text shown so the user decides whether it enters a prompt (`desktop/src/modules/chat/ChatPage.tsx`). The holes are: Coding's `parse_document` tool is implemented and tested but unwired (LSO.P4.B); Coding's composer is text-only; Office files are silently rejected by `accept="application/pdf,image/*"`; expanding that list without a format router would shove a `.docx` through `load_pages`, which treats non-PDF as a single image.

Delivery stays on the existing spine: `core/documents/` (job manager, runtime factory), `runtimes/ocr/` (Python parse child), sidecar `ocr.*` IPC, `src/tools/handlers/parseDocument.ts` plus `modules/coding/runtime/headlessTools.ts`, and `MediaComposer`. Native Office ingest uses `python-docx`, `python-pptx`, and `openpyxl` (the same libraries Docling's `format-office` extras wrap), not the Docling SDK. Bytes in, markdown/text out, Nexus caps (64 MB, 200 pages, tool 50 pages), no URL sources, no `enable_remote_services`, output treated as untrusted.

A4 (optional local Docling layout engine) is **gated**, not scheduled as a build. Phase 4 runs the on-device OCR quality pass that v1.16 deferred (LSO.P3.C) and records adopt-or-decline. If RapidOCR plus Unlimited-OCR hold, A4 closes as evaluated-and-declined in this cycle. If they lose on tables/reading-order, A4 becomes a known-gap for a later cycle with the comparison's local-only mitigations; it does not silently `pip install docling` here.

Success looks like: a user drops a Word file, a deck, a spreadsheet, a PDF, or a screenshot in Chat and gets parsed text back locally; a coding agent can `parse_document` a workspace PDF behind CONFIRM with redaction and the inbound classifier; Coding's composer accepts the same file kinds; Docling, `docling-mcp`, `docling-serve`, IBM watsonx, Apify, and `convert(https://...)` never appear on the attach path.

## Goals

- **Target problem**: A local-first user who attaches a real document (invoice PDF, Word brief, slide deck, spreadsheet) cannot get that file into gen-AI context without leaving Nexus or being told to install a third-party converter whose happy path fetches URLs.
- **Persona**: The same single-machine developer/creator Nexus already serves (laptop, one consumer GPU, no subscription, no outbound by default).
- **Definition of done**: Chat and Coding accept PDF, images, DOCX, PPTX, and XLSX via click / drop / clipboard file paste; PDF and images still use RapidOCR or Unlimited-OCR; Office files use native parsers; unsupported types fail with a reason, not a silent drop; `parse_document` is registered when `nexus.coding.parseDocument.enabled` is on; parsed text never auto-enters a model prompt; no new outbound destination.

## Phase 1: Wire `parse_document` (A1)

**Goal**: Register the already-written `parse_document` tool on every host that has a document runtime, gated on `nexus.coding.parseDocument.enabled`, with optional memory ingest gated on `nexus.coding.parseDocument.memoryIngest.enabled`.
**Prerequisites**: None. Skill-native / existing-build first per MCP Registry Policy.
**Stability Gate**: With the flag on, sidecar headless/ACP/scheduler and the VS Code coding panel expose `parse_document`; a workspace PDF is read as base64 by the tool (never by the parser as a raw path), redacted, classifier-screened, and CONFIRM-gated. With the flag off, the tool is absent. Memory ingest stays off unless its own flag is on. LSO.P4.B and LSO.P4.C close or are re-filed with a remaining-host note.
**Recommended model tier**: frontier
**Recommended effort level**: high
**Rationale**: One high signal (risk: untrusted OCR into agent context on production hosts). Wiring is a few composition-root files, but a missed guard is a prompt-injection hole.

### Sub-tasks

#### 1.1 - Sidecar / ACP / scheduler parser injection

**Objective**: Pass a `documentParser` into `createHeadlessTools` wherever the sidecar builds a headless tool set.

**Failure modes**: Malformed or absent `documentBase64` from the tool stays a tool error envelope (existing `DocumentError` codes), never an uncaught spawn; if the Python OCR child is unreachable or slow, the tool returns the existing engine-unavailable / timeout path and does not hang the ACP session past the runtime's request timeout; if `parseDocumentEnabled` is false while a parser object exists, the tool is not registered (flag wins over presence).

**Build class**: load-bearing.

**Prompt**:

Inject it into every `createHeadlessTools({ ... })` call that is a production coding host: `desktop/sidecar/src/main.ts` (scheduler `runHeadless`), `desktop/sidecar/src/acp/AcpAgent.ts`, and any other sidecar `createHeadlessTools` site. ## Phase 2: Format Router + Native Office Ingest (A3 + A2)

**Goal**: Sniff the payload, route PDF/images to the existing OCR engines, parse DOCX/PPTX/XLSX with native libraries into the existing `{ text, markdown, pages }` envelope, and expand Chat's accept list only after the router exists.
**Prerequisites**: Phase 1 (Coding tool can consume the same runtime once Office engines exist).
**Stability Gate**: A dropped `.docx` / `.pptx` / `.xlsx` in Chat parses without RapidOCR installed; a PDF still uses RapidOCR/Unlimited-OCR; a `.html` or random bytes returns `unsupported-media` with a reason; Image Studio still rejects PDFs; 64 MB and zip-entry caps hold; no torch added to `runtimes/ocr/requirements.txt`.
**Recommended model tier**: frontier
**Recommended effort level**: high
**Rationale**: One high signal (risk: untrusted Office zip/XML parsers on user files). Scope is the existing OCR runtime plus composer accept tests.

### Sub-tasks

#### 2.1 - Magic-byte format router

**Objective**: Classify payloads without trusting `file.type` or a caller MIME.

**Failure modes**: Absent or empty payload keeps `invalid-params`; unknown bytes return `unsupported-media` (not a crash, not a silent image decode); PDF sniffed as `%PDF-` still wins even if the data URL said `image/png`.

**Build class**: load-bearing.

**Prompt**:
> Extend `runtimes/ocr/documents.py`. Today `looks_like_pdf` sniffs `%PDF-` and everything else becomes one `PageImage`. Add a `detect_kind(data: bytes) -> pdf | image | docx | pptx | xlsx | unsupported` helper using magic bytes / ZIP `[Content_Types].xml` (Office Open XML) rather than the caller MIME. Keep `MAX_DOCUMENT_BYTES = 64 * 1024 * 1024`. For OOXML, bound zip member count and decompressed size (copy the *idea* of Docling's iWork limits, not their package; add `defusedxml` only if XML is parsed). Wire `runtimes/ocr/parse.py` to dispatch: pdf/image -> existing `resolve_engine` OCR path; office -> new engines (2.2); unsupported -> `DocumentError("unsupported-media", ...)`. Thread an optional filename hint but never let it override a conflicting magic sniff. Extend `tests/python/ocr/test_documents.py` and `test_parse.py`. Do not import docling.
