**Project**: Nexus AI Studio
**Version**: v1.16.0 (ships as the next 2.x semantic-release)
**Slug**: local-serving-and-ocr
**Filename**: v1.16.0-adoption-local-serving-and-ocr.md
**Plan Type**: Feature / Enhancement (adoption)
**Created**: 2026-07-22
**Seeded from**: [../comparisons/v1.16.0-comparison-local-serving-and-ocr.md](../comparisons/v1.16.0-comparison-local-serving-and-ocr.md)
**Goal**: Turn Nexus from a local-model *consumer* into a local-model *provider* (a loopback OpenAI/Anthropic-compatible gateway fronting the model registry) and give it its first document-OCR / PDF-parsing capability, both reverse-engineered onto the existing sidecar + registry spine, local-only and zero-outbound.

## Overview

This milestone operationalizes the adoption plan from the Nativ + Baidu Unlimited-OCR comparison. It probes two gaps the comparison surfaced. The architectural gap: Nexus consumes local models (Ollama, LM Studio, and any loopback runtime registered through `modules/coding/llm/LocalAdapterRegistry.ts`) and exposes a read-only MCP tools server, but it has no inference gateway that would let the user's other agent tools (Claude Code, Codex, Cursor) reuse Nexus's already-downloaded local models. The capability gap: Nexus ships open models for image (SANA), video (SANA-Video / Wan), ASR (faster-whisper), and TTS (kokoro) via its catalog + Python sidecar, but has no document-OCR / PDF-parsing capability at all. The flagship of this cycle (Phase 1) is the loopback serving gateway, the exact inverse of the v1.6.0 `localAdapters` client and on-brand with "Zero Tokens Billed" extended to the whole toolchain; the second pillar (Phases 3-4) is a new, optional, GPU-tier-gated OCR model plus a document-parse agent tool.

Delivery stays within Nexus's existing stack: a TypeScript sidecar (`desktop/sidecar/`), the model registry (`core/registry/NexusModelRegistry.ts` + `core/registry/catalog.json` + `core/registry/ModelStorage.ts`), the Python runtimes tree (`runtimes/`, where SANA / whisper / kokoro already live), and the Tauri React desktop shell. No architecture is imported: nativ's Swift/SwiftUI macOS-only shell, its macOS-26 / Apple-Silicon-only floor, a bundled first-class MLX runtime, and Unlimited-OCR-as-a-default were all rejected in the comparison (N1-N5). Every candidate is a reverse-engineered internal build (A1, A5, A6) or an extension of an existing subsystem (A2 observability, A4 the Models page), except MLX support (A3), which is documentation of the already-supported loopback-adapter path rather than new code.

**Cross-version prerequisite**: this plan assumes v1.15.0 shipped. v1.15 Phase 4 implements the real `models.*` IPC handlers and the disk/Ollama registry reconciliation that Phase 1 (serving gateway fronting the registry), Phase 4 (OCR model in the registry), and Phase 5 (model-library UX) all build on. If v1.15 has not landed when this cycle starts, sequence its Phase 4 first or treat the registry surface as a hard dependency. Success looks like: the user flips an opt-in setting, points Claude Code / Codex / Cursor at `http://127.0.0.1:<port>/v1`, and drives Nexus's local models from those tools with a local token; the Traces panel shows per-model tokens/sec, TTFT, and memory; a user can install an optional OCR model on a capable GPU and parse a multi-page PDF into text/markdown from the app and from an agent tool; and macOS Apple-Silicon users have a documented, smoke-tested path to run an MLX server through `nexus.llm.localAdapters`.

## Phase 1: Local Serving Gateway (A1, flagship)

**Goal**: Nexus exposes its registry-backed local models over a loopback OpenAI- and Anthropic-compatible HTTP API so external agent tools can drive them, without any code leaving the machine.
**Prerequisites**: v1.15 Phase 4 (real `models.*` registry) landed.
**Stability Gate**: With the opt-in setting on, `GET /v1/models` lists the installed models from `NexusModelRegistry`; `POST /v1/chat/completions` (OpenAI shape) and `POST /v1/messages` (Anthropic shape) stream a completion from the selected local model; the server binds a loopback address only and refuses to start on a non-loopback bind; requests without the configured local token are rejected; with the setting off, no listener is opened. Unit + integration tests cover the happy path, the auth rejection, and the loopback guard.
**Recommended model**: Strong reasoning tier, high effort - claude-opus-4-8 (high). Rationale: a net-new inbound HTTP surface with genuine security requirements (loopback binding, token auth, no tool/filesystem exposure, request limits); correctness and threat-model discipline matter. Re-confirm against the then-current model set at implementation.

### Sub-tasks

#### 1.1 - Serving-gateway settings and lifecycle

**Objective**: Add the opt-in configuration surface and wire the server into the sidecar lifecycle, defaulting off.

**Prompt**:
> In the Nexus AI Studio repo, add a local-serving gateway configuration group to `package.json` `contributes.configuration.properties`, mirroring the existing `nexus.mcp.*` keys: `nexus.serving.enabled` (boolean, default `false`), `nexus.serving.port` (number, default e.g. `11500`), `nexus.serving.host` (string, default `127.0.0.1`), and `nexus.serving.token` (string, default `""`; when empty, generate a random loopback-only token at startup and surface it in the UI). Document each key's description in the local-first / opt-in style used by the surrounding keys. Add the mirrored settings compat entries if the repo's SettingsCompat pattern requires them. Wire a `ServingGateway` lifecycle into the sidecar composition root (the same place `NexusModelRegistry` is constructed for the v1.15 `models.*` handlers, `desktop/sidecar/src/`): start the listener only when `nexus.serving.enabled` is true, stop it on shutdown and when the setting is toggled off. Do NOT open any listener when disabled. Acceptance: toggling `nexus.serving.enabled` starts/stops the server; with it off, no port is bound; the resolved token is retrievable for display.

---

#### 1.2 - Loopback + auth guard

**Objective**: Enforce that the gateway is unreachable off-box and unusable without the local token.

**Prompt**:
> Implement the security guard for the serving gateway. Reuse the loopback-validation logic that `modules/coding/llm/LocalAdapterRegistry.ts` already applies to adapter endpoints (it rejects any non-loopback endpoint citing the AGENTS.md MCP Registry Policy; the check mirrors `modules/coding/utils/ssrf.ts`). Refuse to start the server if `nexus.serving.host` resolves to anything outside `127.0.0.0/8`, `::1`, or a loopback hostname, and log an error that cites the local-first policy. Enforce bearer-token auth on every request: reject with HTTP 401 when the `Authorization` header does not match the resolved `nexus.serving.token`. Add request-size and concurrency limits so a runaway client cannot exhaust the host. The gateway MUST expose only model inference; it must never proxy file access, terminal, or any Nexus tool. Acceptance: a request to a non-loopback bind is refused at startup; a request without/with a wrong token gets 401; oversized requests are rejected; there is no route that reaches the filesystem or tools.

---

#### 1.3 - OpenAI-compatible routes fronting the registry

**Objective**: Serve `/v1/models` and `/v1/chat/completions` (OpenAI shape) backed by real installed models.

**Prompt**:
> Implement the OpenAI-compatible routes on the serving gateway, backed by `core/registry/NexusModelRegistry` and the existing local LLM clients (`modules/coding/llm/OllamaClient.ts`, `LmStudioClient.ts`, and any `localAdapters` runtime). `GET /v1/models` returns the installed chat-capable models (registry `source: "registry"`/`"external"`), mapped to the OpenAI models list shape. `POST /v1/chat/completions` accepts the OpenAI request body (`model`, `messages`, `stream`, `temperature`, etc.), routes to the correct local client for that model, and returns an OpenAI-shaped response; when `stream: true`, emit Server-Sent Events in the OpenAI `chat.completion.chunk` format. Map Nexus/Ollama errors to OpenAI-shaped error bodies without leaking stack traces or file paths. Acceptance: pointing an OpenAI-compatible client (e.g. Codex, or `curl`) at the gateway lists the installed models and streams a completion from a local model.

---

#### 1.4 - Anthropic-compatible route

**Objective**: Serve `POST /v1/messages` (Anthropic shape) so Claude Code and Anthropic-SDK clients can use local models.

**Prompt**:
> Add the Anthropic-compatible `POST /v1/messages` route to the serving gateway. Accept the Anthropic Messages request body (`model`, `messages`, `system`, `max_tokens`, `stream`), translate it to the internal chat request, route to the selected local client, and return an Anthropic-shaped response; when `stream: true`, emit the Anthropic SSE event sequence (`message_start`, `content_block_delta`, `message_delta`, `message_stop`). Share the model-resolution, auth, and error-mapping logic with the OpenAI routes (1.3) rather than duplicating it. Acceptance: an Anthropic-SDK client (or Claude Code configured with a custom base URL + the local token) can list nothing/needs no models list and can stream a `/v1/messages` completion from a local model.

---

#### 1.5 - Desktop surface: enable, copy endpoint + token

**Objective**: Give the user a one-click way to turn the gateway on and copy the connection details.

**Prompt**:
> Add a "Local API server" section to the desktop Settings (near the existing MCP / model settings). Show a toggle bound to `nexus.serving.enabled`, the resolved base URL (`http://<host>:<port>/v1`), the OpenAI and Anthropic endpoint paths, and a copy-to-clipboard for the base URL and the local token (mask the token by default with a reveal control). Show the server's running/stopped state. Include a short inline note that this serves local models to other tools on this machine only. Do not expose the token in logs. Acceptance: a non-technical user can toggle the server on, copy the base URL + token, and paste them into another tool's config.

---

#### 1.6 - Testing and Stabilization

**Objective**: Prove the routes, auth, loopback guard, and lifecycle; cover them in CI.

**Prompt**:
> Add tests for the serving gateway: unit tests for the loopback guard (non-loopback host refused), token auth (missing/wrong -> 401, correct -> pass), and error mapping; integration tests that start the gateway against a fake LLM client and assert `/v1/models`, `/v1/chat/completions` (buffered + streamed SSE), and `/v1/messages` (buffered + streamed) return the correct shapes; a lifecycle test that no port is bound when `nexus.serving.enabled` is false and the listener stops on toggle-off. Then create/update CI to cover the sidecar serving changes and optimize it (path filters on the sidecar/serving surface, concurrency cancel-in-progress, dependency caching); keep it platform-agnostic with GitHub Actions as the primary example. ## Phase 3: Local Document-OCR Capability (A5)

**Goal**: Nexus gains an optional, GPU-tier-gated document-OCR / PDF-parsing capability: an open OCR/VLM model in the catalog, a Python sidecar runtime that runs it, and a "parse document -> text/markdown" action, wired the same way SANA/Whisper/Kokoro are.
**Prerequisites**: v1.15 Phase 4 (registry) landed.
**Stability Gate**: The OCR model appears in `core/registry/catalog.json` as an optional, GPU-tier-gated entry (never auto-installed); on a capable GPU it installs through the existing model-install path; a "parse document" action converts an image or a multi-page PDF (page-to-image) into text/markdown via the sidecar; on an incapable/incompatible host the capability is cleanly unavailable with an explained state, not a crash; the model's remote code is pinned to a specific revision and runs only inside the sandboxed Python runtime.
**Recommended model**: Strong reasoning tier, high effort - claude-opus-4-8 (high). Rationale: supply-chain discipline (`trust_remote_code` pinned + sandboxed), cross-platform gating (CUDA-first vs OS parity), and a net-new Python runtime + registry + action path. Re-confirm against the then-current model set at implementation.

## Phase 4: Document-Parse Agent Tool + Memory Ingestion (A6)

**Goal**: The OCR capability becomes usable by the coding agent (parse a PDF/screenshot into context) and, optionally, feeds parsed text into the memory subsystem, with parsed content treated as untrusted.
**Prerequisites**: Phase 3 (OCR capability).
**Stability Gate**: The agent can call a "parse document" tool that returns parsed text for a given local file; parsed content is routed through the inbound content classifier (as `fetch_page` output is) and `redactSecrets` before it enters context or memory; optional memory ingestion is opt-in; the tool respects the existing permission tier and path-guard rules.
**Recommended model**: Strong reasoning tier, medium-high effort - claude-opus-4-8 (medium). Rationale: a security-sensitive untrusted-content path (parsed documents entering agent context and memory); the reuse of Phase 3 lowers novelty but the trust boundary raises the bar. Re-confirm against the then-current model set at implementation.

### Sub-tasks

#### 4.1 - Document-parse agent tool

**Objective**: Expose OCR as a governed agent tool.

**Prompt**:
> Add a `parse_document` agent tool that wraps the Phase 3 OCR path: input is a workspace-relative file path (image or PDF); output is parsed text/markdown. Register it with the correct permission tier (it reads a file and runs a model - align it with the existing read/confirmation tiers) and route the path through the existing `pathGuard` (symlink-aware, workspace-scoped) so it cannot read outside the workspace or secret paths without the explicit `allow_secrets` override. Treat the returned text as untrusted external content: pass it through the inbound content classifier (`nexus.coding.inboundClassifier`, the same gate `fetch_page`/`web_search` use) so injection markers are annotated before the text reaches the agent's context, and apply `redactSecrets`. Acceptance: the agent can parse a PDF in the workspace into context; a path-traversal or secret-path attempt is blocked; parsed content carries the untrusted-content annotation when the classifier flags it.

---

#### 4.2 - Optional memory ingestion

**Objective**: Let parsed documents optionally enter the memory subsystem, opt-in and redacted.

**Prompt**:
> Add an opt-in path to ingest parsed-document text into the memory subsystem (`core/memory/`), gated behind a setting (default off, mirroring the conservative defaults of `nexus.memory.consolidation.enabled` / `compression.enabled`). When on, store parsed text as observations with provenance (source file + that it came from OCR), after `redactSecrets` and the inbound-classifier pass from 4.1. Never ingest automatically without the opt-in. Acceptance: with the setting on, parsing a document adds redacted, provenance-tagged memory entries; with it off, no memory write occurs; secrets in the document are redacted before storage.

---

#### 4.3 - Testing and Stabilization

**Objective**: Cover the tool, its guards, and memory ingestion; wire CI.

**Prompt**:
> Add tests: a tool test asserting `parse_document` returns text for a fixture file, is blocked on path traversal / secret paths, and annotates classifier-flagged content; a test that parsed content is redacted; memory-ingestion tests for both the opt-in-on (redacted, provenance-tagged write) and opt-in-off (no write) paths. Use fakes for the OCR runtime and the classifier. Run `npm run test:shell` + the relevant suites; iterate to green. Update CI for the tool + memory changes (path filters, caching, cancel-in-progress). Do not proceed to Phase 5 until stable. After tests pass, run `/generate-session-history` for Phase 4.

## Phase 5: MLX-via-Adapters Docs + Model-Library UX (A3 + A4)

**Goal**: Document and smoke-test the already-supported path for running an MLX model server through `nexus.llm.localAdapters` on Apple Silicon, and polish the model-library discovery / quick-switch UX on the Models page.
