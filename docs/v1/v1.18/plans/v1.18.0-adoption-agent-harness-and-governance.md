## Overview

This milestone operationalizes the merged adoption plans of the three v1.18 comparisons: OpenWorker (a local-first Tauri sibling whose adoptable delta is autonomy UX and registry governance, not its 25+ SaaS connectors), Open Interpreter (a mature reference implementation of Nexus's own v1.12 harness-per-model thesis, plus the OS-level sandbox Nexus documents as its single most important open gap), and Laguna-S-2.1 (a 118B/8B-active MoE model whose adoptable delta is catalog *preparation* - quant taxonomy, MoE schema, a llama.cpp loopback recipe - while the model entry itself stays behind the EM.P3/EM.P4 gates).

The cycle theme is agent harness and governance: everything in this plan either activates the harness machinery Nexus already built (`modules/coding/orchestration/HarnessSelector.ts`, shipped opt-in and off per EM.P1.A/B, `docs/v1/v1.12/known-gaps.md`), tightens what agents are allowed to use (catalog flags, quant gates, MoE schema, per-tool MCP control on top of `modules/coding/mcp/HubRegistryPolicyFilter.ts`), makes autonomy safe (ask inbox + scheduler that route every wake through `modules/coding/guardrails/PermissionTiers.ts` and `src/tools/ConfirmationGate.ts`), or confines what agents execute (the per-OS sandbox around `run_terminal`, EM.P5.A, `docs/v1/v1.12/exec-sandbox-audit.md`).

Ordering follows the MCP Registry Policy's reverse-engineer-first discipline: skill-native items ship first (Phase 1: zero-code confirmations plus the documented llama.cpp adapter recipe), then the re-full builds by P-tier and dependency order (Phase 2: OI-A5 P0 harness wiring then OI-A2 P1 profiles; Phase 3: the P1 catalog/registry items OW-A4 + LG-A2 + OW-A5 plus the P2 LG-A3 schema they share files with; Phase 4: OW-A1 P1 ask inbox then OW-A2 P2 scheduler, which depends on it; Phase 5: OI-A3 P2 ACP), then the one in-cycle re-partial build (Phase 6: OI-A1 OS sandbox, started as its own workstream because it is high-effort and independent). Gated items (LG-A1 catalog entry, LG-A4 1M-context budget, OI-A4-native app driver) are tracked, not built - see "Deferred and gated items". Every rejection from the three Section 9s is carried forward under "Out of scope / rejected".

Dedup and overlap notes (merged across the three comparisons):
- **OW-A4 + LG-A3 share one schema change.** The tool-calling-verified flag and the MoE `activeParams`/`totalParams` fields both extend `core/registry/catalog.json`; they are implemented together in Phase 3 as a single backward-compatible schema revision rather than two.
- **OI-A3 overlaps the queued v1.16.0 serving-gateway candidate.** Both add an external control surface over the coding engine (`docs/v1/v1.16/comparisons/v1.16.0-comparison-local-serving-and-ocr.md`). They are complementary (ACP is editor-driving; the gateway is model-serving) but MUST share one loopback transport/auth layer - Phase 5 builds that shared layer; do not build two.
- **Two items are already skill-native in Nexus-Hub and need no code.** OpenWorker's "morning brief" content maps onto the existing `agent-presets` morning-briefing preset (only OW-A2's scheduling mechanism is a build), and Open Interpreter's browser-QA half of OI-A4 maps onto the existing `browser-testing-with-devtools` skill. Phase 1 confirms and documents both instead of rebuilding them.
- **No literal duplicates exist across the three sources.** The A-numbers collide (each comparison numbers its own A1..A5), so this plan disambiguates with OW-/OI-/LG- prefixes; e.g. OW-A1 (ask inbox), OI-A1 (OS sandbox), and LG-A1 (gated catalog entry) are three different items.

Success looks like: the harness selector is live behind `settings.harnessSelectorEnabled` with named per-family profiles and a `/harness`-style inspect/switch; the catalog distinguishes tool-calling-verified models and models MoE resident-vs-active cost; the MCP registry offers per-tool allow/deny that only ever tightens the default-deny; a headless or scheduled agent run parks its approvals in a persistent inbox instead of dying on the 60s `ConfirmationGate` timeout; external editors can drive the engine over loopback ACP with local auth; and `run_terminal` executes inside OS-level confinement on all three OSes.

## Phase 4: Unattended Autonomy - Ask Inbox + Scheduler (OW-A1, OW-A2)

**Goal**: Make headless and recurring agent runs safe: approval requests park in a persistent inbox instead of dying on the 60s `ConfirmationGate` timeout, and a local cron-style scheduler enqueues agent runs that re-enter the full permission stack on every wake.
**Prerequisites**: Phase 3 (ordering); OW-A2 hard-depends on OW-A1 (scheduled runs need somewhere to park asks).
**Stability Gate**: A persistent local approval queue exists; when a run is headless/scheduled, `src/tools/ConfirmationGate.ts` parks the request (with full action context from `modules/coding/guardrails/ActionClassifier.ts`) instead of timing out, and the run suspends or continues per tier semantics; a desktop inbox panel lists parked asks with approve/deny/expire; a later approval replays through the SAME gate + `modules/coding/guardrails/PermissionTiers.ts` tier check (floor-clamp intact) - approval is never a bypass; a local scheduler triggers recurring agent runs (reusing the weekly skills-auto-sync worker pattern), every wake routes through `PermissionTiers`/`ConfirmationGate` with NO auto-approve path, and `modules/coding/guardrails/GitSafetyNet.ts` checkpoints apply to scheduled runs exactly as to interactive ones; tests cover parking, replay, expiry, and the no-auto-approve invariant.
**Recommended model**: Mid-strong tier, high effort - claude-sonnet-5 (high). Rationale: safety-critical queue/replay semantics over existing guardrails; the code is local and additive but the invariants must be airtight. Re-confirm against the then-current model set at implementation.

### Sub-tasks

#### 4.1 - Persistent approval queue + gate integration (OW-A1)

**Objective**: The missing precondition for any safe autonomous run.

**Prompt**:
> Build a local persistent approval queue and integrate it with `src/tools/ConfirmationGate.ts`: when the session is headless or scheduled (an explicit run mode, not an inference), a confirmation request is parked in the queue - capturing the classified action (`modules/coding/guardrails/ActionClassifier.ts`), tier, tool, arguments, and session/run identity - instead of blocking on the 60s timeout. Parked requests have states (pending/approved/denied/expired) and a configurable expiry. Approving a parked request REPLAYS it through the confirmation gate and the `PermissionTiers` floor-clamp at approval time (never a stored "pre-approval" that skips the gate); if the session is gone, approval executes in a fresh gated context or fails safe. Interactive sessions are unchanged. Acceptance: headless runs park instead of timing out; approval replays through gate + tiers; expiry fails safe; interactive behavior is untouched.

**Objective**: The user-facing surface for parked approvals.

Denials and expiries propagate to the suspended run as a clean refusal (the run continues or ends per its tier semantics, never crashes). Acceptance: parked asks are visible and actionable; approve executes via the replay path from 4.1; deny/expire produce clean refusals; the indicator reflects pending count.

## Phase 6: OS Process Sandbox (OI-A1, re-partial, closes EM.P5.A)

**Goal**: Wrap `run_terminal` execution in OS-level confinement on all three OSes (macOS Seatbelt, Linux Landlock+seccomp, Windows job object + restricted token), closing Nexus's top-ranked open gap (EM.P5.A) using Open Interpreter strictly as an Apache-2.0 design reference - no Rust code vendored.
**Prerequisites**: Independent of Phases 2-5 (the comparisons recommend starting it early; it is sequenced last among build phases only because it is the re-partial bucket per the policy ordering - implementation MAY begin in parallel once Phase 1 lands).
**Stability Gate**: A sandbox abstraction wraps the `run_terminal` spawn path (currently `spawn(shell:true)` at user privilege, guarded only by confirmation + touched-path/secret-path denylists + env scrub per `docs/v1/v1.12/exec-sandbox-audit.md`); per-OS backends confine filesystem writes to the project/workspace scope and block or gate network egress per policy; capability detection is explicit - where a backend is unavailable the system runs in a DOCUMENTED degraded mode that is clearly surfaced to the user and recorded, never silently unconfined; existing guardrails (confirmation, denylists, env scrub, `GitSafetyNet`) remain in force IN ADDITION to the sandbox; the existing tool-call contract is unchanged (same inputs/outputs, sandbox is transparent to well-behaved commands); cross-OS CI exercises each backend's policy tests.
**Recommended model**: Strong tier, high effort - claude-opus-4-8 (high). Rationale: three OS security backends with fail-closed semantics; the highest-value and highest-complexity item of the cycle. Re-confirm against the then-current model set at implementation.

### Sub-tasks

#### 6.1 - Sandbox abstraction + policy model

**Objective**: One policy, three backends.

**Prompt**:
> Design the sandbox abstraction around the `run_terminal` execution path (tool implementation under `src/tools/`, per the registry in `src/tools/ToolRegistry.ts`): a policy object (writable roots = project/workspace + declared temp dirs; readable scope; network allow/deny; process/resource limits) and a backend interface (`prepare/spawn/teardown`, capability report). Derive default policy from the existing session's project root and the touched-path/secret-path denylists so the sandbox and denylists agree. Define the degraded-mode contract: if no backend is available, execution continues ONLY with the pre-existing guardrails, the session UI and logs state "unconfined" explicitly, and the classifier can require a higher confirmation tier for that state. Study `docs/v1/v1.12/exec-sandbox-audit.md` first and reconcile its findings. Acceptance: abstraction + policy + degraded-mode contract exist with unit tests; no behavior change yet for callers.

---

#### 6.2 - macOS backend (Seatbelt)

**Objective**: Confinement via `sandbox-exec`/Seatbelt profiles.

**Prompt**:
> Implement the macOS backend using Seatbelt: generate a per-run profile from the policy object (write access limited to the writable roots, read scope per policy, network per policy), launch the `run_terminal` child under it, and surface profile-violation failures as clean, classified tool errors (not crashes). Use Open Interpreter's approach as a design reference only - write Nexus's own profile generation, vendor no code. Handle Seatbelt deprecation caveats with a capability check and fall back to degraded mode per the 6.1 contract. Acceptance: on macOS, a command writing outside the writable roots fails inside the sandbox while in-scope work succeeds; violations surface cleanly; capability detection is honest.

---

#### 6.3 - Linux backend (Landlock + seccomp)

**Objective**: Confinement via Landlock filesystem rules plus a seccomp filter.

**Prompt**:
> Implement the Linux backend: apply Landlock rules for the policy's filesystem scope and a seccomp filter for the network policy (block socket creation when egress is denied) in the child before exec. Detect kernel support (Landlock ABI level) and fall back to degraded mode per the 6.1 contract on old kernels. Same clean-error surfacing as 6.2. Acceptance: on a Landlock-capable kernel, out-of-scope writes and denied network calls fail inside the sandbox; unsupported kernels degrade loudly per contract.

---

#### 6.4 - Windows backend (job object + restricted token)

**Objective**: Confinement on Nexus's first-class platform.

**Prompt**:
> Implement the Windows backend: launch the `run_terminal` child in a job object (kill-on-close, process/resource limits) with a restricted token and, where available, an AppContainer or equivalent filesystem/network restriction honoring the policy object; document precisely which policy dimensions each Windows mechanism can and cannot enforce, and route unenforceable dimensions through the degraded-mode surfacing (partial confinement is stated, not implied). Same clean-error surfacing as 6.2/6.3. Acceptance: on Windows, the child is job-confined with resource limits; the enforced-vs-unenforced policy matrix is documented; partial confinement is surfaced to the user.

---

#### 6.5 - Testing and Stabilization

**Objective**: Prove confinement per OS; wire cross-OS CI.

**Prompt**:
> Add tests: unit tests for policy derivation and the degraded-mode contract (mock backends); per-OS integration tests (in-scope command succeeds; out-of-scope write fails; denied network fails where enforceable; violation surfaces as a classified tool error; capability detection matches the host) tagged to run on their matching CI OS; a regression test that the `run_terminal` tool contract (inputs/outputs, confirmation flow) is unchanged for well-behaved commands; verify existing denylist/env-scrub guardrails still apply inside the sandbox. ## Out of Scope / Rejected (carried forward from the three Section 9s)

Every rejection below is carried forward verbatim in substance and cites the MCP Registry Policy (`AGENTS.md`; decision tree summarized in `CLAUDE.md`) and/or Nexus design principles. Do not let "the source does more" pressure these.

From the OpenWorker comparison:
- **OW-N1 - The 25+ hosted SaaS connectors** (GitHub, Slack, Jira, Notion, Linear, HubSpot, Gmail, Google Calendar, ...). Rejected: MCP Registry Policy "hard no" on as-a-service integrations; third-party data processors; credential sprawl; local-first design principle.
- **OW-N2 - The cloud OAuth broker relay.** Rejected: a new cloud dependency and outbound relay; conflicts with no-outbound-without-opt-in; `HubRegistryPolicyFilter.ts` default-deny.
- **OW-N3 - Cloud provider breadth via aisuite (11 hosted providers).** Rejected: already formally dropped as D1 in v1.6.0 (`docs/v1/v1.6/plans/adoption-aisuite-harness.md`); conflicts with local-first / "Zero Tokens Billed".

From the Open Interpreter comparison:
- **OI-N1 - Vendoring Open Interpreter's Rust harness code.** Rejected: a Rust harness engine does not fit the Node-sidecar spine; violates originality-over-wrappers; policy bucket 3 mandates reverse-engineering the behavior instead (done in Phases 2 and 6).
- **OI-N2 - The "any hosted provider" dynamic catalog** (`write_provider_catalog.py` across cloud providers). Rejected: conflicts with the `LocalAdapterRegistry` loopback guard and local-first posture; local-only provider registration stands.
- **OI-N3 - Bundling `trycua` for native computer-use.** Rejected/gated: heavy dependency and new attack surface; any future native driver is an internal, opt-in, permission-tiered build (see OI-A4-native above).

From the Laguna-S-2.1 comparison:
- **LG-N1 - Bundling Laguna weights or making it a default `recommended.json` pick.** Rejected: 118B total exceeds the single-GPU 24 GB ceiling even at low bit (Design Principle 3); gated patient/offload tier only.
- **LG-N2 - Consuming Laguna via the Poolside API or OpenRouter.** Rejected: outbound third-party generation with per-token billing; MCP Registry Policy "hard no" on generation-as-a-service; conflicts with "Zero Tokens Billed".
- **LG-N3 - Opening the EM.P3 / EM.P4 gates specifically to ship Laguna ahead of independent benchmarks.** Rejected/gated: the v1.12 roadmap requires runtime support + independent benchmarks before flipping either gate (`docs/v1/v1.12/known-gaps.md`); premature enablement risks OOM and unbounded latency on target hardware.
