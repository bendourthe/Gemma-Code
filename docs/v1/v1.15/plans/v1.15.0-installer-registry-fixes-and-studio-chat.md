# Plan - Post-Reinstall Fixes and Chat-Style Studios

**Project**: Nexus AI Studio
**Version**: v1.15.0 (ships as the next 2.x semantic-release)
**Slug**: installer-registry-fixes-and-studio-chat
**Plan Type**: Feature / Enhancement + Bug-fix campaign
**Created**: 2026-07-22
**Goal**: Resolve the five reinstall-reported issues so the installer launches correctly and downloads models reliably, the app truly reflects and manages installed models, the window behaves like a normal maximized desktop app, and Image Studio and Video Lab become intuitive chat interfaces for non-technical users.

## Overview

This milestone addresses five defects the user hit while reinstalling with the new installer. Investigation traced each to a concrete root cause. Issue 1 (installer opens on the "Installation Complete" page): a terminal `state.json` (`status:"completed"`) at `%LOCALAPPDATA%\NexusInstaller\` is never cleared, so the startup planner routes every cold launch to the Complete page, and the uninstaller does not remove it. Issue 2 (models fail to download): the two failures in the user's log (Gemma HTTP 400 from a broken Unsloth GGUF pull target; SANA int4 HTTP 401 from an access-gated repo) are already fixed in the current `core/registry/catalog.json`, meaning the user ran a build predating those fixes; the remaining work is guaranteeing the shipped installer carries the fixed catalog and giving non-technical users a clear, skippable gated-model token flow plus a post-install verify/retry. Issue 3 (app shows only 1 model): the Settings > Models page is still wired to a hardcoded mock client, `models.list` is an unimplemented IPC stub, and the installer's on-disk weights tree and Ollama store are never enumerated. Issue 4 (missing window controls, not maximized): the custom titlebar is fully built and wired but is buried under an opaque `z-index:0` backdrop, and nothing ever maximizes the window. Issue 5 (Image/Video tabs too technical): the parameter-heavy four-tab forms should become chat interfaces mirroring Local Chatbot, with an attachment-capable composer that infers intent (text-to-image, image-to-image, inpaint, outpaint; text-to-video, image-to-video) from attachments and prompt. Issue 6 (VS Code extension broken): the `nexus.coding.newChat` command reports "not found" and the Chat/Memory/Traces webviews load forever because activation throws before commands and webview providers are registered - the eagerly-imported `better-sqlite3` native module can fail to load (Electron ABI mismatch, worsened by the `package:quick` path that skips the electron-rebuild), and `activate()` has no error containment while the memory-subsystem constructor (on by default) is unguarded; the extension also needs renaming to "Nexus Code" and a UX rework to match the Claude Code VS Code extension.

Delivery is a Tauri desktop app (React frontend + TypeScript sidecar + Python diffusion runtimes) distributed through the Windows Python installer, all local-first via Ollama and on-disk diffusers weights. The sidecar diffusion/video protocol already supports every image and video mode via base64 parameters, so the studio redesign is a frontend effort with no protocol change. The registry fix (Issue 3) is sequenced before the studio redesign (Issue 5) because it produces the real model lists the new chat model selectors consume.

Success looks like: a fresh double-click of the installer starts at Welcome; a clean run installs the default model set with no unexplained failures and a plain-language summary; the app opens maximized with working minimize/maximize/close; the Models page lists exactly what is installed and can install/remove; and a non-technical user can open Image Studio or Video Lab, drag in an image (or none), type a request, and get a generation back in a chat thread with parameters tucked behind an optional Advanced panel.

## Phase 2: Installer Relaunch State Machine (Issue 1)

**Goal**: A fresh installer launch always starts at Welcome; a completed install no longer permanently redirects to the Complete page, and uninstall clears installer state.
**Prerequisites**: None (installer is independent of the desktop app).
**Stability Gate**: After a successful install, relaunching the installer opens the Welcome page (not Complete); the in-session tray "reattach shows results" behavior still works; uninstalling removes `%LOCALAPPDATA%\NexusInstaller\`; unit tests cover each startup status.

**Recommended model**: Strong reasoning tier, high effort - claude-opus-4-8 (high). Rationale: startup decision has several states (completed/failed/cancelled/running/interrupted) and interacts with the single-instance path; correctness matters to avoid regressing the tray reattach.

### Sub-tasks

#### 2.1 - Clear terminal state on Complete-page acknowledgement

**Objective**: Treat a completed run as a one-time results view, not a permanent redirect.

**Prompt**:
> In the Nexus AI Studio installer (`scripts/installer/src/nexus_installer/`), a successful install writes `%LOCALAPPDATA%\NexusInstaller\state.json` with `status:"completed"` (`background/recorder.py:202-212`) and nothing deletes it. Make leaving the Complete page clear that state: in `pages/complete.py` `on_finish()` (~line 254), delete the state file via `background.paths.state_file()` (use `Path(...).unlink(missing_ok=True)`), and/or perform the same deletion immediately after `window.switch_page(...Complete)` in `main.py` (~line 554). Ensure deletion is best-effort and never crashes the finish flow. Acceptance: after clicking Finish (or closing from the Complete page), `state.json` is gone; a subsequent launch does not route to Complete.

---

#### 2.2 - Do not treat a cold terminal state as show-complete

**Objective**: Reserve the Complete-redirect for genuine in-session tray reattach, not future cold launches.

**Prompt**:
> In `scripts/installer/src/nexus_installer/background/resume.py`, `interpret_startup()` (~lines 48-61) currently returns `DECISION_SHOW_COMPLETE` for any `STATUS_COMPLETED`/`STATUS_FAILED` state (lines 54-56), which is what wrongly redirects cold relaunches. Change the logic so a cold relaunch (the persisted-state path, `primary_alive=False` in `background/startup.py:plan_startup`) with a terminal status returns `DECISION_FRESH`, while `DECISION_SHOW_COMPLETE` remains reachable only for the in-session reattach that arrives through the single-instance `signal_running_instance` path (see the T703 docstrings in `startup.py` and `single_instance.py`). If a freshness gate is cleaner, gate show-complete on `updated_at` recency plus matching pid/session instead. Verify `main.py:486-487` and `:553-560` still route correctly: `DECISION_FRESH` -> `show_first_page()` (Welcome). Do not break the explicit "Start over" cleanup at `main.py:505-512`. Acceptance: cold relaunch after a completed/failed run shows Welcome; the tray reattach still shows the Complete results view.

---

#### 2.3 - Uninstaller clears the installer state directory

**Objective**: Uninstall fully resets installer state so a reinstall is clean.

**Prompt**:
> Neither uninstall section removes the background-state dir `%LOCALAPPDATA%\NexusInstaller\`. Add its removal to both NSIS uninstall sections: `scripts/installer/legacy/nexus-setup.nsi` (`Section "Uninstall"`, ~lines 135-154) and `scripts/installer/legacy/setup.nsi` (`Section "Uninstall"`, ~lines 217-245), e.g. `RMDir /r "$LOCALAPPDATA\NexusInstaller"`. Confirm this directory name matches `background/paths.py` (`APP_DIR_NAME = "NexusInstaller"`, `_STATE_FILE = "state.json"`). Acceptance: after uninstall, `%LOCALAPPDATA%\NexusInstaller\` no longer exists, so a later installer launch starts fresh even without the 2.1/2.2 fixes.

---

#### 2.4 - Testing and Stabilization

**Objective**: Prove the startup decision across all statuses and cover it in CI.

**Prompt**:
> Add pytest coverage under `scripts/installer/` for the startup decision: table-driven tests over `interpret_startup` / `plan_startup` for each status (completed, failed, cancelled, running-owner-gone, interrupted) in both the cold (`primary_alive=False`) and in-session paths, asserting `DECISION_FRESH` for cold terminal states and `DECISION_SHOW_COMPLETE` only for in-session reattach. Add a test that `pages/complete.py on_finish()` unlinks the state file. Run the installer test suite (the `.venv` under `scripts/installer/` with pytest) and iterate until green. Update/extend CI to run installer tests, gated by a path filter on `scripts/installer/**` (with concurrency cancel-in-progress and pip caching) so desktop-only changes do not trigger them. After tests pass, run `/generate-session-history` for Phase 2.

## Phase 3: Installer Download Reliability + Gated-Token UX (Issue 2)

**Goal**: The shipped installer provably carries the current fixed catalog, gated models present a clear skippable HuggingFace-token flow, and a post-install summary reports and lets the user retry any failed model.
**Prerequisites**: None.
**Stability Gate**: A build check fails if the packaged installer would ship a stale `catalog.json`; a gated model with no token produces an explained, skippable prompt (decline omits the model, no 401 loop); the installing page ends with a plain-language success/failure summary and a working retry for failed models.

**Recommended model**: Strong reasoning tier, high effort - claude-opus-4-8 (high). Rationale: packaging-correctness reasoning (what actually ships in the bundle) plus careful non-technical UX copy and retry semantics.

### Sub-tasks

#### 3.1 - Guarantee the shipped installer carries the current catalog + reliability fixes

**Objective**: Ensure users cannot run a build with the old broken catalog (the root of the user's log).

**Prompt**:
> The user's failing log predates the fixes in commits `e8b500c` (v1.13.0) and `ae3172d` (v1.14.0); the current `core/registry/catalog.json` already reroutes Gemma to `ollama://gemma4:12b` and flags `sana-1.6b-int4` as `gated`. Confirm the packaged installer bundles the current `core/registry/catalog.json` via `nexus_installer.registry_paths` (the `sys._MEIPASS` bundle path used by `engine/model_router.py:default_catalog_path()` and `pages/typed_catalog.py`). Add a packaging/build guard (a PyInstaller spec assertion or a `scripts/` check run in CI/build) that fails if the bundled catalog is missing or does not match the repo `core/registry/catalog.json` (e.g. hash compare), so a stale catalog can never ship. Document in the installer README/notes how the catalog is sourced at build time. Acceptance: building the installer embeds the live catalog; the guard fails a deliberately-staled catalog.

---

#### 3.2 - Clear, explained, skippable gated-model token flow

**Objective**: Non-technical users understand and can skip the HuggingFace token step without a cryptic failure.

**Prompt**:
> The gated-auth subsystem exists (`engine/gated_auth.py:ensure_gated_auth`, invoked from `pages/installing.py:_resolve_gated_auth` ~lines 197-207; token discovery in `engine/hf_auth.py`; puller fast-skip + permanent-401 in `engine/hf_weights_puller.py`). Improve the UX for non-technical users: (a) the gated-model dialog copy should explain in plain language what a gated model is, that it needs a free HuggingFace account + token, exactly where to get one, and that clicking Skip simply omits that one model and continues; (b) ensure a decline cleanly removes the model from the queue (no 401 retry loop) and is reflected in the final summary as "skipped (needs token)", distinct from "failed"; (c) if a token is entered, validate it against the repo (`hf_auth.validate_token_for_repo`) before queueing and show a clear success/failure message. Keep the token user-supplied and never logged (`mask_token`). Acceptance: installing with the default set that includes a gated model shows the explained prompt; Skip continues successfully; a valid token unlocks the download.

---

#### 3.3 - Post-install model verification and retry

**Objective**: End the install with a plain-language summary and a retry path for failures.

**Prompt**:
> On the installing/complete page, present a per-model outcome summary in non-technical language: succeeded, skipped-needs-token, and failed (with a short human reason, e.g. "download error" or "model server rejected the model" rather than raw "Error: 400"/"401"). Distinguish Ollama-pull failures from HuggingFace-download failures and from gated skips. Add a "Retry failed models" action that re-runs only the failed/queued ids through the existing `engine/model_router.py` install path (reusing `model_preflight` where available) without redownloading already-verified models. Ensure the summary and retry integrate with the background state/recorder so retries update `state.failed_models`. Acceptance: after a run with one failure, the user sees a clear summary and can retry just that model; a subsequent success clears it from the failed list.

---

#### 3.4 - Testing and Stabilization

**Objective**: Cover the packaging guard, gated flow, and retry; wire CI.

**Prompt**:
> Add tests: (a) a build/packaging test asserting the bundled catalog matches `core/registry/catalog.json`; (b) unit tests for the gated decline path (model removed, marked skipped, no retry loop) and the token-validate path; (c) unit tests for the retry action re-queuing only failed ids and updating `state.failed_models`; (d) a summary-formatting test mapping raw errors (400/401/network) to the plain-language reasons. Use the installer pytest suite and fakes for network/Ollama. Run until green, then update CI (installer path-filtered job, caching, cancel-in-progress). After tests pass, run `/generate-session-history` for Phase 3.

## Phase 5: Image Studio Chat Redesign (Issue 5, Image)

**Goal**: Image Studio becomes a chat interface (model selector + history + composer) where the user pastes/drags/uploads one or more images (or none) and asks to generate/inpaint/outpaint; intent is inferred; technical parameters live behind an Advanced popover with smart per-GPU-tier defaults.
**Prerequisites**: Phase 4 (real image-model list for the selector).
**Stability Gate**: With no image, a prompt does text-to-image; with an attached image it does image-to-image; with a painted mask it inpaints; with an outpaint request + image it outpaints; generated images render inline in the thread with download/copy-workflow/use-as-source actions; no mode tabs remain; the four sidecar endpoints are called unchanged.

**Recommended model**: Strong reasoning tier, high effort - claude-opus-4-8 (high). Rationale: net-new composer (multi-attachment, drag/paste), intent-inference logic, and media-message rendering; the reusable scaffold built here is consumed by Phase 6.

### Sub-tasks

#### 5.1 - Shared chat-studio scaffold: attachment composer + media messages

**Objective**: Build the reusable pieces the image (and later video) chat needs.

**Prompt**:

## Phase 7: VS Code Extension - "Nexus Code" Activation Fix + Claude Code-Style UX (Issue 6)

**Goal**: The VS Code extension activates reliably (commands register, sidebar views render), is renamed to "Nexus Code", and its chat experience matches the Claude Code VS Code extension.
**Prerequisites**: None (the extension is independent of the installer, registry, and studio work).
**Stability Gate**: On a clean VS Code install of the packaged VSIX, the extension activates without error even when the memory DB / native module is unavailable; `nexus.code.newChat` (and legacy `nexus.coding.newChat` via the shim) work; the sidebar renders its chat UI with no perpetual spinner; the product reads "Nexus Code" everywhere; the chat panel provides a Claude Code-style experience.
**Recommended model**: Strong reasoning tier, high effort - claude-opus-4-8 (high). Rationale: native-module/activation-resilience work plus a substantial UX rework; both are high-risk.

### Sub-tasks

#### 7.1 - Make activation crash-proof (fix "command not found" + forever-loading views)

**Objective**: Register commands and webview providers regardless of engine/DB/native-module failures.

**Prompt**:
> The extension fails because `activate()` throws before commands/providers register. Root cause: the eagerly-imported `better-sqlite3` native module can fail to load (Electron ABI mismatch), and `activate()` (`src/extension.ts:45-57`) has no try/catch; the only unguarded subsystem constructor `buildMemorySubsystem` (`src/panels/ChatPanelInit.ts:89-112`) runs by default (memory is on by default) and its throw aborts activation, so the late-registered command `nexus.coding.newChat` (`src/activation/extensionOnly.ts:320`) and the three webview providers (`extensionOnly.ts:263,:304,:313`) never register -> "command not found" + forever-spinning Chat/Memory/Traces views. Fix: (a) register ALL commands and webview providers BEFORE any heavy engine/DB construction (`new NexusCodingPanel` at `extensionOnly.ts:152`) so the UI surface always exists; (b) wrap the activation branch calls in `src/extension.ts` (`activateProxy`/`activateExtensionOnly`, ~lines 45-57) in try/catch that logs to the output channel and still registers the command/provider surface; (c) add try/catch to `buildMemorySubsystem` mirroring its guarded siblings (return `MemorySubsystem.disabled()` on failure); (d) lazy-load `better-sqlite3` behind the memory feature flag so a missing/ABI-mismatched native binary degrades to a working, memory-disabled extension instead of a dead one. Acceptance: with the memory DB unavailable or the native module unloadable, the extension still activates, all `nexus.*` commands run, and the sidebar renders content.

---

#### 7.2 - Fix native-module packaging + Windows daemon discovery

**Objective**: Ship a VSIX whose native module matches the host Electron, and stop mis-detecting the daemon on Windows.

**Prompt**:
> Two reliability fixes. (a) Packaging: `scripts/build-vsix.ps1` rebuilds `better-sqlite3` for a hardcoded Electron `36.4.0` (~line 105), while `package:quick` (`vsce package`, `package.json:947`) skips the rebuild entirely; either can ship a binary whose ABI mismatches the installed VS Code (`engines.vscode: ^1.90.0` spans several Electron majors). Parameterize the Electron version (derive it from the target VS Code / a config rather than hardcoding), ensure the release path always runs `@electron/rebuild`, and add a guard so a release VSIX cannot be built via the quick path. Document the supported VS Code/Electron range and consider bundling/prebuilding the binary. (b) Windows daemon discovery: `discoverDesktopDaemon` (`src/desktop/daemonDiscovery.ts:78-93`) uses `existsSync` on a named pipe `\\.\pipe\nexus.<user>.sock`, which its own comment says is unreliable; implement the live pipe ping the comment describes (or make extension-only the honest, explicit Windows default) so the activation branch is chosen correctly. Acceptance: a release VSIX activates on the supported VS Code versions; discovery returns the correct branch on Windows.
