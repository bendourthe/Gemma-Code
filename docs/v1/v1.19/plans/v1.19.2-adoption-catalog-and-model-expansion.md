## Phase 1: Catalog, Model, and Tier Additions + Patient-Tier Calibration

**Goal**: Extend the registry and installer so every later phase of the plan family has the model plumbing it needs: the calibrated patient-tier copy, the merged modality/audio schema, quantized-weight delivery, the Hermes family with harness profiles, the Inkling-Small patient-tier entry, and the calibrated patient tier with presets and a determinism assertion.
**Prerequisites**: v1.19.1 Phase 2.4 (per-model compression thresholds feed the Hermes harness profiles in 1.5). Internal ordering: 1.1 before 1.7 (K2 numbers feed the presets); 1.2 before 1.4/1.6 (entries use the new fields); 1.3 before 1.6 (GGUF variant delivery); 1.4 before 1.5 (profiles need entries).
**Stability Gate**: The patient-tier warning floor covers measured trillion-class throughput; catalog schema validates with `modalities` and `audioConditioning` fields; the puller selects and sha256-verifies precision-variant file sets; Hermes entries pass license/provenance checks and drive harness profiles validated on the golden suite; the Inkling entry is opt-in, patient-tagged, never a `recommended.json` default; the determinism-across-budget golden variant runs (skip-if-no-adapter).
**Recommended model**: Mid tier, medium effort - claude-sonnet-5 (medium). Rationale: schema, data, config, and one installer path over existing, well-tested pipelines. Re-confirm against the then-current model set at implementation.

### Sub-tasks

#### 1.1 - Patient-tier throughput honesty (Kimi K2)

**Objective**: Calibrate the patient tier's advertised numbers against independent measurement.

**Prompt**:
> Update `core/registry/patientTier.ts` `PATIENT_TIER_LATENCY_WARNING` (currently "roughly 0.05-2 tokens/sec") to a floor honest against kimi-k3-in-c's measured ~0.03 tok/s (~32 s/token laptop, ~19-21 s/token server) for trillion-class MoE models, and add per-model `expected s/token` plus measured-peak-RSS fields to patient-tier entries in `core/registry/catalog.json` where measurements exist. Data and copy only; no behavior change. Acceptance: the warning floor covers ~0.03 tok/s; patient-tier catalog entries carry expected-throughput fields; existing tier gating tests still pass.

---

#### 1.2 - Merged catalog schema extension: modalities + audio conditioning (Inkling A1 + LongCat A4, per D5)

**Objective**: One schema wave carrying both new field groups.

**Prompt**:
> Extend the catalog schema once with both field groups: (a) a `modalities` input-modalities array (e.g. `["text","image","audio"]`) in `core/registry/catalog.json` entries and `core/registry/catalog.ts` types, so chat surfaces can gate image/audio attachment affordances per selected model (consumed by the v2.0.0 plan's multimodal chat phase); (b) `audioConditioning` fields in `DiffusionTierVideoDefaults` (`core/config/DiffusionTier.ts`) and catalog video entries, so the Video Lab can gate audio-input modes per model/tier (consumed by the v2.0.0 plan's Video Lab phase). Backfill `modalities` for existing entries (text-only unless documented otherwise). Acceptance: schema validates; types compile; existing entries backfilled; both downstream consumers have the fields they need documented.

---

#### 1.3 - Quantized-weights tier in the installer (LongCat A3, shared per D6)

**Objective**: Precision-variant weight delivery with unchanged sha256 discipline.

**Prompt**:
> Extend the catalog `weights` schema and `scripts/installer/src/nexus_installer/engine/hf_weights_puller.py` to support precision-variant file sets per model (e.g. fp16/int8/fp8/GGUF-quant lines, each with its own file list and per-file sha256), plus selection logic (hardware-aware default, explicit user override). `scripts/installer/src/nexus_installer/engine/model_preflight.py` verification applies to whichever variant is selected. Only first-party/official variants are eligible (LongCat comparison N2: no unvetted community re-quantizations). Acceptance: a catalog entry can declare multiple precision variants; the puller downloads and verifies exactly the selected set; installer tests cover selection + verification.

**Dependency note**: this mechanism is consumed twice -- by the Inkling-Small patient-tier GGUF entry in 1.6 (this plan) and by the Avatar-1.5 INT8 weights in the v2.0.0 plan's Video Lab phase. The build lives here; the v2.0.0 plan carries a dependency pointer back to this task.

---

#### 1.4 - Hermes-family catalog entries (Hermes A4, P0 in source)

**Objective**: The Hermes/Nous open-weight family enters the catalog.

**Prompt**:
> Curate Hermes-family local model entries into `core/registry/catalog.json` (currently zero Hermes/Nous entries) through the existing Ollama/Hugging Face pipeline: correct `license`, `origin`, `provenance`, `releaseDate`, `agentic: true` where applicable, VRAM requirements, pinned sha256 digests, and the new `modalities` field from 1.2. Apply the catalog curation rules (license + provenance verification per entry; best-of-family collapse; hardware-tier fit). Acceptance: entries validate, install via the existing pipeline on a test host, and appear in the Agentic tab with correct pills.

---

#### 1.5 - Hermes harness profiles (Hermes A5)

**Objective**: Per-model harness tuning for the new family.

**Prompt**:
> Add Hermes-model profiles to `modules/coding/orchestration/HarnessSelector.ts` (scaffold, per-model compression thresholds from v1.19.1 Phase 2.4, tool-call format quirks), and validate them via `modules/coding/orchestration/HarnessSelectorAb.ts` A/B runs against `modules/coding/evaluation/GoldenTaskSuite.ts`. Acceptance: profiles exist for each catalogued Hermes model; A/B results recorded in the phase session history; golden suite green with the profiles active.

---

#### 1.6 - Inkling-Small patient-tier entry (Inkling A4)

**Objective**: Opt-in frontier-class multimodal entry, honestly framed.

**Prompt**:
> Curate `inkling-small` into `core/registry/catalog.json` as an opt-in, never-default entry tagged for the patient tier (`core/registry/patientTier.ts`), sourced from the official/established GGUF line via the 1.3 variant mechanism, with honest sizeGB (74.8+ GB), the calibrated latency warning, Apache-2.0 license metadata, and `modalities` reflecting what the quantized artifact actually supports -- if GGUF multimodal (image/audio projector) support is unverified in llama.cpp at implementation time, ship the entry text-only and document that gap in the entry copy (comparison Section 9). Never add it to `core/registry/recommended.json` per-VRAM defaults. Acceptance: entry validates, is visible only through the patient-tier gate, carries the warning, and its modality claims match verified runtime support.

---

#### 1.7 - Patient-tier RAM-budget presets + determinism assertion (Kimi K1 + K3, per D7)

**Objective**: Preset-shaped expectations and an offload correctness property.

**Prompt**:
> (a) K1: add RAM-budget preset metadata (laptop / workstation / max shaped) to patient-tier catalog entries plus settings copy, seeded from the 1.1 measured numbers -- Nexus ships expectations and copy; the actual expert-cache sizing lives in the user-registered llama.cpp-lineage adapter, and the copy must not imply Nexus bundles the offload runtime. (b) K3: add a golden-suite variant via `modules/coding/evaluation/GoldenTaskRunner.ts` asserting byte-identical output across two offload configurations of the same model (skip-if-absent when no patient-tier adapter is registered on the test host). Acceptance: presets render in settings with per-preset expected s/token; the determinism test runs green where an adapter exists and skips cleanly where not.

---

#### 1.8 - Testing and Stabilization

**Objective**: Validate calibration copy, schema, puller, entries, and profiles; wire CI.

**Prompt**:
> Run the registry schema validation and the registry test suite covering `patientTier.ts` and `catalog.json` (including the 1.1 warning-floor and expected-throughput fields), the installer test suite (including the new variant-selection tests and `scripts/installer/tests/test_patient_tier_gate.py`), the harness A/B + golden suite, and lint/typecheck across touched packages; iterate to green. Update CI to cover `core/registry`, `core/config`, and the installer engine paths, including path filters if catalog data files gained new fields. Do not mark this plan complete until stable. After tests pass, run `/generate-session-history` for Phase 1.
