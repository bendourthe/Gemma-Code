## Overview

This subplan carries the first two phases of the original v2.0.0 milestone wave, split out per the maintainer's decision so the near-term, well-bounded hardening theme ships as a v1.19 minor while v2.0.0 becomes the convergence release. It operationalizes the agent-governance theme the seven v2.0 comparisons converge on: QM contributes the named security-posture dial, command-level hard denials that survive every posture, and provenance-labelled content screening; Airi's Minecraft agent, Atomic Agent's no-progress veto, and Hermes Herald's iteration-ceiling revisit merge into one `LoopGuards` layer for `src/tools/AgentLoop.ts` (dedup decision D1 in the v2.0.0 plan); Hermes additionally contributes tool self-recovery, context-compression patterns, and DNS-pinned egress; Atomic contributes two small read-only fs tools; Airi contributes action-introspected system prompts.

Per the MCP Registry Policy's reverse-engineer-first ordering, skill-native items land first (Phase 1), then the hardening builds (Phase 2). Every merge/dedup decision governing this subplan (D1-D4, D12, D13) is recorded in the v2.0.0 plan's Cross-Source Dedup Decisions section, which remains the single source of truth for the whole plan family. The consolidated "Out of Scope / Rejected" section also lives in the v2.0.0 plan and binds this subplan in full; no rejection may be revisited here.

Success looks like: the agent loop cannot run away (veto, budgets, burst guards, hard denials in every posture); the user has one named dial for security posture with the floor clamp authoritative everywhere; tool results carry provenance labels through the injection scanner; individual tool failures recover instead of derailing runs; and the label schema is ready for the v2.0.0 plan's browser snapshots to plug in without change.

## Phase 2: Agent-Loop + Guardrail Hardening

**Goal**: Make long-horizon autonomous runs trustworthy before any new tool surface ships: command-level hard denials in every posture, unified loop circuit breakers, tool self-recovery, compression reliability, a named security-posture dial, provenance-labelled screening, DNS-pinned egress, and small tool-family extensions.
**Prerequisites**: Phase 1 (policy ordering). Internal ordering: 2.1 before 2.5 (the dial's invariant needs the denials); 2.6 before the v2.0.0 plan's browser tool surface phase (browser snapshots consume provenance screening).
**Stability Gate**: Hard denials block the declared command shapes in every posture including the most permissive; the loop guards (identical-call veto, no-action budget, error-burst guard, bounded queue) each trigger and halt/redirect in tests; spill files pass secret scrubbing; the posture dial only composes existing gates and cannot drop below the tier clamp; tool results carry origin labels through `PromptInjectionScanner`; `ssrf.ts` fetches connect to the DNS-pinned resolved address; golden-task suite green with compression changes.
**Recommended model**: Strong tier, high effort - claude-opus-4-8 (high). Rationale: this is the security-critical core of the wave; a mistake here weakens every later phase of the plan family. Re-confirm against the then-current model set at implementation.

### Sub-tasks

#### 2.1 - Command-level hard denials (QM A3, P0)

**Objective**: A declarative deny-list for command shapes that applies in every posture.

**Prompt**:
> Extend `modules/coding/guardrails/ActionClassifier.ts` and the terminal handler (`src/tools/handlers/terminal.ts`) with a predeclared, declarative deny-list for destructive command shapes (recursive deletes, destructive SQL, git history rewrites, and similar), reverse-engineered from QM's "predeclared command policy ... applies in every posture, Dangerous included". The list is evaluated before the allowlist and before any tier/confirmation logic, and is strictly subtractive: it can only block, never permit. Make the deny-list data-driven (one declaration file) so Phase 2.5's postures can reference it as a shared invariant. Acceptance: each declared shape is denied under every permission configuration, including maximum-permissiveness; the deny path is covered by unit tests per shape; nothing previously blocked becomes allowed.

---

#### 2.2 - Unified loop guards (Airi A2 + Atomic C4 + Hermes iteration ceiling; merged per D1)

**Objective**: One circuit-breaker layer for auto-mode runs.

**Prompt**:
> Implement a unified loop-guard layer for `src/tools/AgentLoop.ts` auto mode, integrating with (not duplicating) `modules/coding/guardrails/LoopDetector.ts`, with four named guards: (1) identical-call veto -- abort/redirect after N identical consecutive tool calls (Atomic's N=5 as default, configurable); (2) no-action budget -- cap consecutive non-tool "thinking" turns (Airi); (3) error-burst guard -- halt on a burst of consecutive tool errors (Airi); (4) bounded action queue -- cap in-flight plus pending actions (Airi's 1 executing + 4 pending as the default shape). Revisit the loop iteration ceiling deliberately (Hermes moved 90 -> 500; pick a Nexus value justified in a code comment, gated by the other guards). Guard trips must surface a clear user-facing reason and leave the session recoverable. Acceptance: each guard triggers in a dedicated unit test and halts/redirects; a normal multi-step run is unaffected; guard thresholds are configurable in one place.

---

#### 2.3 - Tool self-recovery (Hermes A2)

**Objective**: Recover individual tool failures instead of losing them.

**Prompt**:
> Add Hermes Herald's tool self-recovery patterns to the `src/tools/` handlers: (1) truncated terminal/tool output spills to a readable local file and the model is told the path and how to page it -- spill files MUST pass through the `redactSecrets` / `secretPaths.ts` scrubbing path before being written or re-read into context; (2) patch/edit tools detect an already-applied edit and report success-noop instead of failing; (3) search tools return near-miss probes (closest candidates) when an exact match fails. Acceptance: each behavior covered by a unit test (oversized output spills and is scrubbed; re-applied patch is a noop; failed search returns probes); no handler regresses its existing contract.

---

#### 2.4 - Context-compression patterns (Hermes A1; scope per D13)

**Objective**: Per-model, reliability-focused compaction.

**Prompt**:
> Layer Hermes Herald's compression overhaul onto `modules/coding/chat/ContextCompactor.ts` / `CompactionStrategy.ts`: per-model compression thresholds keyed off the `modules/coding/orchestration/HarnessSelector.ts` per-model profile, per-turn micro-compaction, proactive tool-result pruning, and guaranteed N-user-message tail retention (the last N user messages are never compacted away). Validate against the golden task suite via `modules/coding/evaluation/validationGate.ts` before merge -- the known risk is over-pruning context. Confirm the existing `compress_range` / `compress_message` tools compose with (and are not duplicated by) the new strategies. Acceptance: thresholds resolve per model; the user-message tail survives aggressive compaction in tests; golden-task gate green.

---

#### 2.5 - Security-posture dial (QM A2)

**Objective**: One named, user-facing control composing the existing guardrails.

**Prompt**:
> Build named security-posture presets (working names: Strict / Standard / Unattended) as pure compositions over the existing `modules/coding/guardrails/PermissionTiers.ts`, `src/tools/ConfirmationGate.ts`, and the `src/tools/AgentLoop.ts` auto-mode verification gate, plus a settings UI surface for selecting the posture. Invariants (non-negotiable): the `PermissionTiers.ts` floor clamp remains authoritative in every posture; the Phase 2.1 hard denials apply in every posture; the most permissive posture means "fewer confirmations above the floor", never "no floor" -- Nexus must NOT ship a literal QM "Dangerous" mode. Each posture is documented in plain language in the settings surface. Acceptance: switching postures changes only confirmation frequency/screening strictness; property-style tests assert that no posture permits a tier-clamped or hard-denied action; the dial state persists across sessions.

---

#### 2.6 - Provenance-labelled content screening (QM A5; shared with the v2.0.0 browser phase per D4)

**Objective**: Origin labels on everything untrusted, screened before it reaches the model.

**Prompt**:
> Add provenance labelling to tool results and external content: tag every tool result with an origin class (user, workspace file, terminal output, web fetch, MCP tool, browser snapshot -- reserve the last for the v2.0.0 plan's browser tool surface), and route externally-originated content through `modules/coding/guardrails/PromptInjectionScanner.ts` before it enters the model context, per QM's Auto-posture classifier pattern. Screening strictness may vary by posture (Phase 2.5) but never turns off for web/browser/MCP origins. Design the label type so the v2.0.0 plan's ARIA snapshots plug in without schema changes. Acceptance: origin labels present on tool results end-to-end in tests; a seeded injection payload in a web-fetch result is flagged/neutralized; label taxonomy documented.

---

#### 2.7 - DNS-pinned egress fetches (Hermes A6)

**Objective**: Close the DNS-rebinding TOCTOU gap in the SSRF guard.

**Prompt**:
> Harden `modules/coding/utils/ssrf.ts` with DNS pinning reverse-engineered from Hermes's Ironproxy pattern: resolve the hostname once, validate the resolved address against the SSRF policy, then connect to that pinned address (not a re-resolved name) for the actual fetch. Strictly tightening; no behavior change for already-valid fetches. Acceptance: a unit test simulating a rebinding resolver (first resolution public, second private) shows the fetch uses the pinned first resolution and the private target is never contacted; existing ssrf tests still pass.

---

#### 2.8 - watch/hash file tools (Atomic C2)

**Objective**: Two small read-only additions to the fs tool family.

**Prompt**:
> Add `watch_path` (observe filesystem changes during a run, scoped to the workspace root, `fs.watch`-based) and `hash_file` (cheap content hash for integrity/change detection, `crypto`-based) handlers under `src/tools/`, registered in `src/tools/ToolRegistry.ts` with AUTO_APPROVE tier entries in `modules/coding/guardrails/PermissionTiers.ts` (read-only justifies the tier). `watch_path` must reject paths outside the workspace root. Acceptance: both tools work end-to-end in tests; out-of-workspace watch is rejected; tier entries present.

---

#### 2.9 - Action-introspected system prompts (Airi A4)

**Objective**: Prompts and tools in lockstep.

**Prompt**:
> Build a prompt assembler that walks `src/tools/ToolRegistry.ts` and emits compact typed per-tool docs into the system prompt, reverse-engineered from Airi's action-registry introspection (Zod-typed docs), using Nexus's existing `modules/coding/llm/ToolCallFormat.ts` types as the source of truth. Replaces any hand-maintained tool descriptions in the prompt so a registered tool can never be undocumented or stale. Acceptance: prompt tool docs are generated, not hand-written; adding a test tool to the registry surfaces it in the assembled prompt; token cost of the generated block is measured and bounded.

---

#### 2.10 - Testing and Stabilization

**Objective**: Prove the hardened loop end-to-end; wire CI.

**Prompt**:
> Add an integration-level test pass over the whole phase: a scripted auto-mode run that (a) trips each loop guard, (b) attempts a hard-denied command in the most permissive posture, (c) receives a seeded injection via a labelled web-origin tool result, and (d) exercises spill/noop-patch/near-miss recovery -- asserting the correct halt/deny/flag/recover behavior for each. Run the full coding-module suite + lint + typecheck + the golden-task gate; iterate to green. Update CI to cover the guardrails, loop, ssrf, and tools paths. Do not mark this plan complete until stable. After tests pass, run `/generate-session-history` for Phase 2.
